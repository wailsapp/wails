    Runtime Internals

    The runtime is the layer that transforms ordinary Go functions into a cross-platform desktop application.
    This document explains the moving parts you will meet when tracing through the source code.

    1. Application Lifecycle

    Phase Code Path What Happens
    Bootstrap pkg/application/application.go:init() Registers build-time data, creates a global application singleton.
    New() application.New(...) Validates Options, spins up the AssetServer, initialises logging.
    Run() application.(*App).Run() 1. Calls platform mainthread.X() to enter the OS UI thread.
    2. Boots the runtime (internal/runtime).
    3. Blocks until the last window closes or Quit() is called.
    Shutdown application.(*App).Quit() Broadcasts application:shutdown event, flushes log, tears down windows & services.

    The lifecycle is strictly single-entry: you may create many windows, but the application object itself is initialised once.

    2. Window Management

    Public API

    win := app.Window.NewWithOptions(application.WebviewWindowOptions{
    Title:  "Dashboard",
    Width:  1280,
    Height: 720,
})
win.Show()

    app.Window.New() takes no arguments; use NewWithOptions(...) when you need to pass an application.WebviewWindowOptions struct (by value).

    app.Window.New[WithOptions]() delegates to pkg/application/webview_window_*.go where the platform-specific implementations live:

    pkg/application/
├── webview_window_darwin.go    // WKWebView
├── webview_window_linux.go     // GTK + WebKitGTK (plus linux_cgo*.go)
└── webview_window_windows.go   // WebView2

    Each file:

    1. Creates a native webview (WKWebView, WebKitGTK, WebView2).
    2. Registers a Message Processor callback (pkg/application/messageprocessor*.go).
    3. Maps Wails events (WindowDidResize, WindowFocus, WindowFilesDropped, …) to the constants in pkg/events.

    internal/runtime/ is reserved for the small build-tag glue (runtime{,_darwin,_linux,_windows,_android,_dev,_prod}.go) and the embedded JS runtime under internal/runtime/desktop/.

    Active windows are tracked by pkg/application/window_manager.go / webview_window.go. pkg/application/screenmanager.go is for display metadata (resolution, scale, work area) — it does not manage windows.

    3. Message Processing Pipeline

    The bridge between JavaScript and Go is implemented by the Message Processor family in pkg/application/messageprocessor_*.go.

    Flow:

    1. JavaScript calls Call.ByID(<fnv-id>, ...args) from /wails/runtime.js (implemented in internal/runtime/desktop/@wailsio/runtime/src/calls.ts) — or Call.ByName("pkg.Struct.Method", ...args) for name-mode builds.
    2. The runtime helper packages the call and dispatches it through the per-platform native bridge into Go.
    3. Go receives the message in pkg/application/messageprocessor_call.go.
    4. The processor looks up the bound method in pkg/application/bindings.go (hand-written, reflect-based) and invokes it.
    5. The result or error is marshalled back to JS where a Promise resolves or rejects.

    The exact JSON envelope is defined by the runtime helper on the JS side and by messageprocessor_call.go on the Go side — older drafts of this page quoted a {"t":"c","id":"123","m":"Greet","p":[…]} shape, but that doesn’t match the current implementation. Read both files together when chasing a wire-format bug.

    Specialised processors:

    File Purpose
    messageprocessor_window.go Window actions (hide, maximize, …)
    messageprocessor_dialog.go Native dialogs (OpenFile, MessageBox, …)
    messageprocessor_clipboard.go Clipboard read/write
    messageprocessor_events.go Event subscribe / emit
    messageprocessor_browser.go Browser navigation, devtools

    Processors are stateless – they pull everything they need from the ApplicationContext passed with each message.

    4. Events System

    Events are namespaced strings dispatched across three layers:

    1. Application events: global lifecycle (application:ready, application:shutdown).
    2. Window events: per-window (window:focus, window:resize).
    3. Custom events: user-defined (chat:new-message).

    Implementation details:

    • Event constants live in pkg/events/ (defaults.go, known_events.go, events.txt). They are generated by v3/tasks/events/generate.go and exposed as events.Common.*, events.Mac.*, events.Windows.*, events.Linux.*. You can rebuild them with wails3 generate constants.
    • Go side (application events):
    app.Event.OnApplicationEvent(events.Common.ApplicationStarted, func(e *application.ApplicationEvent) {})
    • Go side (window events):
    window.OnWindowEvent(events.Common.WindowFocus, func(e *application.WindowEvent) {})
    • Go side (custom events):
    app.Event.On("chat:new-message", func(e *application.CustomEvent) {})
    • JS side:
    import { Events } from "/wails/runtime.js";
Events.On("chat:new-message", (e) => { /* … */ });

    Application/window/custom events all flow through pkg/application/event_manager.go. Window-event subscriptions are scoped to their window, so closing the window unregisters its handlers automatically.

    5. Platform-Specific Implementations

    Conditional compilation keeps the public API identical while hiding OS wrinkles.

    Concern Darwin Linux Windows
    Main Thread mainthread_darwin.go (Cgo to Foundation) mainthread_linux.go (GTK) mainthread_windows.go (Win32 AttachThreadInput)
    Dialogs dialogs_darwin.* (NSAlert) dialogs_linux.go (GtkFileChooser) dialogs_windows.go (IFileOpenDialog)
    Clipboard clipboard_darwin.go clipboard_linux.go clipboard_windows.go
    Tray Icons systemtray_darwin.* systemtray_linux.go (DBus) systemtray_windows.go (Shell_NotifyIcon)

    Key principles:

    • macOS and Windows use Cgo sparingly (mostly through pkg/mac/ and the w32 Win32 wrappers in pkg/w32).
    • Linux is heavily Cgo by necessity — pkg/application/linux_cgo.go (~69 KB) plus linux_cgo_gtk4.{c,go,h} (~50 KB+) drive GTK/WebKitGTK directly.
    • Use build tags (//go:build darwin, //go:build linux, …) to keep per-OS files readable.
    • internal/capabilities/ exists for per-platform capability flags, but the framework does not export an ErrCapability sentinel — feature gating is done by platform-specific stub returns.

    6. File Guide

    File Why You’d Touch It
    internal/runtime/runtime_*.go Change the small build-tag stub layer (dev vs prod, OS-specific glue).
    pkg/application/webview_window_*.go Implement a new window hint or behaviour.
    pkg/application/messageprocessor*.go Add a new bridge command callable from JS.
    pkg/events/*.go Extend built-in event definitions (then re-run wails3 generate constants).
    internal/assetserver/* Tweak dev/production asset handling.
    internal/runtime/desktop/@wailsio/runtime/src/* Edit the embedded JS runtime (call/event dispatch, dialogs, drag, …).

    7. Debugging Tips

    • Configure Options.LogLevel (e.g. slog.LevelDebug) and inspect Options.Logger output — there is no WAILS_LOG_LEVEL environment variable.
    • wails3 dev flags are --config, --port, -s (enable HTTPS) and the global --no-colour. There is no -verbose flag.
    • On macOS run under lldb -- to catch Objective-C exceptions early.
    • For Windows Chromium issues, enable WebView2 debug logs:
      set WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222

    8. Extending the Runtime

    1. Optional: declare any new capability flag in internal/capabilities/.
    2. Implement the feature in each pkg/application/*_{darwin,linux,windows}.go variant using build tags. Provide a stub on platforms that don’t support it.
    3. Add the public API in pkg/application (interface + concrete WebviewWindow methods, options struct, etc.).
    4. Register a new message-processor method (pkg/application/messageprocessor*.go) and a matching helper in the JS runtime if JS needs to call it.
    5. If you add an event, declare its constant in pkg/events/ and run wails3 generate constants to refresh the generated files.

    Follow this checklist and you’ll keep the cross-platform contract intact.

    9. Drag-and-Drop

    File drag-and-drop uses a JavaScript-first approach on all platforms. The native layer intercepts OS drag events, but the actual drop handling and DOM interaction happens in JavaScript.

    Flow

    1. User drags files from OS over the Wails window
    2. Native layer detects the drag and notifies JavaScript for hover effects
    3. User drops files
    4. Native layer sends file paths + coordinates to JavaScript
    5. JavaScript finds the drop target element (data-file-drop-target)
    6. JavaScript sends file paths + element details to Go backend
    7. Go emits WindowFilesDropped event with full context

    Platform Implementations

    Platform Native Layer Key Challenge
    Windows WebView2’s built-in drag support Coordinates in CSS pixels, no conversion needed
    macOS NSWindow drag delegates Convert window-relative to webview-relative coords
    Linux GTK3 drag signals Must distinguish file drags from internal HTML5 drags

    Linux: Distinguishing Drag Types

    GTK and WebKit both want to handle drag events. The key is checking the drag target type:

    static gboolean is_file_drag(GdkDragContext *context) {
    GList *targets = gdk_drag_context_list_targets(context);
    for (GList *l = targets; l != NULL; l = l->next) {
        GdkAtom atom = GDK_POINTER_TO_ATOM(l->data);
        gchar *name = gdk_atom_name(atom);
        if (name && g_strcmp0(name, "text/uri-list") == 0) {
            g_free(name);
            return TRUE;  // External file drag
        }
        g_free(name);
    }
    return FALSE;  // Internal HTML5 drag
}

    Signal handlers return FALSE for internal drags (letting WebKit handle them) and TRUE for file drags (handling them ourselves).

    Blocking File Drops

    When EnableFileDrop is false, we still need to prevent the browser from navigating to dropped files. Each platform handles this differently:

    • Windows: JavaScript calls preventDefault() on drag events
    • macOS: JavaScript calls preventDefault() on drag events
    • Linux: GTK signal handlers intercept and reject file drags at the native level

    Key Files

    File Purpose
    pkg/application/linux_cgo.go GTK drag signal handlers (C code in cgo preamble)
    pkg/application/webview_window_darwin.go macOS drag delegates
    pkg/application/webview_window_windows.go WebView2 message handling
    internal/runtime/desktop/@wailsio/runtime/src/window.ts JavaScript drop handling

    Debugging

    • Linux: Add printf in C code (remember fflush(stdout))
    • Windows: Use globalApplication.debug()
    • JavaScript: Check browser console, enable debug mode

    Common issues:

    1. Internal HTML5 drag not working: Native handler intercepting it (return FALSE for non-file drags)
    2. Hover effects not showing: JavaScript handlers not being called
    3. Wrong coordinates: Check coordinate space conversions

    You now have a guided tour of the runtime internals. Combine this knowledge with the Codebase Layout map and the Asset Server docs to navigate confidently and make impactful contributions. Happy coding!

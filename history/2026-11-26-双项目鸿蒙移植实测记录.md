## 1. 工具链

### 1.1 Go fork 的选择

`GOOS=openharmony` 不是官方 Go 支持的目标，必须用定制 Go。

- 【实测】**A 线用 `ZxillyFork/go-hmos`**：go1.27.4-hmos-devel，带 `runtime/sigtab_openharmony.go`（保留 OHOS 自己的 SIGURG/SIGPROF，不像 Linux 那样挪用）、`runtime/cgo/gcc_openharmony.c`、`net/dnsconfig_openharmony.go`、`internal/cpu/cpu_arm64_openharmony.go`。本机直接用 windows-amd64 工具链交叉编译 x86_64，路径：
  `C:\Users\a1\sdk\go1.27.4-hmos\toolchains\81bad8b625b9c845961010ea2af776a3cb426b4a-windows-amd64`
- 【源码】**B 线用 `sysit/ohos-go`**（go1.24.6+），需两处补丁：① `*_openharmony.go/.s` 缺 build tag，stock bootstrap Go 不认 `_openharmony` 后缀，会和 linux 文件一起编 → 加 `//go:build openharmony`；② `/storage`(hmfs) 的 `fallocate` 返回 `EACCES`，Go linker 只容忍 `EPERM`/`ENOTSUP` → 在 `src/cmd/link/internal/ld/outbuf_mmap.go` 里也容忍 `EACCES`。补丁在 fork 的 `tools/ohos-go/`。
- 【源码】mygo 文档提到更完整的 go-hmos 曾因「只发布 linux-amd64 二进制、arm64 主机需自举、且自举出的新工具二进制在本机终端被 execve(EACCES) 拒绝」而未采用；本机后来正是用它的 windows-amd64 构建成功——所以这个限制是主机相关的，不是平台限制。

选型建议：**先用能直接跑起来验证目标的工具链，再考虑产物部署形态**。模拟器阶段 x86_64 + windows-amd64 工具链组合最省时间。

### 1.2 一个高频陷阱：CC 选错

【实测】不设 CC 时，Windows 上会回落到 w64devkit 的 gcc，报一串看似 Go 代码问题的错误：`implicit declaration of 'clearenv'`、`sys/mman.h file not found`、`unknown type name 'sigset_t'`、`struct sigaction` 不完整。正确写法：

```sh
set GOOS=openharmony
set GOARCH=amd64
set CGO_ENABLED=1
set CC=C:/PROGRA~1/Huawei/DevEco~1/sdk/default/openharmony/native/llvm/bin/clang.exe --target=x86_64-linux-ohos --sysroot=C:/PROGRA~1/Huawei/DevEco~1/sdk/default/openharmony/native/sysroot
```

短路径（`PROGRA~1`、`DevEco~1`，已实测存在）可省掉大量引号问题。

### 1.3 两种 Go 产物形态

| 形态 | 产物 | 谁加载 | 适用 |
|---|---|---|---|
| `c-shared` | `.so` | ArkTS 直接 `import`，C++ 薄封装若干导出函数 | A 线：多个独立导出给 ArkTS 调（`WailsStart/WailsAsset/WailsRequest…`） |
| `c-archive` | `.a` | 链进 `libentry.so`，Go 侧只暴露少量 C 入口 | B 线：Go 自绘、Go 主导生命周期（surface/touch/frame） |

【实测】`c-shared` 严格链接：`go build -mod=mod -buildmode=c-shared -ldflags=-extldflags=-Wl,--no-undefined`，用 `readelf -d` 确认 `DT_NEEDED` 含 `libace_napi.z.so` 和 `libc.so`。【实测】`c-archive` 用 `go build -buildmode=c-archive -o libapp.a .`，CMake 以 `add_library(app STATIC IMPORTED)` 链入 `libentry.so`。

### 1.4 模块依赖的离线处理

【实测】国内网络下 `go build -mod=mod` 会卡在 sum.golang.google.cn 验证（EOF）。解决：复制 fork 的 `go.sum` 到 demo 目录，并设 `GOFLAGS=-mod=mod GOPROXY=off`。

【实测】`replace` 路径在把项目复制到别处后会失效：A 线 demo 的 `replace github.com/wailsapp/wails/v3 => ../../..` 复制到新目录后解析成 `C:\Users\go.mod`，报 `The system cannot find the file specified`。改成绝对路径即可。B 线同理：`replace github.com/egoist/mygo => <fork 绝对路径>`。

## 2. A 线：Wails3 fork 全盘经验

### 2.1 M1：让 Go runtime 在 openharmony 上编译链接

- 【实测】cgo 报错的根因是 **C 前导码注释与 `import "C"` 之间的空行**。独立对照实验证明：只删这个空行，`go tool cgo` 从退出 2 变成 0。这是 cgo 的硬性语法要求，不是平台问题。
- 【实测】补齐平台接口与构建标签后，`pkg/application` 的 native 与纯 Go server 两套都编译通过——同一份代码要同时保住桌面/server 模式，不能为了鸿蒙改坏另一条。
- 【实测】最小 `c-shared` 用 `--no-undefined` 链接通过，`DT_NEEDED` 正确。
- 本地提交 `3cf654b60`。

### 2.2 M2：独立 NAPI 桥验证

- 【实测】探针源码 `v3/tests/openharmony-native-bridge/`，两次独立进程均输出
  `M2 PASS sent=true complete=true pending=true closed=true cancelled=true deadline=true`，PID 26997 / 32110，计时器触发 13 / 14 次。
- 设计要点：TSFN 独立于 Wails，验证设计本身；明确边界——**M2 通过不代表 Wails 或 ArkWeb 集成通过**。
- 本地提交 `84fa75a3a`。

### 2.3 M3：真正的 Wails runtime + ArkWeb

【实测】源码在 `C:\Users\a1\wails3\v3\tests\openharmony-hellowails\{go,harmony}`，本次另复制出音乐播放器 demo。关键点：

**架构分工**：UIAbility / WindowStage / ArkWeb 归 ArkTS；Go 跑真实 Wails runtime（`application.New` + `app.Run()` + `Event.Emit` + Service binding）。借鉴 Android/iOS 的资源与消息两条通路，但不复制 JNI 的同步线程模型。

**无 HTTP 监听**：
- 受控虚拟 origin `https://wails.localhost/`，`onInterceptRequest` 直接从 Go 资源 handler 取字节。
- 无 `INTERNET` 声明、无服务端口；页面 CSP `connect-src 'none'`；file access / popup 关闭，外域资源 403。
- 验证：设备 `netstat` 无 LISTEN 才算数。

**Webview 消息通路**：
- 页面先设 `window.wails.invoke`，动态 `import('/wails/runtime.js')`，用公开的 `setTransport` 把调用接到 `wailsOpenHarmony.request`，不改写 Runtime TS、不生成绑定包。
- `main.js` 自动 `runtime.Call.ByName('main.GreetService.Greet', ...)`，监听 `hello:tick`，检查 CSS；成功日志精确为 `M3 PASS: local HTML/JS/CSS, Greet and Go event`。
- **只有「页面出现」不算通过**；必须有 binding 返回值和事件更新。

**Go 侧导出**（`M3/go/main.go`）：
- `WailsStart` 注册服务、建名为 `main` 的 WebviewWindow、`app.Run()`、每秒 `app.Event.Emit("hello:tick", n)`。
- `WailsAsset` / `WailsMime` 对接现有 Go asset API。
- `WailsRequest`：容量 16 的并发门，调 `application.WailsOhNativeHandleRuntimeCall`，用 `window.ExecJS` 发 `wailsOpenHarmonyResolve` 回包。
- `WailsMessage` 从 C 复制字符串后异步转发；`WailsRunMain` 转主线程回调。
- 依赖包导出在**主包**显式包装成 `WailsBridgeOpen/Result/Close`，因为 `c-shared` 生成的头只声明主包导出；C++ 只 include 实际生成的 `libhomecast_go.h`，不要手写缺失的依赖包声明。

**线程与队列**（`bridge_openharmony.go` / `mainthread_openharmony.go`）：
- `pthread_mutex` 保护全局 TSFN，容量 64、`napi_tsfn_nonblocking`。
- C 对两个 `CString` 在每条路径保持唯一所有权（原实现有双重释放）。
- 统一 `uint32` 回包 ID；无回包命令用 ID 0；有返回值的只在后台等。
- `WailsOhNativeInit` 接收 ArkTS 函数；`WailsOhClose` 撤销并关闭待处理返回 channel；`ohBridgeVoid` 不等待。
- 线程本地标记 `ohOnArkTSThread` 判断是否已在 ArkTS 线程，否则异步投递 `runOnMainThread`；队列不可用时删除函数记录并 panic，让问题在测试期暴露，不要静默吞掉。

**资源/事件入口**（`platform_openharmony.go` / `asset_openharmony.go`）：
- 新增 `OpenharmonyReady()`，取消资源入口等待 10 秒，改为立即返回未就绪；`WailsRequest` 据此拒绝未就绪请求。
- 消息从无人消费的 `openharmonyWindowMessageBuffer` 接入 `application.go` 消费的 `windowMessageBuffer`。
- `wails:runtime:ready` 驱动 `WebviewWindow` 的 pending JS 队列——页面 reload 时 `dispatchWailsEvent` 可能尚未挂载，这个时序必须处理好。
- `getScreenInfoJson` 由 Go fallback 提供尺寸（ArkTS 侧回 `{}`），这不是屏幕 API 验收。

### 2.4 A 线打包踩过的错

| 错误 | 修法 |
|---|---|
| cgo 空行（见 §2.1） | 删掉注释与 `import "C"` 之间的空行 |
| ArkTS `arkts-no-any-unknown` | 显式写 `native.Asset \| null`、`OnLoadInterceptEvent`、`OnInterceptRequestEvent` |
| `.javaScriptCanOpenWindowsAutomatically` 不存在 | 改用 API 26 SDK 里的 `.allowWindowOpenMethod(false)` |
| C++ `use of undeclared identifier 'WailsOhNativeInit'` / `WailsOhOnBridgeResult` / `WailsOhClose` | 在主包加包装函数、切 C++ 调用、重新生成 Go `.so` 和头 |
| `local.properties` 写 `sdk.dir=...\\sdk` 报 SDK 管理错误 | 必须指向 `...\\sdk\\default`，且冒号要转义：`sdk.dir=C\:\\Program Files\\...\\sdk\\default` |
| 页面 binding 调用超时、Go 事件不显示，但 ExecJS 在跑 | **回包脚本的 session 守卫**：`if(window.wailsOpenHarmonySession===<session>)`，前端漏了 `Object.defineProperty(window,'wailsOpenHarmonySession',{value:session})`，所有回包被静默丢弃。先查守卫条件，别先怀疑 binding 注册 |
| `go.mod replace` 复制后失效 | 改成 fork 的绝对路径 |
| HAP 里 `.so` 的 MD5 与源 `.so` 不一致，以为打了旧包 | HAP 里是 **stripped 版本**。用 `llvm-nm \| grep MusicService` 比对符号，或 `strings` 找新加的字符串，不要直接比 MD5 |

### 2.5 A 线验证纪律

- 冷启动 PASS 记录 PID；`aa force-stop` 后重启，确认**新 PID** 的 PASS。
- 前后台：`aa start` 对已在前台的 ability 只切前台、不重载页面，不会重跑初始化日志——没新 PASS 不一定是回归。
- 设备锁屏时 `aa start` 返回 `10106102`，需手动解锁到桌面；不要因此关开发者模式或重装。
- `hilog -x` 是**读缓冲并退出**；不带 `-x` 会流式挂住（曾因此超时 180 秒）。缓冲会被 chromium 日志刷掉，PASS 要在启动后短时间内读。
- 快照：`snapshot_display -f /data/local/tmp/x.jpeg` + `file recv`。

## 3. B 线：mygo-harmony fork 全盘经验

### 3.1 架构（【源码】读 `docs/ohos-port.md`，本机未端到端验证修复版）

```
app.ets ── XComponent(libraryname:'entry')
             ▼
        libentry.so (napi_init.cpp)
             OnSurfaceCreated → mygo_surface_created(OHNativeWindow*, w, h, density)
             DispatchTouchEvent → mygo_touch(phase, id, x, y, pressure)
             OnFrame → mygo_frame()
             ▼
        libapp.a (Go: package main + internal/ohos 或 mobile backend)
```

- 一个 MyGo 窗口就是一个 XComponent。第一个全尺寸；后续窗口从 1×1 长大，页面用 `bind` 指明自己的 component 画哪个窗口。surface、触摸、坐标轴各自独立。
- **XComponent 的回调在 module 加载时注册，不是页面 bind 时**——顺序错了会丢事件。
- 【源码】surface 归属：一个 native window 上第二个窗口再建 EGL surface 会 `EGL_BAD_ALLOC`、窗口全黑且不响应触摸；修复是「谁显示谁拿 surface」，一次只有一个窗口持有。
- 【源码】host call 通道：Go 发 `{id, op, args}` JSON，经 `napi_threadsafe_function mygo_host_call` 给 ArkTS；ArkTS 用 `native.hostReply` 回 `{id,result}` / `{id,error}`，`rpc.go` 匹配等待的 goroutine。已实现 clipboard / dialog / notification。
- 【源码】文本引擎：`libnative_drawing`，`FontMgrMatchFamilyStyle` → `FontTextToGlyphs` + `FontGetWidths` → `FontGetPathForGlyph` + `PathGetBounds`，再栅格化 coverage。两个常量：`COLOR_FORMAT_ALPHA_8 = 1`、`ALPHA_FORMAT_PREMUL = 2`，写反会得到 sheared / half-width 文本（所谓「text looks broken」）。
- 【源码】其他已修问题：XDG_CONFIG_HOME/XDG_CACHE_HOME（手机没有 home，配置写不进去、每次启动回默认）、系统 back 键、theme 切换后重绘、settings 页面。

### 3.2 【实测】同 demo 在旧 checkout 上的表现

用 mygo 的 c-archive 工具链把同一个音乐播放器编成 `libapp.a`（29 MB），装进它的 HAP shell：

- 能安装、能启动、进程活着。
- HTML 确实加载了（`CallLoadHTML` 2626 字节、`mygo: call 7 of 14168 bytes`），但**页面全白**，页面 JS 的 `mygo.call` 回调不到 Go（没有 PAGE READY / binding / event 日志）。`CallSetTitle` 报 `This window state is abnormal... Window set title failed`。
- 为绕过死掉的页面 JS，在 Go 侧用定时器直接 `sound.Play()` → 触发 `CallAudioWrite`（op 69）高频写入（一次跑出 800 条 `call 69 of 3843 bytes`），在高吞吐版本上**复现了 native 崩溃**。

### 3.4 根因与上游修复（对照表）

| 根因 | 旧代码表现 | 上游修复提交 | 时间 |
|---|---|---|---|
| Go 工作线程直接 `napi_call_function` | `[CheckThread] Fatal: ecma_vm cannot run in multi-thread!`，启动 3 秒崩，栈 `napi_create_typedarray` / `mygo_ohos_call` | `371dc6f4`：改用 `napi_threadsafe_function g_calls` 投递到 JS 线程，调用方等回复（2 秒上限，超时丢弃并记日志） | 11-26 15:30 |
| `renderer.write()` 并发乱写 | NAPI async work 线程在 `libaudio.z.so` SIGSEGV | `22301fe5`：`this.audioQueue = this.audioQueue.then(() => renderer.write(buf))`，串行化；否则「千个写同时到，声音成碎片，`WriteArrayBufferToNative: Write length < 0`」 | 11-26 17:08 |

【实测】下载 `ohos-wire` 最新 tarball，确认两个修复都在源码里：`Host.ets` 有 `audioQueue` 链、`napi_init.cpp` 有 `g_calls` TSFN。

**所以：抓的 bug 在测试期间就已被作者修掉，针对当前版本提 issue 是错误报告。**

### 3.5 B 线构建经验（【实测】）

- 同 demo 的 `go.mod` 要 `replace github.com/egoist/mygo => <fork 路径>`，并复制 fork 的 `go.sum` + `GOPROXY=off`。
- 编辑时行号漂移会改坏代码（曾出现 `undefined: wav` / 重复 if 块），必须 re-read 后再改。
- 用当前 `ohos-wire` 的 canonical shell 在本机构建失败，全是 SDK 环境边界，不是 fork 的 bug：
  - `arkts-no-any-unknown`（Host.ets 947/951）
  - `Cannot find module '@hms.collaboration.systemShare'`（API 26 无此模块）
  - `Expected 5 arguments, but got 4` / `4 vs 3`（Index.ets 新 shell API 与旧页面不匹配）
  - `DEVECO_SDK_HOME` 未设；`abiFilters` 在 `entry/build-profile.json5` 不是根 build-profile；`deviceTypes` 要与模拟器对齐（`["default"]` 而非 `["phone","tablet","2in1"]`），否则 `intersection of system capability sets is empty`
- Go range 规则：Go 1.22+ 用 `for i := range n` / `for range n`，不要 `for i := 0; i < n; i++`。

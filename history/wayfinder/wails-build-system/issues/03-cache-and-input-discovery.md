# Automatic input discovery and cache identity

Type: grilling
Status: resolved
Blocked by: 02

## Question

How does the new runner discover and hash inputs for Go packages, embedded
files, frontend lockfiles and outputs, generated bindings, platform metadata,
toolchains, environment variables, and user-owned scripts? Which operations are
cacheable by default, and which must always run because they may have external
side effects?

## Comments

### 2026-08-16 — Grilling round 1

- Use a persistent file snapshot fast path: reuse a stored content digest when
  path, file identity, size, modification time, and change time are unchanged.
  Dev Session watchers invalidate touched paths, and a manual full-verification
  path handles metadata-preserving tools.
- Store the project action index locally while keeping artifact bytes in a
  machine-global content-addressed store. Keys remain portable, but remote
  caching is deferred.
- Generated outputs are Wake-owned. Missing outputs may be restored; modified
  outputs cause a miss and atomic replacement. Customization enters through
  manifest fields, hooks, or user-owned templates.
- Deterministic Nodes are cacheable. Dependency installation uses a receipt but
  does not archive dependency directories. Signing, notarization, publication,
  credential access, and network side effects always run. Hooks require an
  explicit cache opt-in with complete declared inputs and outputs.
- Native Nodes fingerprint only recognized environment values; hooks must
  explicitly declare inherited variables. Fingerprints use normalized
  manifest-relative paths rather than project locations.
- Each Node handler has an implementation version, so a Wails upgrade only
  invalidates Nodes whose resolved configuration or implementation changed.

### 2026-08-16 — Grilling round 2

- Cache the selected Go package inventory by Target, build tags, workspace and
  module state, and toolchain identity. Track selected source, Cgo, assembly,
  embed, and local-replacement files without scanning the module cache.
- A changed Go source snapshot may rerun binding analysis, but only a changed
  semantic Binding Model or changed generated bytes invalidates the frontend.
- Frontend installation uses a receipt over package/workspace manifests, the
  selected lockfile, package-manager configuration, and package-manager
  identity. It never archives or scans the dependency directory.
- Frontend source discovery excludes dependency, output, VCS, and Wake state
  directories. It includes generated bindings, selected script and mode,
  recognized environment, and frontend tooling. External symlinks make the
  consuming Node machine-specific.
- Generated assets fingerprint only the manifest projection they consume.
  Built-in packaging should normalize ordering and timestamps so its output is
  cacheable.
- Downstream Nodes depend on upstream Artifact content, not the upstream
  sources. Byte-identical regeneration therefore stops invalidation from
  propagating.
- External tool identities are persisted from executable identity and reported
  version, and only the tools consumed by a Node enter its key.
- Use BLAKE3 with canonical typed encoding and domain separation for content,
  action, and Artifact-tree digests.
- The user accepted all recommendations as the standing default and asked to
  review a working MVP rather than continue optimizing the design in advance.

## Answer

Wake uses content-addressed, typed action caching with a persistent filesystem
fast path. Correct automatic input discovery belongs to each Node handler; the
Manifest does not expose source globs for built-in Nodes.

### Cache identities

Three identities are distinct:

1. A **Snapshot** is the BLAKE3 digest of a typed, sorted input tree. It covers
   normalized manifest-relative path, entry type, relevant mode bits, symlink
   identity, and file content. Modification times and absolute project paths
   are not part of the digest.
2. An **Action Key** identifies requested work. Its canonical typed encoding
   contains the Node kind, handler implementation version, resolved typed Spec,
   Target where relevant, recognized environment, consumed tool identities,
   direct Snapshots, and the content digests of consumed upstream Artifacts.
   Profile names and other provenance are excluded when they resolve to the
   same effective work.
3. An **Artifact digest** identifies the published output tree by normalized
   path, type, relevant mode, symlink, and content. Downstream Nodes consume
   this digest, not the producer's transitive source list or Action Key.

Canonical encodings are domain-separated so a file digest, Action Key, and
Artifact-tree digest cannot collide across kinds. Paths use `/` separators and
preserve case. Host-specific absolute paths enter an Action Key only when an
external input cannot be represented portably; that marks the result
machine-specific.

### Fast input snapshots

The project action index stores each file's last content digest with its path,
filesystem identity, size, modification time, and platform change stamp. Wake
reuses the digest when that tuple is unchanged and reads the file only when it
changes. Directory inventory records detect additions, removals, renames, and
entry-type changes. During development, watcher events invalidate the touched
file and parent inventory immediately.

A manual full-verification mode discards the metadata shortcut and rehashes all
selected inputs. The exact CLI spelling belongs to the CLI compatibility
decision. This protects unusual workflows that deliberately preserve every
filesystem timestamp without charging every normal no-op build for full reads.

### Automatic discovery by Node kind

| Node kind | Automatically discovered direct inputs | Cache behavior |
| --- | --- | --- |
| `InstallFrontendDependencies` | Selected package manager and version; package and workspace manifests; selected lockfile; relevant manager configuration; recognized install environment | A successful install writes a Receipt. A matching Receipt plus the expected dependency-store marker skips installation. Dependency directories are neither scanned nor stored as Artifacts. Locked/frozen install mode is preferred when a lockfile exists. |
| `GenerateBindings` | Cached selected Go package inventory; workspace/module files; selected Go source graph; build constraints and options; generator handler version | Source changes may rerun analysis. The resulting Binding Model and generated file-tree digests determine whether downstream frontend work changes. Implementation-only changes that leave generated bytes identical stop here. |
| `GenerateIcons` | Source image or icon project, typed generation options, relevant tool identity | Fully cacheable; independent output groups may be separate Nodes. |
| `BuildFrontend` | Frontend tree excluding dependency, output, VCS, and Wake-state directories; generated bindings Artifact; package script and mode; recognized environment; package-manager and runtime identities; frontend configuration | Fully cacheable. Output is a content-addressed `dist` Artifact. Symlinks within the project use their logical identity and target content; external symlinks make the result machine-specific. |
| `CompileApplication` | Selected Go, Cgo, assembly, and embed files; `go.mod`, `go.sum`, applicable `go.work` state and local replacements; build flags and Target; compiler or `garble` identity; consumed frontend and compile-time platform Artifacts | Fully cacheable. On a miss Wake invokes the Go tool once and still benefits from Go's own build cache. It never scans `GOMODCACHE`; immutable modules are represented by module/workspace resolution and checksums, while local replacements are snapshotted as project inputs. |
| `GeneratePlatformAssets` | Only the typed manifest projection consumed by that asset; Target; source resources; user-owned template content; handler or external tool identity | Fully cacheable. Unrelated manifest changes do not invalidate the Node. |
| `AssembleBundle` | Binary and platform Artifact digests; bundle-specific resolved config and resources | Fully cacheable and published atomically. |
| `PackageArtifact` | Bundle Artifact; package-format projection; consuming templates; package tool identity | Cacheable when the built-in handler controls ordering, ownership metadata, and timestamps. A format that cannot be made reproducible is always run until it has a safe handler contract. |
| `SignArtifact` | Unsigned Artifact and signing policy | Always runs. Signing, notarization, credential access, timestamps, and remote services never produce reusable cache entries. Signed output remains an Artifact for the current Plan only. |
| `RunHook` | Script content and executable metadata; declared inputs, outputs, inherited environment, Target/Profile values, and interpreter identity | Always runs by default. It is cacheable only when the hook explicitly opts in and declares complete inputs and outputs. Secret values are never stored; a cacheable secret-bearing hook is machine-specific. |

Go package inventory discovery is cached per Target, build tags, workspace and
module state, and Go toolchain identity. Its inventory includes directory
membership, so a newly added buildable or embedded file invalidates discovery
without requiring a repository-wide walk. The Dev Session retains this graph
and package state in memory.

Frontend discovery is rooted at the configured frontend directory. It does not
infer inputs from `node_modules` or the previous output tree. Package manager
selection is deterministic when multiple lockfiles exist and becomes part of
the typed Spec rather than ambient command behavior.

### Lookup, execution, and publication

The project keeps a local Action Index while Artifact bytes live in a
machine-global content-addressed store. The Action Index maps Action Keys to
successful result metadata, Artifact manifests, timing history, and Receipts.
The global store permits reuse across projects and worktrees without making
absolute paths part of portable keys. Remote storage is not part of the first
version, but the key format does not prevent it later.

Cache evaluation validates direct input identities recursively through the
Plan before work enters the ready queue. A valid Action result with matching
published outputs is a hit. Missing outputs are materialized from the Artifact
store, using reflinks or hardlinks when safe and copying otherwise. A present
output whose content differs from the recorded digest is treated as a dirty
miss and rebuilt, preserving the rule that generated paths are Wake-owned but
never silently trusted after manual edits.

Nodes execute in engine-owned scratch space and publish outputs atomically.
Only successful publication writes an Action result or Receipt. Failed and
cancelled work cannot become cache-valid. Concurrent Wails processes use an
Action-Key lock, recheck after acquiring it, and atomically install Artifact
content, so identical work is single-flight where the host permits it.

The normal cache can be bypassed for diagnosis while underlying compiler and
package-manager caches remain independently useful. Cache eviction may remove
global Artifact content at any time; this turns a future lookup into a miss and
cannot affect correctness.

### MVP boundary

The first vertical slice should prove the filesystem Snapshot fast path,
Action Index, local Artifact store, and Artifact-digest propagation through
`GenerateBindings`, `BuildFrontend`, and `CompileApplication` for one host
desktop Target. Packaging, signing, remote caching, every package manager, and
perfect cross-platform materialization are not prerequisites for reviewing
whether the new model is fast and understandable.

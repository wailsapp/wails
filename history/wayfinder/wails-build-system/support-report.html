Start here

Build your first profile

Create wails.hcl in the project root

Its presence is the opt-in switch. From this point, Wails ignores every Taskfile in the project; invalid HCL fails instead of falling back.

version = 3

project {
  name         = "notes"
  product_name = "Notes"
  identifier   = "com.example.notes"
  version      = "1.0.0"
}

frontend {
  directory = "frontend"
  install   = ["pnpm", "install", "--frozen-lockfile"]
  build     = ["pnpm", "run", "build"]
  dev       = ["pnpm", "run", "dev"]
  output    = "frontend/dist"
}

build {
  output    = "bin"
  trim_path = true
  strip     = true
}

profile "release" {
  target "linux/amd64" {
    formats = ["deb", "rpm", "appimage"]
  }
}

Validate before building

wails3 config check
wails3 config check release

The first command checks the base manifest and every profile. The second checks only the complete release request after validating the base.

Inspect the resolved work

wails3 build release --plan
wails3 build release --plan --json

--plan is concise text for a person. Add --json for deterministic, versioned machine-readable output. Planning does not write build state.

Build the profile

wails3 build release

Final artifacts are published beneath build.output. Wails writes a verified artifact receipt to .wails/artifacts/receipt.json.

How to work day to day

Use the everyday workflow

Develop locally

wails3 dev
wails3 dev --plan

Dev builds only the current host target. It starts and readiness-checks the frontend and application, watches configured files, cancels stale rebuilds and preserves the last healthy session if a replacement fails.

Run a one-off build

wails3 build --targets linux/amd64
wails3 build --targets linux/amd64 --formats deb,rpm

Use comma-separated targets and formats when the request is genuinely temporary. Anonymous builds also accept --tags, --obfuscated, --garble-args and --force.

Prefer profiles for repeatable outcomes. A named profile is a complete production request. It cannot be combined with artifact-changing CLI overrides, so local and CI builds mean the same thing.

How to make repeatable releases

Create production profiles

Add a named profile for each outcome your team needs, then invoke the profile rather than maintaining separate build commands.

profile "linux-release" {
  target "linux/amd64" {
    formats = ["deb", "rpm", "appimage"]
  }
}

profile "android-release" {
  target "android/universal" {
    formats = ["aab"]
  }
}
wails3 config check
wails3 build linux-release
wails3 build android-release

Profiles can also select signing, notarisation and a mobile destination. Production Android output is AAB-only. APK is generated internally only for development deployment.

How to keep customisation in your repository

Use project-owned assets

Point HCL fields at files you own. Wails copies them into a disposable .wails/ workspace before invoking platform tools and never edits the sources.

Supported project inputs

  • Icons and platform manifests
  • Apple Info.plist and Assets.car
  • Linux desktop entries and package lifecycle scripts
  • Package templates and AppImage assets
  • File-association icons and DMG artwork/files
  • Signing certificates, profiles and environment references

Discover available fields

wails3 eject

This writes the complete resolved configuration to wails.ejected.hcl. Treat it as a reference or starting point; copy only the settings your project needs into wails.hcl.

Complete package templates are opaque files or directories. Wails does not interpolate, merge or normalise them.

Explanation and stage reference

Understand the internal build stages

Wails owns a typed build graph. Configuration selects outcomes; it does not redefine these stages or their dependencies. The executor starts independent nodes as soon as their inputs are ready, so the diagram below is a lifecycle view rather than a promise that every operation runs serially.

  1. Resolve configuration and planValidate the manifest, profile, host capabilities and requested targets; construct the immutable graph. No hook runs during planning.
  2. before_build hook projectRuns once before project preparation or target work begins.
  3. Prepare project inputsInstall frontend dependencies and generate bindings in parallel. Platform assets may also start here when compilation needs them.
  4. Build frontendProduce the embeddable frontend after dependency installation and binding generation complete.
  5. Compile native targetCompile one target or its architecture components. Merge macOS component binaries when producing a universal target.
  6. after_build hook targetThe native binary or libraries now exist. App-bundle assembly and package formats may still be pending.
  7. Generate remaining assets and assemble applicationCreate platform-owned assets and, for app-style targets, assemble the runnable application bundle. Binary-style targets skip assembly.
  8. before_package hook targetAll package inputs are ready. The context names the planned package path or common parent, but the packages do not exist yet.
  9. Package requested formatsBuild independent formats concurrently, such as DEB, RPM and AppImage for one Linux target.
  10. after_package hook targetEvery requested package for the target now exists.
  11. before_sign hook targetUnsigned packages—or the base binary/app for a sign-only request—are ready.
  12. Sign and notariseSign requested artifacts. Independent package signatures can run concurrently; signing is deliberately never cached.
  13. after_sign hook targetAll signed outputs for the target now exist.
  14. Publish and collect artifactsAtomically publish final outputs, verify them and write .wails/artifacts/receipt.json.

Read hook names as lifecycle boundaries. In this contract, “build” ends when native compilation and any universal-binary merge finish; it does not mean the final app bundle or installer already exists. Likewise, after_package is before signing and after_sign is before final publication and receipt collection. There is no hook around publication or collection.

Conditional stages disappear from the graph. A build with no package formats does not run package hooks. A request with no signing does not run sign hooks. App assembly runs only for app-style targets. Use wails3 build [profile] --plan to see the exact graph for one request.

Package and sign hooks are target-scoped barriers, not per-format callbacks. If a profile requests DEB and RPM, before_package runs once, both package nodes may run in parallel, and after_package runs once after both finish.

A configured hook runs whenever its matching phase is executed; planning never runs hooks. By default it is not cached and makes only its downstream work non-cacheable. For example, an uncached after_build hook does not prevent compilation from hitting the cache, while an uncached before_build hook makes the complete downstream build run. A cacheable hook must declare all inputs and outputs.

How to handle the small amount that remains custom

Add a lifecycle hook

A hook names one project-owned script at one of the documented internal stage boundaries, not an inline shell command. On Unix it must be executable and start with a shebang. Windows accepts .cmd, .bat and .ps1.

hook "before_build" {
  script = "scripts/generate-version.sh"
}

hook "after_package" {
  script = "scripts/check-packages.sh"
}

Read the invocation context

Wails passes exactly one Wails-owned context variable: WAILS_HOOK_CONTEXT_FILE. Read that JSON file with the parser appropriate for your script.

#!/bin/sh
set -eu

context="$WAILS_HOOK_CONTEXT_FILE"
phase="$(jq -r '.phase' "$context")"
output="$(jq -r '.output' "$context")"

printf 'checking %s output: %s\n' "$phase" "$output"
{
  "version": 1,
  "phase": "after_build",
  "command": "build",
  "scope": "target",
  "project_dir": "/work/notes",
  "working_directory": "/work/notes",
  "profile": "release",
  "target": { "os": "linux", "arch": "amd64" },
  "output": "/work/notes/bin/notes",
  "declared_outputs": []
}

The file is atomically generated under .wails/hooks/context/, protected for the current user, and contains no inherited environment or secrets. Wails removes it after success or cancellation. A real failure retains it and reports its path.

Cache a deterministic hook

hook "before_build" {
  script  = "scripts/generate-version.sh"
  cache   = true
  inputs  = ["version.txt"]
  outputs = ["generated/version.go"]
}

Hooks run every time by default. Enable caching only when every input and output is declared. The generated context path never affects cache identity; its semantic version and resolved scope do.

Intentionally bounded. Supported phases are before_build, after_build, before_package, after_package, before_sign and after_sign. This is not a custom pipeline language.

How to deploy during development

Run on an Android device or emulator

Discover available targets

wails3 android devices

Wails lists connected ADB devices and emulators with their serial, state and model.

Select a target

wails3 android run --device SERIAL
wails3 android run --emulator AVD_NAME

Without a selector, an interactive terminal offers connected devices and configured AVDs. Automation with multiple targets must provide one explicitly.

Attach logs when diagnosing the app

wails3 android run --emulator AVD_NAME --logs
wails3 android run --emulator AVD_NAME --logs --stop-emulator

--logs follows PID-filtered application logs and target loss. Emulators remain running by default; --stop-emulator stops an attached emulator when the session ends.

Wails selects the target ABI, builds an internal debug APK, installs it and launches com.wails.app.MainActivity. Use --no-launch to stop after installation, or --apk PATH to install an existing APK.

How to try this in an existing project

Migrate a Taskfile project safely

Analyse without changing files

wails3 migrate --dry-run
wails3 migrate --json

Review the inactive draft

wails3 migrate

Representable behaviour is written to wails.migrated.hcl. Custom shell logic is reported instead of being guessed. Existing Taskfiles, scripts, YAML and assets remain untouched.

Activate only after validation

wails3 migrate --activate
wails3 config check
wails3 build --plan

Activation atomically renames the draft to wails.hcl. That immediately disables Taskfile execution, so commit or stash the project first.

How to recover quickly

Resolve common problems

ProblemWhat to do
The build fails before executing workRun wails3 config check [profile]. Diagnostics identify the HCL file, line, column and field, then show a caret and correction hint where possible.
Taskfile changes have no effectCheck for wails.hcl. Its presence means Taskfiles are intentionally ignored; there is no fallback.
You want to see what Wails will doRun wails3 build [profile] --plan. Add --json for tooling.
A hook failedRead the captured output and exit code, then inspect the retained context path printed in the error.
Generated state appears staleRun wails3 clean. It removes .wails/ only and preserves final artifacts and project-owned files.
A cached output was deletedBuild normally; the content-addressed cache restores valid missing outputs. Use --force only when you deliberately need all work rerun.

Verification snapshot

Confirmed on this Linux host

  • Real Linux binaries and packages
  • All nine built-in web templates
  • Development process lifecycle
  • Cache hits, restoration and stable receipts
  • Android AABs and x86_64 AVD deployment
  • Focused race, vet and cross-compile gates

Still needs matching-host acceptance

  • Native Windows and macOS packaging
  • iOS simulator/device builds
  • Physical Android deployment
  • Credentialed platform signing

The default Linux template builds in about 3.5 seconds with warm machine caches. Its unchanged rebuild median is 99.870 ms, below the accepted 150 ms gate.

Outside the current contract

Custom stages and dependency graphs, inline hook commands, HCL expressions or includes, typed wails3 tool calls, remote caching, arbitrary Taskfile translation, iOS deployment control, production APK output and config show are not supported.

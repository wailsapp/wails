Wails v3 HCL Build System

Exactly what the current branch supports, what has been verified, and what remains before multi-platform release acceptance.

Executive summary. This is a complete Linux-tested experimental vertical slice, not merely a proposal. Multi-platform support is implemented in code and structurally tested, but it is not release-ready until the matching-host matrix is completed.

Core behaviour

  • A root wails.hcl opts the project into the native build system.
  • Once present, Taskfiles are completely ignored.
  • Invalid HCL fails explicitly and never falls back to Taskfiles.
  • Projects without wails.hcl continue using the legacy Taskfile path.
  • Wails owns a fixed pipeline; users describe desired outputs instead of tasks or stages.
  • The schema accepts literal strings, numbers, booleans, lists and maps.
  • Unknown fields, duplicate fields or blocks, incorrect types and unsupported combinations are rejected with source locations.

Anonymous builds also support --tags, --obfuscated, --garble-args and --force. A named profile is a complete production request and cannot be mixed with artifact-changing CLI overrides.

wails3 config check performs validation without building. wails3 android run supports --profile, --device, --emulator, --apk, --no-launch, --logs and --stop-emulator.

wails3 package and wails3 sign remain as deprecated compatibility aliases for HCL projects.

Configuration diagnostics

  • wails3 config check validates the base manifest and every named profile without executing build operations.
  • wails3 config check release validates only the requested profile after validating the base manifest.
  • HCL syntax, schema, semantic, path, target and format failures identify the file, line and column, display the source line and caret range, and provide an actionable hint where possible.
  • The same source ownership continues through planner, signing and configuration-owned host-capability validation during Build and Dev.
  • Environment values are redacted from diagnostic source excerpts; golden output, multiple errors and terminal-neutral text are covered by tests.
  • Command-line-only failures remain ordinary command errors instead of being misreported as invalid HCL.

Source-aware validation is complete for the configuration path. A real CLI acceptance pointed an invalid Linux/AAB profile to formats = ["aab"], and a Linux/arm64 native cross-build host failure to the exact toolchain = "native" line. The no-source renderer benchmark is approximately 1.3 µs per diagnostic on the Linux audit host.

Android device and emulator deployment

  • wails3 android devices lists connected ADB devices and emulators with serial, state and model.
  • wails3 android run [profile] selects a connected device or configured AVD, using a terminal picker when selection is interactive.
  • --device and --emulator provide deterministic automation and report offline, unauthorised or missing targets clearly.
  • The selected target ABI drives an arm64 or amd64 development build.
  • Wails builds a debug APK, installs or reinstalls it through ADB, and launches com.wails.app.MainActivity; --no-launch stops after installation.
  • Emulator startup waits for ADB, Android boot completion and Package Manager readiness, with bounded cancellation and logs under .wails/android/.
  • --logs streams PID-filtered application logs, follows app restarts, exits on app shutdown or Ctrl+C, and reports device loss.
  • Emulators persist by default. --stop-emulator explicitly stops an emulator after an attached run; cancelled or failed startup cleans up only the newly started process.
  • Production Android profiles remain AAB-only. APK is an internal installable development artifact, not a Google Play publishing output.

Real Android acceptance passed. The Linux host has API 36, Build Tools 36.0.0, NDK r29 and an API 36 x86_64 AVD. Generated projects use the supported AGP 9.0.1/Gradle 9.2.1 pairing. Production amd64, arm64 and universal AABs passed with receipts and zero-work reruns. wails3 android run built a native x86_64 debug APK, installed it, launched the configured activity, and displayed the live Wails badge application without a fatal logcat error.

Cross-compilation

Configured toolchain values are auto, native, zig and docker.

  • Windows and Linux: native, Zig or Docker.
  • macOS: native or the prepared Docker cross-compilation environment.
  • iOS: native Xcode toolchain on macOS.
  • Android: Android NDK on Linux, macOS or Windows.
  • Docker-based cross-compilation from a Windows host is not currently supported.
  • Packaging has additional host restrictions: MSIX requires Windows, while DMG and IPA require macOS.

Configuration covered by wails.hcl

  • Project identity, version, build number, binary name, company, description, copyright, comments and icon.
  • Frontend directory, install/build/dev argument vectors, package manager, output and environment.
  • TypeScript bindings, interface/class output, generated filenames and Go time representation.
  • Build output, tags, linker/compiler flags, environment, trim path, stripping, VCS metadata and garble obfuscation.
  • Development tags, watch/exclude patterns, Git-ignore handling, debounce, log level and shutdown grace period.
  • Platform metadata and user-owned assets for Windows, macOS, Linux, iOS and Android.
  • Per-target flags, environment, minimum OS version, build number, obfuscation and toolchain.
  • Named profiles selecting targets, formats, signing, notarisation and mobile destination.
  • File associations and custom protocols.
  • Structured package settings and complete package-template replacements.
  • Platform signing references without storing secret values in HCL.

User-owned assets

Supported project-owned inputs include icons, platform manifests, Apple Info.plist and Assets.car, Linux desktop entries, signing inputs, package templates, AppImage assets, Linux package lifecycle scripts, file-association icons, and DMG files and artwork.

Wails copies these inputs into disposable .wails/ workspaces. Source files are not modified. Complete templates are opaque files or directories: no interpolation, merging or line-ending conversion is performed.

Pipeline and caching

  1. Install frontend dependencies.
  2. Generate bindings.
  3. Build the frontend.
  4. Compile the native application.
  5. Merge universal binaries where required.
  6. Generate platform assets.
  7. Assemble applications.
  8. Package, sign and notarise as requested.
  9. Publish artifacts and generate a verified receipt.

The executor supports shared work across targets, bounded parallelism, content-addressed local caching, automatic input tracking, restoration of missing outputs, dirty-output detection, transactional publication and non-cacheable signing. Final artifact metadata is written to .wails/artifacts/receipt.json.

--plan produces a human-readable inspection without writing state. --plan --json emits the same resolved graph as deterministic, versioned JSON.

Development mode

  • Uses the same planner and cache with separate development policy.
  • Runs only for the current host target.
  • Starts and readiness-checks the frontend server and native application.
  • Watches configured files with debounce and optional .gitignore filtering.
  • Cancels stale rebuild generations and restarts only affected processes.
  • Reloads wails.hcl transactionally and preserves the last healthy session after a failed replacement.
  • Stores development binaries beneath .wails/dev/.
  • Keeps stripping, obfuscation and other production policy out of development.

New projects, wizard and migration

  • All built-in templates generate wails.hcl.
  • The init wizard writes metadata and TypeScript/interface choices through a typed internal state and HCL writer.
  • Existing manifest updates preserve unrelated configuration, comments, ordering and file permissions.
  • The signing wizard updates one platform signing block without replacing the remainder of the manifest.
  • Community templates with Taskfiles are analysed. Representable templates can become active HCL projects; custom behaviour produces an inactive draft and preserves legacy execution.

Migration inspects root and included Taskfiles, reachable build/package/sign/dev tasks, build/config.yml, frontend metadata and lockfiles, binding settings, conventional assets, project metadata, file associations and protocols.

Only behaviour with a typed equivalent is migrated. Conservative argument-free lifecycle tasks that invoke one project-owned script become HCL hooks; other reachable custom shell logic remains a blocker. Activation atomically renames wails.migrated.hcl to wails.hcl; Taskfiles, scripts, YAML and assets are not deleted or edited.

Experimental lifecycle hooks implemented

  • One project-owned executable script may be declared for each of before_build, after_build, before_package, after_package, before_sign and after_sign.
  • Package and signing hooks form per-target barriers around the complete requested format set; independent package nodes remain concurrent.
  • Scripts run directly without inline shell interpolation, inherit a stable overriding WAILS_* environment, retain failure output and exit status, and are terminated as a process group on cancellation.
  • Hooks run every time by default and make downstream operations non-cacheable. Explicit cache = true requires complete inputs and bounded outputs, preserves downstream reuse through its artifact identity, and supports content-addressed hit and restoration.
  • Script, directory, input and output paths are constrained to the project after symlink resolution; cached output trees accept only regular files and directories. Windows uses explicit .cmd, .bat or .ps1 interpreter adapters.

This hook surface is an experiment for evaluation, not accepted first-release scope. It is deliberately not a general task or user-defined pipeline language.

Explicitly not supported

  • Arbitrary pre/post-build command strings or multiple commands per hook.
  • Custom stages, dependencies or user-defined pipelines.
  • Calling wails3 tool operations from HCL.
  • HCL expressions, variables, functions, interpolation, includes, conditions, loops or HCL-JSON.
  • Remote caching.
  • Automatic translation of arbitrary Taskfile shell logic.
  • iOS device deployment, simulator control or IDE launching (Android device/emulator deployment is now implemented).
  • Production APK output.
  • A config show command or generic config export.
  • Cleaning final artifacts: wails3 clean removes .wails/ only.

Behaviour outside the six bounded hook phases can still run separately before or after Wails, but it is not represented in the build graph.

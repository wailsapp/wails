## 全体構造

Go→JS と JS→Go では異なる仕組みを使用しており、この非対称性こそが設計の核心です。

```
Go                                  webview
──                                  ───────
Send() ─► per-window queue ─────────► GET  /wails/stream/poll   (held open)
                                      └─ one held request per window,
                                         carrying frames for every connection

Receive() ◄─ per-conn inbox ◄──────── POST /wails/stream/send   (one or more frames)
```

**Go→JS は保留型ポーリングです。** 配信するものが現れるまでリクエストを待機させます。意図的にポーリング間隔も適応的な処理も設けていません。フレームが存在するまでサーバーがリクエストを保持するため、配信レイテンシはすでに約 0 であり、クライアント側の間隔はレイテンシを増やすことしかできないためです。応答の処理中に到着したフレームは蓄積され、次の応答に同梱されます。そのため、ラウンドトリップ自体がバッチ処理の時間枠となり、計測する仕組みがなくても負荷の上昇に応じて広がります。実測では、100/秒で応答あたり 1.0 フレーム、5000/秒でも 1.0、20000/秒では 3.4 となり、レートが上がるにつれて p99 レイテンシは<em>低下します</em>。

**JS→Go は通常の POST を使用します。** 同時に実行した `fetch` 呼び出しでは順序が維持されず、Go は送信順序どおりに受信できることを前提としているため、送信は Promise チェーンによって接続ごとに直列化されます。処理中のリクエストの後ろに蓄積されたフレームは、次の POST にまとめられます。Go は応答する<em>前に</em>、受け入れたフレームまたはバッチのプレフィックスを接続の受信トレイに追加します。そのため、Go がまだキューに入れていないバイトより先へクライアントが進むことはありません。

**ウィンドウごとに処理中のポーリングは 1 つで、すべての接続を多重化します。** これにより、単一のキューと単一のドレイナーだけが存在し、最初の配信経路を追い越し得る第 2 の経路がないため、構造上、順序が正しく保たれます。また、Windows ではこれらが `http://wails.localhost` に対する実際の Chromium ネットワークリクエストとなるため、HTTP/1.1 のホストあたり 6 接続という制限も回避できます。

## これらの設計判断を採用した理由

これらはすべて、イベントトランスポートの開発で生じた傷跡です。いずれかを取り除くと、実測で確認されたバグが再発します。

**Go→JS 経路では、メインスレッドに一切触れません。** `Send` は mutex のロック中に追加して戻ります。以前のイベント処理では、先行する goroutine からの emit がまだキューにある間にメインスレッドからイベントを emit すると、その eval がインラインで実行され、3 つすべてのプラットフォームでイベントの 4.4% の順序が逆転していました。単一のキューと単一のドレイナーでは、この問題は起こりません。

**サイズにかかわらず、`evaluateJavaScript` には一切触れません。** eval のソースにペイロードを組み込むと、プラットフォーム固有のしきい値を超えたところでホストメモリが解放されずに残るようになります。100 × 1 MB/秒の場合、保持されるメモリ量は macOS では 11.6 GB、WebKitGTK では 6.2 GB です。ストリームはこの経路に一切近づかないため、一定バイトレートのスイープは、どのフレームサイズでも平坦になります。

**制御データは常にヘッダーで送られ、ボディやクエリ文字列では送られません。** WebKitGTK の 6.0 は、カスタム URI スキームで POST ボディをクエリパラメーターとして渡すことがあります（まさにその場合に備えて、`transport_http.go` にはフォールバックがあります）。また、WebView2 ではボディの配信が約 2 MB に制限されます。

**ポーリング応答は JSON ではなくバイナリです。** フレームは `[]byte` です。JSON エンベロープ内で base64 を使用すると、すべてのフレームで 33% のオーバーヘッドが生じ、さらに UI スレッドでの解析も必要になります。

```
magic "WS1\0" | flags u8 | count u32 | count × ( connID u32 | kind u8 | len u32 | payload )
```

`kind` は data / open / close / error です。シーケンス番号も ack もありません。WebSocket は再送を行わず、接続が切断されると処理中だったデータは失われます。容量に上限のあるバッファでは常に満たせるとは限らないカーソルを設けるよりも、その動作を再現する方が単純で誠実です。

**リクエストを保持しても安全です**。すべての webview リクエストには、すでにそれぞれ専用の goroutine が割り当てられているためです。`assetserver_webview.go` の `dispatchWorkers` は、まさにこのケースを明記したコメントとともに 0 に固定されています。そのプールを有効にするには、まずリクエストの有効期間に上限を設ける必要があります。

## バッファ定数

すべて `stream.go` にあります。**これらはオプションではなく、コンパイル時定数です**。`Options.Streams` もストリームごとの設定もありません。変更するにはファイルを編集する必要があります。

| 定数 | 値 | 制限対象 |
| --- | ---: | --- |
| `streamOutQueueBytes` | 8 MB | 収集を待つウィンドウごとのバッファ済みバイト数 |
| `streamOutQueueDepth` | 256 | ウィンドウごとのバッファ済みフレーム数 |
| `streamOutQueueBytesGlobal` / `streamOutQueueDepthGlobal` | 256 MB / 8192 | アプリケーション全体でバッファされる送信データ |
| `streamInQueueBytesGlobal` / `streamInQueueDepthGlobal` | 256 MB / 8192 | アプリケーション全体で `Receive` を待つ受信データ |
| `streamMaxConnections` | 256 | 1 つのセッション内の有効な接続とキューに入った close の合計 |
| `streamMaxConnectionsGlobal` | 4096 | アプリケーション全体の有効な接続 |
| `streamOutCloseDepthGlobal` | 4096 | アプリケーション全体の未配信の close 通知 |
| `streamMaxSessionsPerWindow` | 16 | 新しい世代が古い世代を置き換える必要が生じるまでに、1 つのウィンドウが保持できるセッション数 |
| `streamMaxSessions` | 1024 | アプリケーション全体のセッション数 |
| `streamOutControlDepth` / `streamOutControlDepthGlobal` | 256 / 4096 | セッション単位およびアプリケーション全体でキューに格納される、close 以外の制御フレーム |
| `streamMaxChunkSets` / `streamMaxChunkTotal` | 256 / 4096 | セッションごとの未完了アップロード数、および1回のアップロード内のパート数 |
| `streamMaxChunkBytesGlobal` / `streamMaxChunkPartsGlobal` | 128 MB / 4096 | アプリケーション全体のチャンクペイロードおよびパートのメタデータ |
| `streamMaxChunkIDLen` | 64バイト | クライアントから提供される1つのチャンクセット識別子 |
| `streamMaxResponseBytes` | 1 MB | 1回のポーリング応答 |
| `streamHoldTimeout` | 20秒 | 空のポーリングを待機状態にしておく時間 |
| `streamSessionTTL` | 60秒 | この時間にわたってポーリングがなく、ライブ接続もない ⇒ セッションは終了済み |
| `streamSessionGrace` | 10分 | ライブ接続がある状態で、この時間にわたってポーリングがない ⇒ セッションは終了済み |
| `streamSessionSweep` | 20秒 | janitor が終了済みセッションを検索する間隔 |
| `streamMaxFrameBytes` | 64 MB | いずれかの方向の1フレーム |
| `streamMaxNameLen` | 256バイト | 登録または要求される1つのストリーム名 |
| `streamInQueueDepth` / `streamInQueueBytes` | 256 / 8 MB | 受信済みで、まだ`Receive`によって取り出されていないフレーム |

### 値の決め方

**`streamOutQueueDepth`は意図的に`eventQueueCapacity`（64）とは異なる値にしています。** この定数は、eval 1回につき1つずつ消費されるキューについて測定されたもので、その場合、深さを増してもテールレイテンシーが増えるだけでした。ポーリングはバッチ単位で消費するため、ここでの深さは生成処理の1往復分を収容できなければなりません。5000フレーム/秒、往復時間5ミリ秒なら、約25フレームです。256なら、プロデューサーを停止させずにバーストを収容する余裕があります。

実際に重要なのは<strong>`streamOutQueueBytes`の上限です</strong>。1 MBのフレームが256個あれば、合計256 MBになるためです。フロントエンドが収集を停止した場合に、ホストメモリを保護する最後の歯止めとなります。

ここでは2つの規則が相互に作用します。特に2つ目は、意図せず破ってしまいがちです。

- 深さとバイト数の上限によって、<em>蓄積量</em>を制限します。
- **空のキューは、サイズにかかわらず常に1フレームを受け入れます。** バイト数の上限を無条件に適用すると、上限より大きいフレームはまったく送信できなくなりました。待機条件が成立することはないため、`Send`は永久にブロックされ、`TrySend`は永続的に満杯と報告しました。フレームサイズを呼び出し元が常に選べるとは限りません。`[]byte`フィールドを持つ構造体をマーシャリングすると、その結果のサイズにしかなりません。

**`streamMaxResponseBytes`が存在するのは Windows のためです。** WebView2 のレスポンスライターは本文全体をメモリに蓄積し、`Finish`でのみ引き渡すため、応答を無制限にすると、そこでのメモリ割り当ても無制限になります。この値を引き上げても、Windows のスループットは向上し<em>ません</em>。測定では、Windows のボトルネックは応答単位ではなくバイト単位でした。フレームサイズを変えた一連の測定では、応答数/秒が4倍変動する一方、MB/秒は約90で横ばいでした。

**フロントエンドを待機させるのは、受信側の上限です。** デスクトップでは、`deliver`が満杯であることを報告し、エンドポイントが`429`で応答すると、クライアントは同じフレーム、または受け入れられなかったバッチの残りを、上限付きバックオフで再試行します。これにより、ハンドラーが処理に追いつくまで webview のリクエストスロットを占有せずに済みます。サーバーモードでは、ソケットの読み取りポンプが待機し、TCP にバックプレッシャーを適用させます。この上限がなければ、`Receive`の呼び出しが遅いハンドラーによって、ホストメモリが無制限に増加する可能性があります。

**制御フレームはデータの上限を迂回しますが、独立したライフサイクル上の制限があります。** バックプレッシャーによってデータフレームが失われれば処理が遅くなるだけですが、open ack が失われるとフロントエンドは永久に`CONNECTING`のままになり、close が失われると終了済みの接続をライブ接続だと認識し続けます。そのため、close 以外の制御フレームには、close が使用するキューとは別に、独自の有界キューがあります。これにより、拒否された open が一度に集中しても、受け入れ済み接続が終了を報告するために必要な容量を使い尽くすことはありません。また、各セッションは、受け入れ済み接続ごとに1つの close スロットを予約します。その容量が使用中の場合、新しい open は登録前に再試行可能なバックプレッシャーを受けます。

**セッション単位の上限には、アプリケーション全体に対応する上限もあります。** これらがなければ、許可されたすべてのセッションまたは接続が、それぞれのローカル許容量を同時に最大まで保持できてしまいます。そのため、送信データと受信データは、デスクトップおよびサーバートランスポート全体で、それぞれ別個の256 MiB / 8192フレームの予算を共有します。ライブ接続には4096エントリの予算があり、未配信の close 通知には同じサイズの別の予算があります。共有上限に達した場合も、ローカル上限に達した場合と同じ、ブロッキングの`Send`または非ブロッキングの`TrySend`の動作が適用されます。また、消費、受信、close、書き込み失敗、シャットダウンのすべての経路で、予約が返却されます。

この2つの予算は、接続が自身の close フレームに引き渡す1つの許容量にはせず、意図的に分離しています。各予約は、必ず1つの所有者によって解放されます。接続のスロットは、一度だけ実行される`shutdown`によって解放され、close フレームのスロットは、そのフレームを破棄する処理、つまり消費処理またはセッションの破棄によって解放されます。2者間を移動する所有権はアトミックに移転する必要があります。以前のリビジョンでは、close に接続のスロットを継承させていたため、close を試行してからその試行が失敗するまでの間に破棄処理が実行されると、スロットが1つ永久にリークしていました。

**Go のフレームは所有権を移転し、JavaScript のフレームはスナップショットを作成します。** Go の`Send`は、トランスポートが書き込むまで呼び出し元のスライスを保持するため、呼び出しが成功した後、呼び出し元はそのストレージを変更または再利用してはなりません。JavaScript の`send()`は、可変のバイナリ入力を返る前にコピーし、ネイティブ WebSocket の所有権セマンティクスに合わせます。この非対称な規則により、ブラウザー向け API を直感どおりに保ちながら、Go 内部でフレーム全体をもう一度コピーせずに済みます。

**JavaScript の送信処理は、WebSocket のバッファリング契約に従います。** `send()`はブロックできないため、ネイティブ WebSocket の処理速度を上回れるのと同様に、アプリケーションはデスクトップのリクエストチャネルが受け入れるよりも速くデータをキューに追加できます。`bufferedAmount`には、そのソケットが保持するすべてのバイトが含まれ、呼び出し元へのバックプレッシャーシグナルとなります。ホスト側のキューには、これとは独立して上記の上限が適用されます。回復不能な障害、ピアからの close、またはローカルの`close()`が発生すると、保持されているペイロードが解放されます。ローカルで close した場合は、予約済みの close 制御フレームを送信する前に、`429`で待機中の open またはデータリクエストもキャンセルします。そのため、受け入れ処理または受信側のバックプレッシャーによって、ソケットが`CLOSING`のまま停止することはありません。

**チャンクの再構成には、ホストメモリ全体で共有される上限があります。** 各セッションは最大 64 MiB のフレームを一度に1つ再構成できますが、この上限を受け入れ済みの全セッション数に応じて増やしてはなりません。そのため、未完了および再試行可能なチャンクセットは、受け入れ済みペイロード用の 128 MiB の予算を共有します。セットの完成時には、その各パートと連続領域に再構成されたフレームの両方が短時間保持されるため、この論理上限を2倍にしても、実効メモリ上限である 256 MiB の範囲内に収まります。保持されるパートは、4096 エントリ分のメタデータ上限も共有するため、微小または空のチャンクによって、バイト上限に近づくことなくマップやスライスの管理情報が増大することはありません。いずれかの上限を超える要求には、再試行可能なバックプレッシャーが返されます。配信、拒否、期限切れ、またはセッションのシャットダウンが発生すると、バイト数とパートのエントリ数の両方が共有予算に戻されます。

**ポーリングで再試行するのは、回復可能な障害だけです。** ネットワークエラー、リクエストタイムアウト応答（`408`）、早期データ応答（`425`）、バックプレッシャー（`429`）、およびサーバーエラー（`5xx`）では、250 ms から最大 5 秒までの指数バックオフを使用します。その他の `4xx` 応答はプロトコルまたは所有権の障害であり、ページの Streams を直ちに閉じます。`410` は、廃止されたセッションを示す正常な終了シグナルです。最後の接続を閉じると、進行中のポーリングまたはバックオフタイマーが中止されます。その終了処理中に接続が開かれた場合は、代替のポーリングループが1つ開始されます。

**`streamSessionTTL` は `streamHoldTimeout`** より十分に大きく保つ必要があります。そうしないと、セッション自身のポーリングが正当に待機している間に、そのセッションが回収されてしまいます。

小さなメッセージを大量に扱うワークロード向けに調整する場合は、深さの上限に先に達します。大きなペイロードの場合は、バイト数の上限に先に達します。一般的なアプリでは、どちらも変更する必要はありません。macOS では、デフォルト設定で 634000 フレーム/秒および 2100 MB/秒を維持できます。

## 接続とセッションのライフサイクル

<strong>セッション</strong>とは、1つのウィンドウにおける1回のページ読み込みであり、クライアントが生成した ID（ランタイムの `clientId` など）をキーとします。セッションは、最初に到着した要求によって遅延作成されます。プラットフォームが要求元のウィンドウを識別できない場合（`windowID == 0`）も、セッション ID の数には引き続きグローバルな上限が適用されますが、世代は意図的に比較されません。これは、互いに無関係な世代カウンターを持つ独立したブラウザクライアントに属する可能性があるためです。これらのセッションは互いを置き換えるのではなく、クローズまたは TTL によって期限切れになります。

次の3つの仕組みが、検知の速い順に対象を閉じます。

1. **あるウィンドウに対する新しいセッションのポーリングは、古い世代を置き換えます。** 再読み込みすると、ページには新しいセッション ID が割り当てられ、そのウィンドウの `sessionStorage` に保存されている世代がインクリメントされます。同じ値は `window.name` にも複製されます。これはストレージが無効でも再読み込み後に保持され、さらに `performance.timeOrigin`（古いエンジンでは `Date.now()`）を基準とするため、両方のストアを消去しても1から再開しません。すべての要求にセッション ID と世代が含まれます。ポーリングで廃止されるのは、それより古いページ世代だけです。このため、サーバーのスケジューリングによって、以前のページから遅れて届いた要求が、その後継ページより新しく見えることはありません。ポリシーによってストレージと `window.name` の両方がブロックされている場合、順序付けはページクロックにフォールバックするため、後のページにより後の時間原点が与えられることに依存します。マネージャーはウィンドウごとに廃止済み世代のウォーターマークを保持するため、過去のすべてのセッション ID を保持しなくても、すでに処理中の要求によって古いページが再作成されることを防げます。以前のセッションの接続は直ちに閉じられます。
2. <strong>ウィンドウの破棄</strong>では、`eventPayloadStore.dropWindow`と同様に、そのウィンドウの全セッションが破棄されます。
3. <strong>TTL による回収</strong>では、それ以外のもの（クラッシュしたレンダラーやスリープ中のマシンなど）を処理します。

ページ世代を廃止するのは、最初の2つの仕組みだけです。TTL クリーンアップは、廃止済み世代のウォーターマークを進めずに、アイドル状態のセッションを削除します。ページは最後の接続が閉じられるとポーリングを停止しますが、読み込まれたままの同じページが、後で別のストリームを開けなければならないためです。実際に置き換えられた世代は引き続きブロックされます。古いセッションが削除される前に、新しいページのポーリングによってウォーターマークが進められるためです。

**Apple WebView は、キャンセルされた要求を通知します。** macOS と iOS では、WebKit の `stopURLSchemeTask` コールバックが対応する要求コンテキストをキャンセルするため、別のページへ移動済みのページに属するポーリングは直ちに待機を解除されます。レジストリは保持されたネイティブタスクの識別情報をキーとし、要求処理によってタスクが閉じられるとエントリを削除します。現在のブリッジでは、Linux と Windows には同等の早期中止コールバックがまだ公開されていません。そのため、これらの環境では待機中の要求は保持期限が切れるまで残ります。規則 1 により、いずれの場合も<em>接続</em>は速やかに閉じられます。それ以外の場合、キャンセルは Linux では `EPIPE` として表面化し、Windows では `Finish` になって初めて表面化します。

## トランスポートの選択

`Stream(name)` は `window._wails.streamFactory` を参照します。サーバービルドでは、実際の `WebSocket` を返す実装が設定されます。WebView ビルドでは未設定のままとなり、ポーリングクライアントが使用されます。

生成されたバインディングはモジュールスコープでストリームを作成するため、どのモジュール本体が実行されるよりも前にファクトリーを設定<strong>しなければなりません</strong>。`custom.js` では設定できません。`loadOptionalScript` は HEAD 要求を行ってから `<script>` タグを追加するため、実行が遅すぎます。代わりに、配信時にファクトリーをランタイムバンドルの先頭へ追加します（`stream_prelude_server.go`）。ES モジュールの依存関係はインポーターより先に評価されるため、この方法は構造上同期的です。

3つ目のトランスポートを追加する場合も、prelude に配置してください。`custom.js` に戻したくなっても、そうしてはいけません。

## 開発モードでのフロントエンドパッケージ

生成されたプロジェクトは、アセットサーバーが配信するバンドル済みの `/wails/runtime.js` からではなく、**npm** から `@wailsio/runtime` をインポートします。`wails3 dev` では、Vite はこれを `node_modules` から解決するため、公開済みランタイムを使用してビルドされたアプリには、ブランチ上で追加されたクライアント側の機能は反映されません。

ストリームが未リリースの間は、テストアプリがこの作業ツリーのパッケージを参照するようにします。

```bash
task v3:install-runtime -- ./path/to/your-app/frontend
```

これにより最初に `dist/` が再ビルドされるため、常に最新のソースがインストールされます。元に戻すには、同じディレクトリで  
`npm install @wailsio/runtime@latest` を実行します。

クライアントのビルド出力は <strong>2 つ</strong>あり、一方だけを再ビルドしてもう一方を再ビルドし忘れやすい点に注意してください。`task v3:runtime:build:package` は npm パッケージの `dist/`（アプリのフロントエンドがインポートするもの）を生成し、`task v3:runtime:build:assets` は  
`bundledassets/runtime.js`（WebView がアセットサーバーから読み込むもの）を生成します。  
`stream.ts` を変更した場合は、両方を再ビルドする必要があります。

## テスト

```bash
go test ./pkg/application/ -run TestStream -race        # protocol, ordering, backpressure
go test -tags server ./pkg/application/ -run TestServerMode
pnpm --dir v3/internal/runtime/desktop/@wailsio/runtime test
```

重要なのは順序テストです。8 個の goroutine が、キューロック下で払い出されるカウンターに基づいて並行送信し、取り出された順序が受理された順序と完全に一致しなければなりません。このテストが一度でも失敗した場合、単一ドレイナーの不変条件が破られています。

負荷テスト用ハーネス：

```bash
go run ./tests/stream-performance -duration 20s              # full sweep
go run ./tests/stream-performance -upload -duration 10s      # JS→Go matrix
go run ./tests/stream-performance -reloads 6                 # connection lifecycle
```

Windows では、対話型コンソールセッションで実行する必要があります。通常の SSH 呼び出しでは、セッション 0 内で出力長がゼロのまま終了します。また、`C:\Users\<user>` の ACL は所有者だけにアクセスを許可するよう設定されているため、バイナリは SSH アカウントとコンソールアカウントの両方が読み取れる場所に配置する必要があります。

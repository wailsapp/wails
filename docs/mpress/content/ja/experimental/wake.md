Wake は Wails の実験的なビルドシステムです。1 つの `wails.yaml` に、アプリケーション、フロントエンド、ターゲットプラットフォーム、パッケージ、署名設定を記述します。Wake はその設定を使用してビルドを計画および実行し、変更されていない処理をキャッシュして、生成されたファイルを報告します。

このチュートリアルでは、小さなデスクトップアプリケーションを作成し、ブラウザーで設定して、自分のコンピューター向けにビルドした後、開発モードで実行します。まず、ローカルターゲットを 1 つだけ指定し、署名なしでビルドします。最初のビルドが成功してから、クロスコンパイルと配布を追加してください。

すでにアプリケーションがある場合は、[既存のプロジェクトを移行する](#heading-6)に進んでください。個々のフィールドと高度なワークフローについては、[YAML ビルドガイド](/experimental/yaml-builds/)および[マニフェストリファレンス](/reference/wails-yaml-fields/)を参照してください。

## 実験版で想定されること

@note{type="caution" title="テスト用プロジェクトまたは別のブランチを使用してください"}
Wake はオプトイン方式であり、その設定、コマンド、動作はプレビュービルド間で変更される可能性があります。安定版ビルドシステムと同等の互換性保証はまだありません。プロジェクトの動作が確認済みのリビジョンを保持し、テストした CLI とフレームワークのバージョンを記録してください。パッケージを配布する前に、配布先のシステムでテストしてください。
@end

Wake と **Pure Go** バックエンドは別々の選択項目です。Wake を有効にしても、Pure Go は自動的には有効になりません。このチュートリアルでは標準バックエンドを使用するため、macOS および Linux の GUI ビルドには通常どおりネイティブ開発ツールが必要です。

ウィザードは要件を確認し、設定を保存します。保存はビルドではなく、選択したすべてのターゲットの準備が整っていることを証明するものでもありません。不足しているツールや認証情報には、たとえば CI ホスト上で後から対処できます。無効なターゲットとパッケージの組み合わせは、保存前に修正する必要があります。

移行は**一方向**です。Wake は Taskfile を実行せず、Task テンプレートを展開せず、YAML を Taskfile に戻す変換も行いません。未移行のプロジェクトでは、引き続き別の従来型 Task ランタイムを使用します。有効な `wails.yaml` が暗黙的にそのランタイムへフォールバックすることはありません。

## 開始する前に

Go、スターターフロントエンド用の npm を含む Node.js、および使用するコンピューター向けの[プラットフォーム依存関係](/getting-started/installation/#platform-specific-dependencies)が必要です。新しいプロジェクトフォルダーを作成するディレクトリから開始してください。ウィザードを使用するためのブラウザーも必要です。

このプレビューを含む CLI とフレームワークのリビジョンを使用してください。安定版の `v3.0.0` CLI をインストールしても、ここで説明する Wake セットアップ画面は追加されません。次のコマンドでは、[PR #6531](https://github.com/wailsapp/wails/pull/6531) のプレビューに固定します。

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@44e449c91
wails3 version
```

Go の実行ファイルがあるディレクトリが `PATH` に含まれていることを確認してください。詳しくは、[インストールガイド](/getting-started/installation/)を参照してください。このチュートリアルの後半では、アプリケーションの Go 依存関係を同じリビジョンに固定します。より新しいプレビューをテストするときは、両方のリビジョン引数を同時に更新してください。

### ターミナルで Wake を有効にする

Bash または Zsh の場合：

```bash
export WAILS_EXP_USE_WAKE=1
```

PowerShell の場合：

```powershell
$env:WAILS_EXP_USE_WAKE = '1'
```

チュートリアルの残りの手順では、このターミナルを開いたままにしてください。Wake コマンドを実行する新しいターミナルや CI ジョブでは、この変数を再度設定してください。Wake は変数の**存在**によって有効になります。`false` または空文字列を設定しても無効にはなりません。以前の `WAILS_USE_WAKE` という名前は無視されます。

## アプリケーションを作成する

プロジェクト作成ウィザードを実行します。

```sh
wails3 init -ui
```

ブラウザーでプロジェクトウィザードが開きます。このウィザードはソースファイルを作成します。ビルド方法は、この後に説明する別の `wails3 setup` ウィザードで設定します。

| 画面 | このチュートリアルでの選択 | 次に行われること |
| --- | --- | --- |
| **プロジェクト — Wails プロジェクトの作成** | `wake-demo` と入力し、**続行**を選択します。 | 表示されているディレクトリの下に、新しい `wake-demo` フォルダーとしてプロジェクトが作成されます。 |
| **フレームワーク — フレームワークの選択** | **Vanilla** を選択し、**続行**を選択します。 | フレームワーク固有の学習手順を必要としない、小規模なフロントエンドが作成されます。 |
| **言語 — 使用言語** | **JavaScript** を選択し、**続行**を選択します。 | TypeScript 専用の**バインディング**画面はスキップされます。 |
| **詳細 — プロジェクトの詳細** | 製品名には `Wake Demo`、バンドル識別子には `com.example.wakedemo`、バージョンには `0.1.0` を使用します。**プロジェクトを作成**をクリックします。 | Wake が有効な場合、詳細情報は `wails.yaml` に書き込まれます。 |

このチュートリアルでは、**グローバルの既定値を使用**を選択しないでください。選択すると、フレームワークと言語の選択がスキップされます。別のプロジェクトで TypeScript を選択した場合は、**バインディング**画面で、生成する Go データバインディングにインターフェースとクラスのどちらを使用するか選択できます。

ターミナルに戻り、プロジェクトの作成が完了するまで待ちます。その後、次を実行します。

```sh
cd wake-demo
go get github.com/wailsapp/wails/v3@44e449c91
```

これで、`main.go`、Go モジュール、`frontend` ディレクトリ、ネイティブの `wails.yaml` が作成されているはずです。組み込みテンプレートは Wake を直接使用するため、この新しいプロジェクトを移行する必要はありません。コミュニティテンプレートには、独自の従来型タスクが含まれている場合があり、代わりに後述する移行レビューが必要になることがあります。

## 画面ごとにビルドを設定する

`wake-demo` 内から、次を実行します。

```sh
wails3 setup
```

ブラウザーに **WAKE セットアップ**が表示されます。一般的なセットアップフローが表示された場合は、コマンドを起動したターミナルで `WAILS_EXP_USE_WAKE` が設定されていることと、プレビュー版 CLI を実行していることを確認してください。

以下のスクリーンショットは、Linux でこの手順を実行した場合のものです。ホストターゲットと必要なツールは、Windows または macOS では異なります。

### プロジェクト — メタデータがない場合のみ

作成したばかりのアプリケーションでは、`init` によってメタデータがすでに書き込まれているため、この画面は**スキップ**されます。これは想定どおりです。

ネイティブマニフェストや従来のビルド設定がない既存の Go ソースディレクトリを設定する場合、**プロジェクトについて**画面で、製品名、プロジェクト名、アプリケーション識別子、バージョン、会社、説明の入力を求められます。これらの値は、**保存**を選択するまでウィザード内に保持されます。セットアップではアプリケーションのソースファイルは作成されません。Taskfile または従来のメタデータが検出された場合は、先に移行手順に従ってください。

### アプリケーション — 何をビルドしますか？

**デスクトップアプリケーション**を選択します。**既存のバイナリをパッケージ化**はオフのままにし、**標準バックエンド**を選択します。**続行**をクリックします。

![デスクトップアプリケーションと標準バックエンドを選択し、ビルド済みバイナリのパッケージ化をオフにしたアプリケーション画面。](/assets/screenshots/wake/application.png)

- **デスクトップアプリケーション**は、Web フロントエンドを備えた GUI をビルドします。
- **コマンドラインアプリケーション**と**サーバー**は、デスクトップウィンドウを持たないプログラムを表します。この選択を変更しても、アプリケーションのソースは書き換えられません。選択した種類に一致するソースプロジェクトを使用してください。
- <strong>Pure Go（実験的）</strong>は、別途有効化するオプトイン項目です。依存関係も CGo なしでビルドできる場合、サポート対象のデスクトップコンパイルで C コンパイラーが不要になります。ただし、ターゲットのランタイムライブラリや、すべてのパッケージ化および署名ツールが不要になるわけではありません。
- **既存のバイナリをパッケージ化**は、`--skip-build`を使用するコマンドを準備します。
  事前にビルド済みのバイナリが必要です。新規プロジェクトでは無効のままにしてください。

バックエンドは**プロジェクト全体の設定**です。これらの設定を継承するほかのプロファイルも、ここでの変更によって動作が変わる場合があります。

### ターゲット — どこで実行しますか？

使用中のコンピューター向けのターゲットだけを残し、**続行**をクリックします。
ウィザードでは、最初にホストのオペレーティングシステムとアーキテクチャが選択されています。

![チュートリアルのホスト向けに linux/amd64 だけが選択されたターゲット画面。](/assets/screenshots/wake/targets.png)

ターゲット名は、オペレーティングシステムと CPU アーキテクチャの組み合わせです。たとえば、`windows/amd64`、Apple Silicon Mac 向けの`darwin/arm64`、`linux/amd64`などです。
`darwin`は macOS を意味します。別のターゲットを選択すると、そのマシン向けの実行ファイルが要求されますが、その実行ファイルを現在のコンピューターで実行できるようになるわけではありません。

追加のアーキテクチャ、macOS ユニバーサルビルド、試験的なモバイルターゲットは、後でセットアップを再実行するときに設定してください。

### パッケージ — リリース出力を選択する

パッケージ形式のチェックボックスはすべて未選択のままにし、**リリース出力に署名**も無効のままにします。
**続行**をクリックします。

![追加の Linux パッケージ形式が選択されておらず、署名が無効になっているパッケージ画面。](/assets/screenshots/wake/packages.png)

追加の形式を選択しない場合、Wake はターゲットのデフォルト出力を生成します。デスクトップ実行ファイル、または macOS GUI の場合は macOS アプリケーションバンドルです。これでアプリケーションをローカルに確認できます。後で形式を選択すると、サポートされている環境では DMG、MSIX、NSIS、DEB、AppImage などの配布用出力が追加されます。

この最初のローカルビルドでは、署名は任意です。未署名のビルドが成功しても、アプリケーションを一般公開する準備が整ったことにはなりません。

### ツール — ビルドに使用するツール

選択内容に対する要件を確認してください。この一覧は Wake のビルドプランに基づくものであり、すべてのプラットフォームにすべてのツールをインストールするよう求めるものではありません。

![ローカルの Linux ソースビルド向けに解決された要件を示すツール画面。](/assets/screenshots/wake/tools.png)

このレッスンでは、Go とフロントエンドツールに加えて、ホストの標準 GUI バックエンドに必要なネイティブ開発ツールが必要です。Docker は一律の要件ではありません。CGo を使用するクロスビルドでは、コンパイラとターゲットライブラリ、またはサポートされているコンテナツールチェーンが必要になる場合があります。

ローカルビルドを試す前に、**準備未完了**、**設定が必要**、**更新が必要**と表示された行を解決してください。表示されている手順があればそれに従い、なければ[プラットフォーム別インストールガイド](/getting-started/installation/)を参照してから、**再確認**をクリックします。インストールによってターミナルの`PATH`が変更された場合は、セットアップの再起動が必要になることがあります。ホストの要件が整ったら、**続行**をクリックします。

このコンピューターにツールがなくても、ウィザードでは有効な設定を保存できます。これは CI の設定には便利ですが、このチュートリアルでは、このコンピューター上で実行できるビルドが必要です。

### 署名 — 選択した場合のみ

署名を無効のままにしたため、この画面は**スキップ**されます。後で実行する際に**リリース出力に署名**を有効にすると、選択したデスクトッププラットフォーム用の既存の署名コントロールが表示されます。**署名は後で設定**を選ぶと、保存されるセットアッププロファイルで署名が無効になります。モバイル署名は、これらのコントロールではなく YAML で設定します。

署名のデフォルト設定はユーザー設定に保存されます。Wake は、秘密鍵やパスワードを`wails.yaml`にコピーすることなく、プロジェクト外にある設定済みの証明書ファイルを使用できます。プロジェクトで明示した署名設定が優先されます。一般公開リリースを準備する前に、[セットアップの署名ガイダンス](/getting-started/setup/)と[パッケージ化と署名のガイド](/experimental/yaml-builds/#package-and-sign-for-distribution)に従ってください。

### 保存 — ビルド設定を保存する

概要を確認します。デスクトップアプリケーション、標準バックエンド、ソースビルド、ホストのターゲット、署名無効となっていることを確認してください。**wails.yaml を保存**をクリックします。

![GUI アプリケーション、標準バックエンド、ソースビルド、未署名の linux/amd64 ターゲットを要約した保存画面。](/assets/screenshots/wake/save.png)

**ビルド設定を保存しました**、マニフェストへのパス、および次の内容が表示されます。

```sh
wails3 build setup
```

**完了**をクリックし、ターミナルに戻ります。セットアップにより、ターゲットとパッケージの選択内容が`profiles.setup`に保存されました。また、アプリケーションの種類、フロントエンドの有効化、バックエンドの設定も更新されます。既存のフロントエンドコマンド、コンパニオンプログラム、フック、無関係な設定は保持されます。

プロファイル名は重要です。`wails3 build setup`は、保存された選択内容を使用します。単に`wails3 build`を実行しても、`setup`プロファイルは自動的に選択されません。

## 最初のアプリケーションをビルドして実行する

ウィザードに表示されたコマンドを実行します。

```sh
wails3 build setup
```

最初のビルドでは、フロントエンドの依存関係をインストールし、バインディングを生成して、アプリケーションをコンパイルします。以降のビルドでは、変更のない処理結果を再利用できます。**ビルド成功**と表示されるまで待ち、CLI が出力したパスを確認してください。デフォルトの出力ディレクトリは`bin`です。macOS GUI は`.app`バンドルとして構成されます。

自分のコンピューターで開発モードを開始します。

```sh
wails3 dev
```

スターターアプリケーションのウィンドウが表示されます。名前を入力して、挨拶機能を試してください。`frontend/index.html`にある名前入力欄のプレースホルダーを変更してファイルを保存すると、フロントエンドが更新されます。Go の再ビルドを試すには、`greetservice.go`の挨拶文を編集します。完了したら、ターミナルで**Ctrl+C**を押します。

開発はローカルホストで行うワークフローです。リリースプロファイルに複数のクロスビルドターゲットを含めても、開発ウィンドウを実行できるマシンは変わりません。本番用アプリケーションをローカルでビルドして起動するには、`wails3 run`を使用します。[run リファレンス](/reference/wails-yaml-run/)も参照してください。

これで、ソースプロジェクト、確認済みのビルドプロファイル、正常に動作するローカル開発ループが用意できました。ソースと`wails.yaml`をバージョン管理にコミットしてください。生成された`.wails/`作業ファイルは、設定のソースではありません。

## 次にできること

| 目的 | Wake のサポート | 最初に確認すること |
| --- | --- | --- |
| 別のデスクトップ向けにビルドする | Windows、macOS、Linux のターゲット。macOS の両アーキテクチャとユニバーサル出力を含みます。 | Pure Go と CGo では、コンパイラの要件が異なります。デプロイ先の OS とアーキテクチャでテストしてください。 |
| インストーラーまたはパッケージを作成する | MSIX、NSIS、macOS app/DMG、DEB、RPM、Arch、Void、AppImage。 | NSIS には`makensis`が必要です。AppImage にはターゲットランタイムが必要です。GUI のクロスパッケージ化には、別途用意した Linux ランタイムツリーも必要です。 |
| リリースに署名する | Windows、macOS、DEB/RPM/Arch 向けの、エクスポートした鍵によるポータブルな署名。ネイティブの ID ストアも引き続き使用できます。 | ID、形式、ホストごとに制限があります。AppImage と Void には組み込みの署名フローがありません。 |
| macOS アプリを公証する | チーム用 API キーによる提出とチケットのステープル、または macOS キーチェーンプロファイル。 | 適切な Developer ID 署名とタイムスタンプも必要です。Go が生成したテスト署名がネイティブチェックに合格しても、Apple がリリースを受理する証明にはなりません。 |
| 複数のプログラムをビルドする | GUI、CLI、またはサーバーのプライマリプログラムと、名前付きのコンパニオンプログラム。 | コンパニオンのパッケージと種類を YAML で宣言します。ウィザードはそれらのソースを生成しません。 |
| 別の場所でビルドしたファイルをパッケージ化する | `wails3 build setup --skip-build`. | `build.output` に、対応する実行可能ファイル名とアーキテクチャを指定します。このフラグはコマンド実行時に一度だけ選択するものであり、永続的なセットアップ設定ではありません。 |
| リリース自動化を追加する | 名前付きプロファイル、範囲が限定されたライフサイクルフック、キャッシュ、およびパッケージ処理の並列実行。 | リテラル YAML と、プロジェクトが所有する宣言済みスクリプトを使用します。任意の Taskfile の動作を Wake の拡張機構として使用することはできません。 |

`setup` プロファイルを変更するには、`wails3 setup` を再度開きます。その他の名前付きプロファイルと詳細設定は、`wails.yaml` で編集します。完全な例とパッケージ要件については、[YAML ビルドガイド](/experimental/yaml-builds/)を参照してください。GUI アプリケーションには、引き続き対象環境のシステムライブラリが必要です。Pure Go を使用しても、完全に静的なアプリケーションにはなりません。

iOS と Android は引き続き実験的機能であり、それぞれのプラットフォーム SDK と CGo が必要です。また、この最初のデスクトップ向けチュートリアルの対象外です。ウィザードを使用しても、任意のホスト間でモバイルビルドを移植可能にはできません。

## 既存プロジェクトを移行する

動作している **Wails v3** プロジェクトの作業ツリーを、別のブランチまたはコピーで扱ってください。これはビルド構成の移行であり、Wails v2 からのアップグレードではありません。有効化後に動作を比較できるよう、既存のビルド結果とテストを保持してください。

@note{type="caution" title="移行対応は未完了です"}
固定されたプレビュー版では、現在の標準レガシーテンプレートから生成したプロジェクトでも、阻害要因が報告される場合があります。既知の例として、動的に選択されるタスクや、レガシービルド構成内の認識されない `exit_policy` フィールドがあります。有効化を通すためだけに、必要な動作を削除しないでください。解析でプロジェクトを表現できない場合は、レガシービルドを使い続け、診断結果を報告してください。上記の新規プロジェクト向けチュートリアルでは、移行は不要です。
@end

### 1. アクティブなビルドを変更せずに解析する

Wake を有効にし、このページの冒頭で示したプレビュー版 CLI を使用します。既存プロジェクトのルートから、次を実行します。

```sh
wails3 migrate --dry-run
```

報告された対応済みの設定と阻害要因を確認してください。アナライザーはレガシー宣言を読み取りますが、そのコマンドは実行しません。ドライランではアクティブなマニフェストは作成されません。機械可読な診断結果を得るには `wails3 migrate --json` を使用します。ドラフトの書き込みも避ける場合は、`--dry-run --json` を使用してください。

### 2. 非アクティブな移行案を作成して確認する

```sh
wails3 migrate
```

これにより作成されるのは **`wails.migrated.yaml`** であり、`wails.yaml` ではありません。既存の Taskfile および `build/config.yml` と並べて内容を確認してください。プロジェクトのメタデータ、フロントエンドコマンド、対象アーキテクチャ、パッケージの内容、アセット、署名設定を確認します。シークレットは環境変数または認証情報ストアに保持してください。

既知の組み込みタスクは、ネイティブ設定にマッピングできます。プロジェクト所有のスクリプトを呼び出す、保守的で引数を取らないライフサイクルタスクは、フックに変換できます。それ以外の到達可能なカスタムタスクの動作は阻害要因となります。Wake が暗黙に破棄したり、フォールバックとして Task 経由で実行したりすることはありません。

ドラフトがすでに存在する場合、移行処理は確認済みの編集内容を上書きしません。意図的に置換または再生成する前に、コピーを保存してください。有効化チェックを回避する目的で、阻害要因のあるドラフトの名前を `wails.yaml` に変更しないでください。未対応のレガシー動作を削減または置換し、有効化の前に解析を再実行します。プロジェクトをまだ表現できない場合は、レガシービルドを使い続け、不足している対応を報告してください。

### 3. 明示的に有効化する

ドラフトを確認して阻害要因を解消したら、次を実行します。

```sh
wails3 migrate --activate --dry-run
wails3 migrate --activate
```

最初のコマンドは、有効化を反映せずに検査します。2 番目のコマンドは、レガシー宣言を再検査してドラフトを検証した後、`wails.yaml` をアトミックに作成します。有効化に成功すると、非アクティブな `wails.migrated.yaml` は削除されます。Taskfile、`build/config.yml`、スクリプト、アセットは変更されません。この時点以降、アクティブなマニフェストが Wake のビルドを制御します。古いファイルが第 2 の構成ソースとして扱われることはありません。

一部の古いプロジェクトには、トップレベルに `info:` セクションを持つ、メタデータ専用の `wails.yaml` がすでに存在します。これはネイティブの Wake マニフェストではありませんが、有効化先をすでに占有しています。そのレガシーファイルを保持したうえで、有効化の前に意図的に移動してください。移行ツールが代わりに上書きまたは名前変更することはありません。

### 4. 移行したアプリケーションを検証する

```sh
wails3 config check
wails3 build
wails3 dev
```

カスタムのリリース動作も含め、アプリケーションとパッケージの内容を以前のビルドと比較してください。プロジェクトのテストを実行します。ドラフトに `release` プロファイルが含まれている場合は、たとえば `wails3 config check release` と `wails3 build release` のように、移行した各プロファイルを明示的に確認してください。

これで、`wails3 setup` を実行して専用の `setup` プロファイルを追加または置換できます。既存の `release` プロファイルが自動的に選択または編集されることはありません。

### 実験を中止する必要がある場合

`WAILS_EXP_USE_WAKE` の設定を解除するとオプトインは無効になりますが、アクティブな `wails.yaml` が存在する場合は、引き続き Taskfile への自動ルーティングが阻止されます。無効な YAML がある場合もエラーで停止します。逆移行用のコマンドはありません。

以前のワークフローに戻すには、アクティブなマニフェストが存在しない状態も含め、移行前の完全なプロジェクトリビジョンをバージョン管理から復元し、それと互換性のある CLI および依存関係を使用してください。その前に、必要な新しいソース変更を保存しておきます。試行用のブランチを分けておくと、この意図的な復旧がはるかに容易になります。

## 問題を診断してフィードバックを送る

| 症状 | 最初に確認すること |
| --- | --- |
| セットアップで汎用ウィザードが表示される | 起動元のターミナルで `WAILS_EXP_USE_WAKE` を設定し、`PATH` 上にある `wails3` 実行可能ファイルを確認してください。 |
| セットアップで移行を求められる | レガシープロジェクト、またはレガシー構成を使用するコミュニティテンプレートを開いています。有効化する前に移行内容を確認してください。 |
| 保存したビルドでツール不足が報告される | 保存されるのは設定の意図です。**ツール**に戻り、ホストの要件を満たしてから再確認してください。 |
| クロスビルドした実行可能ファイルをこの環境で起動できない | 選択したオペレーティングシステムとアーキテクチャ上で実行してください。ローカル開発にはホストターゲットを使用します。 |
| ビルド済みモードでバイナリが見つからない | 複数ターゲット用のサブディレクトリも含め、[ビルド済みファイルの名前とパス](/experimental/yaml-builds/#use-prebuilt-desktop-executables)を確認してください。 |
| マニフェストの変更が失敗する | 該当するプロファイルに対して `wails3 config check` を実行し、フィールドの診断内容に従ってください。Wake は Taskfile にフォールバックしません。 |

`wails3 build setup --plan --json` を使用して、ビルドを実行前に検査します。
`wails3 config check` は構成を検証し、`wails3 eject` はアクティブなマニフェストを変更せずに、非アクティブな `wails.ejected.yaml` スナップショットを書き込みます。
コマンド出力を共有する前に確認してください。プロジェクトのパスや認証情報の保存場所から、ローカル環境が特定される可能性があります。

[Experiments Discussions](https://github.com/wailsapp/wails/discussions/categories/experiments) でフィードバックを共有するか、[再現可能なバグを報告](https://github.com/wailsapp/wails/issues)してください。CLI とフレームワークのリビジョン、ホストの OS／アーキテクチャ、選択したターゲット、実行した正確なコマンド、Pure Go を選択したかどうか、および関連する診断結果を含めます。失敗した段階がコンパイル、パッケージ化、署名、アプリケーションの実行のいずれであるかも記載してください。シークレットを削除した最小限のマニフェストと、役立つ場合は `wails3 doctor` の出力を含めてください。

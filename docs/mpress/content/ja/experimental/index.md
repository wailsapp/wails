## 「実験的」とは

Wails は実験を公開した状態で提供します。実験とは、早い段階で皆さんに試していただく価値があると考えているものの、まだ正式採用を確約していないアイデアです。Wails の恒久的かつサポート対象の機能にするかどうかを決める前に、実際の使用から学びたい*ため*公開しています。

そのため、このセクションのすべての機能には次の点が当てはまります。

- <strong>オプトイン方式です。</strong>実験によって `wails3` のデフォルトの動作が変わることはありません。明示的に有効化する必要があり（通常は環境変数またはビルドフラグを使用します）、無効のままであれば既存のワークフローは何も変わりません。
- <strong>存続するとは限りません。</strong>安定版の機能へ移行する実験もあれば、原形をとどめないほど作り直されたり、廃止されたりするものもあります。確信できるものだけをリリースするよりも、公開の場で試して素早く学ぶことを重視しています。
- <strong>API は確定していません。</strong>実験の仕様が固まるまでは、リリース間で名前、フラグ、デフォルト値、動作が変わる可能性があります。変更はリリースノートに明記しますが、安定版の機能と同等の安定性は保証されません。

## CGO 不要のビルド（purego）

@note{type="caution" title="実験的機能"}
CGO 不要のバックエンドは、`purego` ビルドタグ（または `WAILS_PUREGO=1`）によってオプトインで有効になり、デフォルトでは**ありません**。有効にしなければ、macOS と Linux のビルドは従来どおり cgo バックエンドを使用します。動作はリリース間で変わる可能性があります。

@end

### 概要

通常、macOS と Linux 上の Wails は、cgo を介してシステムの UI ライブラリ（macOS では AppKit と WKWebView、Linux では GTK と WebKitGTK）を呼び出します。CGO 不要のバックエンドは、実行時にシステムライブラリを読み込む [purego](https://github.com/ebitengine/purego) を使用し、純粋な Go から同じ呼び出しを行います。

公開アプリケーション API に変更はありません。ビルド時にバックエンドを選択するだけで、アプリケーションコードを変更する必要はありません。配布する前に、配布先のシステムでアプリをテストしてください。

次の利点があります。

- <strong>Go のコンパイルに C ツールチェーンが不要です。</strong>Go のビルドには、Xcode コマンドラインツール、`gcc`、Linux 開発用ヘッダーが不要です。フロントエンドのビルドには、引き続き通常の JavaScript ツールが必要です。
- <strong>Docker を使わずにクロスコンパイルできます。</strong>任意の OS から、通常の `go build` を使用して macOS または Linux のバイナリをビルドできます。

Windows はすでに cgo を使わずにビルドされるため、影響を受けません。

### 有効にする前に

この実験を含む CLI とフレームワークのバージョンを両方使用してください。CLI だけを更新しても、アプリケーションの `go.mod` にある古いフレームワーク依存関係へバックエンドは追加されません。開発版を試すには、アプリケーションのディレクトリから次のコマンドを実行します。

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@master
go get github.com/wailsapp/wails/v3@master
```

どちらのコマンドも更新され続ける `master` ブランチを追跡します。再現可能なビルドにするには、CLI とフレームワークで同じテスト済みコミットを使用してください。Go ツールチェーンと CLI のセットアップについては、[インストールガイド](/getting-started/installation/)に従ってください。

実験的な macOS および Linux バックエンドは、`amd64` と `arm64` をサポートしています。クロスコンパイルでは指定したターゲット用の実行可能ファイルが作成されますが、そのファイルがビルドマシン上で実行されるわけではありません。ターゲットのオペレーティングシステムとアーキテクチャでテストしてください。

### 使用方法

次のいずれかの方法でバックエンドを選択します。

#### Wails CLI を使用する場合

このバージョンの CLI で生成したプロジェクトでは、`WAILS_PUREGO` を有効にすると、`build`、`package`、`dev` が実験的バックエンドを使用します。POSIX シェルでは次のようにします。

```sh
WAILS_PUREGO=1 wails3 dev
WAILS_PUREGO=1 wails3 build
WAILS_PUREGO=1 wails3 package
```

PowerShell では次のようにします。

```powershell
$env:WAILS_PUREGO = "1"
wails3 build
```

CLI は、大文字と小文字および前後の空白を区別せず、`1`、`true`、`on`、`yes` を認識します。空の値では、この実験は有効になりません。

または、1 回のビルドコマンドまたはパッケージ化コマンドにタグを渡します。

```sh
wails3 build -tags purego
wails3 package -tags purego
```

タグを設定すると、更新済みの標準 Taskfile は、ホストの Go ツールチェーンを使用して `CGO_ENABLED=0` でビルドします。たとえば、macOS または Windows から Linux ARM64 の実行可能ファイルをビルドするには、次のようにします。

```sh
wails3 build -tags purego GOOS=linux ARCH=arm64
```

古いプロジェクトでは既存の Taskfile が維持されます。カスタムビルドタスクを更新済みテンプレートと比較するか、通常の Go を使用して、それらのタスクを変更せずにバックエンドをテストしてください。環境変数は Wails CLI コマンドでタグを選択します。通常の `go build` ではタグを明示的に指定する必要があります。

#### 通常の Go を使用する場合

`go:embed` が参照するすべてのアセットが存在するように、最初にフロントエンドをビルドしてから、アプリケーションをコンパイルします。

```sh
CGO_ENABLED=0 go build -tags purego,production .
```

`CGO_ENABLED=1 go build -tags purego` も使用できます。バックエンドは同じで、プログラムのほかの部分で cgo を引き続き使用できるだけです。

クロスビルドでは、`GOOS` と `GOARCH` も設定します。

```sh
GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go build -tags purego,production -o myapp .
```

Linux では、`-tags purego,gtk3,production` を指定して GTK3 スタックを選択します。

デフォルトのバックエンドに戻すには、`purego` タグを削除し、`WAILS_PUREGO` の設定を解除します（POSIX シェルでは `unset WAILS_PUREGO`、PowerShell では `Remove-Item Env:WAILS_PUREGO`）。macOS または Linux の cgo バックエンドに戻す場合は、明示的な `CGO_ENABLED=0` 設定も削除してください。

`CGO_ENABLED=0` を指定してビルドするときにタグを付け忘れた場合、修正方法を示す 1 件のエラーでビルドが停止します。

```
undefined: requires_CGO_ENABLED_1_or_build_tag_purego
```

### 実行時要件

アプリは起動時にシステムライブラリを読み込むため、cgo ビルドの場合と同様に、ターゲットマシンへそれらのライブラリをインストールしておく必要があります。

| プラットフォーム | ライブラリ | サポート対象の最古バージョン |
|---|---|---|
| macOS | AppKit、WebKit（OS の一部） | cgo バックエンドと同じ |
| Linux（デフォルト） | GTK 4、WebKitGTK 6.0 | GTK 4.8、WebKitGTK 2.40（Debian 12） |
| Linux（`gtk3`） | GTK 3、WebKit2GTK 4.1 | GTK 3.24、WebKit2GTK 2.36（Ubuntu 22.04） |

これらの最低対応バージョンより新しい関数は、アプリの起動時に検索され、インストール済みのライブラリに存在する場合にのみ使用されます。そのため、同じバイナリを新旧どちらのシステムでも実行できます。

アプリは引き続きネイティブ UI ライブラリを使用し、Linux の libc などのシステムライブラリに動的リンクする場合があります。`CGO_ENABLED=0`は、完全に静的な実行ファイルを意味するものではありません。必要なランタイムライブラリがない場合は、対象システムに対応する GTK/WebKit スタックをインストールしてください。ビルドマシンに C ヘッダーをインストールしても、ランタイムライブラリの不足は解消されません。

### パッケージ化と署名

このバックエンドにより、コンパイル時に C ツールチェーンが不要になります。ただし、各パッケージ形式には固有の要件があります。特に、`purego`を選択しても、既存の AppImage デプロイツールがクロスプラットフォームになるわけではありません。[Linux のパッケージ化](/guides/build/linux/)を参照してください。

クロスビルドした macOS アプリケーションも、配布前に適切な署名と公証が必要です。Windows インストーラーにも、引き続きインストーラー作成用のツールが必要です。[macOS のパッケージ化](/guides/build/macos/)および[Windows のパッケージ化](/guides/build/windows/)を参照してください。cgo を使用する依存関係がある場合、`CGO_ENABLED=1`にも C コンパイラーと、対象環境向けのヘッダーまたはライブラリが必要です。Wails の pure-Go バックエンドを選択しても、それらの依存関係の要件はなくなりません。

### 検証

生成されたバインディングのチェックと`puregocheck`では、ネイティブシンボル、オプションのバージョンガード、バックエンドのカバレッジを検査します。Linux の同等性ワークフローでは、両方のバックエンドを使用して GTK4 と GTK3 をテストします。これには、アセットリクエスト、バイナリのリクエストボディ、ネイティブディスパッチが含まれます。また、Linux ARM64 ターゲットのクロスコンパイルも行います。クロスコンパイルのチェックではコードをビルドできることを確認し、ランタイムのチェックではテストマシンにインストールされたネイティブライブラリを実際に使用して検証します。

[バックエンドのテストガイド](https://github.com/wailsapp/wails/blob/master/v3/TESTING.md)では、同等性プローブとエンドツーエンドの入力テストについて説明しています。問題を報告する際は、コンパイルの失敗と、ランタイムまたはパッケージ化の失敗を区別してください。

### 既知の相違点

- <strong>Linux のメニューアクセラレーターは、アプリケーションレベルで登録されます。</strong>異なるメニューに競合するアクセラレーターを割り当てないでください。`SetMenu(nil)`を使用してウィンドウのメニューを明示的に削除すると、削除されたメニューのショートカットもそのウィンドウでは作動しなくなります。他のウィンドウでは、メニューとショートカットが引き続き維持されます。
- **macOS の「開く」パネルと「保存」パネル**は、cgo の場合と同様に別のシステムプロセスで実行されます。テストでは、これらのパネルが開き、正常にキャンセルできることを確認します。

ほかにも何か見つけた場合は、ぜひお知らせください。

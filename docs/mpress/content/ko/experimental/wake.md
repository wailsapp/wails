Wake는 Wails의 실험적 빌드 시스템입니다. 하나의 `wails.yaml`에서 애플리케이션, 프런트엔드, 대상 플랫폼, 패키지 및 서명 설정을 정의합니다. Wake는 이 구성을 사용해 빌드를 계획하고 실행하며, 변경되지 않은 작업을 캐시하고 결과 파일을 보고합니다.

이 튜토리얼에서는 작은 데스크톱 애플리케이션을 만들고 브라우저에서 구성한 다음, 현재 컴퓨터용으로 빌드하고 개발 모드에서 실행합니다. 먼저 로컬 대상 하나와 서명되지 않은 빌드로 시작하세요. 첫 빌드가 정상적으로 작동한 후 교차 컴파일과 배포를 추가하세요.

이미 애플리케이션이 있나요? [기존 프로젝트 마이그레이션](#---1)으로 이동하세요. 개별 필드와 고급 워크플로는 [YAML 빌드 가이드](/experimental/yaml-builds/) 및 [매니페스트 참조 문서](/reference/wails-yaml-fields/)를 확인하세요.

## 실험 기능에서 예상할 수 있는 사항

@note{type="caution" title="테스트 프로젝트 또는 별도 브랜치를 사용하세요"}
Wake는 선택적으로 활성화하는 기능이며, 미리 보기 빌드 간에 구성, 명령 및 동작이 변경될 수 있습니다. 아직 안정적인 빌드 시스템과 같은 호환성 보장을 제공하지 않습니다. 정상 작동이 확인된 프로젝트 리비전을 유지하고 테스트한 CLI 및 프레임워크 버전을 기록하세요. 패키지를 배포하기 전에 대상 시스템에서 테스트하세요.
@end

Wake와 **Pure Go** 백엔드는 서로 별개의 선택 사항입니다. Wake를 활성화해도 Pure Go가 자동으로 활성화되지는 않습니다. 이 튜토리얼에서는 표준 백엔드를 사용하므로 macOS 및 Linux GUI 빌드에는 일반적으로 필요한 네이티브 개발 도구가 필요합니다.

마법사는 요구 사항을 확인하고 구성을 저장합니다. 저장은 빌드가 아니며, 선택한 모든 대상이 준비되었다는 증거도 아닙니다. 누락된 도구나 자격 증명은 나중에 CI 호스트 등에서 준비할 수 있습니다. 유효하지 않은 대상 및 패키지 조합은 저장하기 전에 수정해야 합니다.

마이그레이션은 **단방향**입니다. Wake는 Taskfile을 실행하거나 Task 템플릿을 확장하지 않으며, YAML을 Taskfile로 다시 변환하지도 않습니다. 마이그레이션하지 않은 프로젝트는 별도의 레거시 Task 런타임을 계속 사용합니다. 활성 `wails.yaml`은 이 런타임으로 자동 대체되지 않습니다.

## 시작하기 전에

Go, 스타터 프런트엔드용 Node.js와 npm, 그리고 현재 컴퓨터에 필요한 [플랫폼 종속 항목](/getting-started/installation/#platform-specific-dependencies)이 필요합니다. 새 프로젝트 폴더를 만들 디렉터리에서 시작하세요. 마법사를 사용하려면 브라우저도 필요합니다.

이 미리 보기가 포함된 CLI 및 프레임워크 리비전을 사용하세요. 안정 버전 `v3.0.0` CLI를 설치해도 여기에서 설명하는 Wake 설정 화면은 추가되지 않습니다. 다음 명령은 [PR #6531](https://github.com/wailsapp/wails/pull/6531)의 미리 보기 리비전으로 고정합니다.

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@0243da963
wails3 version
```

Go 실행 파일 디렉터리가 `PATH`에 포함되어 있는지 확인하세요. 자세한 내용은 [설치 가이드](/getting-started/installation/)를 참조하세요. 이 튜토리얼의 뒷부분에서는 애플리케이션의 Go 종속 항목을 같은 리비전으로 고정합니다. 더 최신 미리 보기를 테스트할 때는 두 리비전 인수를 함께 업데이트하세요.

### 터미널에서 Wake 활성화

Bash 또는 Zsh에서는 다음과 같이 실행하세요.

```bash
export WAILS_EXP_USE_WAKE=1
```

PowerShell에서는 다음과 같이 실행하세요.

```powershell
$env:WAILS_EXP_USE_WAKE = '1'
```

튜토리얼을 마칠 때까지 이 터미널을 열어 두세요. Wake 명령을 실행하는 새 터미널이나 CI 작업마다 변수를 다시 설정하세요. 변수의 **존재 여부**에 따라 Wake가 활성화됩니다. `false` 또는 빈 문자열로 설정해도 비활성화되지 않습니다. 이전 `WAILS_USE_WAKE` 이름은 무시됩니다.

## 애플리케이션 만들기

프로젝트 생성 마법사를 실행하세요.

```sh
wails3 init -ui
```

브라우저에서 프로젝트 마법사가 열립니다. 이 마법사는 소스 파일을 생성하며, 아래의 별도 `wails3 setup` 마법사에서 해당 파일의 빌드 방법을 구성합니다.

| 화면 | 이 튜토리얼에서 선택할 항목 | 다음에 진행되는 작업 |
| --- | --- | --- |
| **프로젝트 — Wails 프로젝트 만들기** | `wake-demo`을 입력한 다음 **계속**을 선택하세요. | 표시된 디렉터리 아래의 새 `wake-demo` 폴더에 프로젝트가 생성됩니다. |
| **프레임워크 — 프레임워크 선택** | **Vanilla**를 선택한 다음 **계속**을 선택하세요. | 특정 프레임워크를 별도로 학습하지 않고도 사용할 수 있는 작은 프런트엔드가 생성됩니다. |
| **언어 — 언어 기본 설정** | **JavaScript**를 선택한 다음 **계속**을 선택하세요. | TypeScript 전용 **바인딩** 화면을 건너뜁니다. |
| **세부 정보 — 프로젝트 세부 정보** | 제품 이름에는 `Wake Demo`, 번들 식별자에는 `com.example.wakedemo`, 버전에는 `0.1.0`을 사용하세요. **프로젝트 만들기**를 클릭하세요. | Wake가 활성화되어 있으므로 세부 정보가 `wails.yaml`에 기록됩니다. |

이 튜토리얼에서는 **전역 기본값 사용**을 선택하지 마세요. 이 옵션은 프레임워크와 언어 선택을 건너뜁니다. 다른 프로젝트에서 TypeScript를 선택하면 **바인딩** 화면에서 생성되는 Go 데이터 바인딩에 인터페이스 또는 클래스를 사용할지 선택할 수 있습니다.

터미널로 돌아가 프로젝트 생성이 완료될 때까지 기다리세요. 그런 다음 다음을 실행하세요.

```sh
cd wake-demo
go get github.com/wailsapp/wails/v3@0243da963
```

이제 `main.go`, Go 모듈, `frontend` 디렉터리 및 네이티브 `wails.yaml`이 있어야 합니다. 기본 제공 템플릿은 Wake를 직접 사용하므로 이 새 프로젝트를 마이그레이션할 필요가 없습니다. 커뮤니티 템플릿에는 사용자 지정 레거시 작업이 있을 수 있으며, 이 경우 아래에서 설명하는 마이그레이션 검토가 필요할 수 있습니다.

## 화면별로 빌드 구성하기

`wake-demo` 안에서 다음을 실행하세요.

```sh
wails3 setup
```

이제 브라우저에 **WAKE 설정**이 표시됩니다. 일반 설정 절차가 표시된다면 명령을 실행한 터미널에 `WAILS_EXP_USE_WAKE`이 설정되어 있는지, 미리 보기 CLI를 실행하고 있는지 확인하세요.

아래 스크린샷은 Linux에서 진행한 이 튜토리얼을 보여 줍니다. Windows 또는 macOS에서는 호스트 대상과 필요한 도구가 다릅니다.

### 프로젝트 — 메타데이터가 없을 때만

방금 만든 애플리케이션에서는 이 화면을 **건너뜁니다**. `init`에서 이미 메타데이터를 기록했기 때문이며, 이는 정상적인 동작입니다.

네이티브 매니페스트나 레거시 빌드 구성이 없는 기존 Go 소스 디렉터리를 구성하면 **프로젝트 정보** 화면에서 제품 이름, 프로젝트 이름, 애플리케이션 식별자, 버전, 회사 및 설명을 입력하라는 메시지가 표시됩니다. 이러한 값은 **저장**을 선택할 때까지 마법사에만 유지됩니다. 설정 과정에서는 애플리케이션 소스 파일을 생성하지 않습니다. Taskfile 또는 레거시 메타데이터가 발견되면 먼저 마이그레이션 절차를 따르세요.

### 애플리케이션 — 무엇을 빌드하나요?

**데스크톱 애플리케이션**을 선택하세요. **기존 바이너리 패키징**은 선택하지 않은 상태로 두고 **표준 백엔드**를 선택하세요. **계속**을 클릭하세요.

![데스크톱 애플리케이션과 표준 백엔드가 선택되어 있고 미리 빌드된 바이너리 패키징은 꺼져 있는 애플리케이션 화면.](/assets/screenshots/wake/application.png)

- **데스크톱 애플리케이션**은 웹 프런트엔드가 포함된 GUI를 빌드합니다.
- **명령줄 애플리케이션**과 **서버**는 데스크톱 창이 없는 프로그램을 나타냅니다. 이 선택을 변경해도 애플리케이션 소스는 다시 작성되지 않으므로 선택한 종류와 일치하는 소스 프로젝트를 사용하세요.
- <strong>Pure Go(실험적)</strong>는 별도로 선택해 활성화하는 기능입니다. 종속 항목도 CGo 없이 빌드할 수 있다면, 지원되는 데스크톱 컴파일에서 C 컴파일러 요구 사항이 없어집니다. 대상 런타임 라이브러리나 모든 패키징 및 서명 도구가 불필요해지는 것은 아닙니다.
- **기존 바이너리 패키징**은 `--skip-build`을 사용하는 명령을 준비합니다.
  이미 빌드한 바이너리가 필요하므로 새 프로젝트에서는 선택하지 마세요.

백엔드는 **프로젝트 전체에 적용되는 설정**입니다. 이 설정을 상속하는 다른 프로필은
여기서 설정을 변경하면 동작이 달라질 수 있습니다.

### 대상 — 어디에서 실행할까요?

현재 사용 중인 컴퓨터의 대상만 남긴 다음 **계속**을 클릭하세요.
마법사는 처음에 호스트 운영 체제와 아키텍처를 선택합니다.

![튜토리얼 호스트용 linux/amd64만 선택된 대상 화면.](/assets/screenshots/wake/targets.png)

대상 이름은 운영 체제와 CPU 아키텍처를 조합합니다. 예를 들면
`windows/amd64`, Apple Silicon Mac용 `darwin/arm64` 또는 `linux/amd64`입니다.
`darwin`은 macOS를 의미합니다. 다른 대상을 선택하면 해당 컴퓨터용 실행 파일을 요청하는 것이며,
그 실행 파일을 현재 컴퓨터에서 실행할 수 있게 되는 것은 아닙니다.

추가 아키텍처, macOS 유니버설 빌드 및 실험적 모바일 대상은 나중에 설정을 다시 진행할 때 선택하세요.

### 패키지 — 릴리스 출력 선택

패키지 형식 확인란은 모두 선택하지 않고 **릴리스 출력 서명**도 끄세요.
**계속**을 클릭하세요.

![추가 Linux 패키지 형식이 선택되지 않고 서명이 꺼진 패키지 화면.](/assets/screenshots/wake/packages.png)

추가 형식을 선택하지 않으면 Wake는 대상의 기본 출력을 생성합니다.
즉, 데스크톱 실행 파일 또는 macOS GUI용 macOS 애플리케이션 번들을 생성합니다. 이 정도면
애플리케이션을 로컬에서 확인하기에 충분합니다. 나중에 형식을 선택하면 지원되는 경우
DMG, MSIX, NSIS, DEB 또는 AppImage 같은 배포용 출력이 추가됩니다.

이 첫 번째 로컬 빌드에서는 서명이 선택 사항입니다. 서명되지 않은 빌드에 성공했더라도
애플리케이션을 공개 배포할 준비가 되었다는 의미는 아닙니다.

### 도구 — 빌드에 필요한 도구

선택 항목의 요구 사항을 확인하세요. 이 목록은 Wake의 빌드 계획에서 가져오며,
모든 플랫폼에 모든 도구를 설치하라는 의미는 아닙니다.

![로컬 Linux 소스 빌드에 맞게 확인된 요구 사항을 보여 주는 도구 화면.](/assets/screenshots/wake/tools.png)

이 과정에서는 Go와 프런트엔드 도구 외에도 호스트의 표준 GUI 백엔드에 필요한
네이티브 개발 도구가 필요합니다. Docker가 항상 필요한 것은 아닙니다.
CGo를 사용하는 크로스 빌드에는 컴파일러와 대상 라이브러리 또는 지원되는
컨테이너 도구 체인이 필요할 수 있습니다.

로컬 빌드를 시도하기 전에 **준비되지 않음**, **구성 필요** 또는 **업데이트 필요**로
표시된 행의 문제를 해결하세요. 표시된 지침이 있으면 이를 따르고, 그렇지 않으면
[플랫폼 설치 가이드](/getting-started/installation/)를 참조한 다음 **다시 확인**을 클릭하세요. 설치로 인해
터미널의 `PATH`이 변경되었다면 설정을 다시 시작해야 할 수 있습니다. 호스트 요구 사항이 준비되면
**계속**을 클릭하세요.

이 컴퓨터에 도구가 없어도 마법사는 유효한 구성을 저장할 수 있습니다.
이는 CI 구성에 유용하지만, 이 튜토리얼에서는 현재 컴퓨터에서 실행할 수 있는 빌드가 필요합니다.

### 서명 — 선택한 경우에만

서명을 꺼 두었으므로 이 화면은 **건너뜁니다**. 나중에 다시 실행하여
**릴리스 출력 서명**을 활성화하면 선택한 데스크톱 플랫폼의 기존 서명 제어 항목이 표시됩니다.
**나중에 서명 설정**을 선택하면 저장된 설정 프로필에서 서명이 꺼집니다.
모바일 서명은 이 제어 항목이 아니라 YAML에서 구성합니다.

서명 기본값은 사용자 설정에 저장됩니다. Wake는 비공개 키나 암호를
`wails.yaml`에 복사하지 않고도 프로젝트 외부에 구성된 인증서 파일을 사용할 수 있습니다.
명시적인 프로젝트 서명 설정이 우선합니다. 공개 릴리스를 준비하기 전에
[설정 서명 지침](/getting-started/setup/)과
[패키징 및 서명 가이드](/experimental/yaml-builds/#package-and-sign-for-distribution)를 따르세요.

### 저장 — 빌드 구성 저장

요약에서 데스크톱 애플리케이션, 표준 백엔드, 소스 빌드, 호스트 대상 및 서명 비활성화를 확인하세요.
**wails.yaml 저장**을 클릭하세요.

![GUI 애플리케이션, 표준 백엔드, 소스 빌드 및 서명되지 않은 linux/amd64 대상을 요약하는 저장 화면.](/assets/screenshots/wake/save.png)

**빌드 구성 저장됨**과 매니페스트 경로 및 다음 내용이 표시되어야 합니다.

```sh
wails3 build setup
```

**완료**를 클릭하고 터미널로 돌아가세요. 설정 과정에서 대상과 패키지 선택 사항이
`profiles.setup` 아래에 저장되었습니다. 애플리케이션 종류, 프런트엔드 활성화 및 백엔드 설정도 업데이트됩니다.
기존 프런트엔드 명령, 보조 프로그램, 훅 및 관련 없는 구성은 그대로 유지됩니다.

프로필 이름은 중요합니다. `wails3 build setup`은 저장된 해당 선택 사항을 사용합니다.
일반 `wails3 build`은 `setup` 프로필을 자동으로 선택하지 않습니다.

## 첫 번째 애플리케이션 빌드 및 실행

마법사에 표시된 명령을 실행하세요.

```sh
wails3 build setup
```

첫 빌드에서는 프런트엔드 종속성을 설치하고 바인딩을 생성한 다음 애플리케이션을 컴파일합니다.
이후 빌드에서는 변경되지 않은 작업을 재사용할 수 있습니다. **빌드 성공**이 표시될 때까지 기다린 후
CLI가 출력한 출력 경로를 확인하세요. 기본 출력 디렉터리는 `bin`이며,
macOS GUI는 `.app` 번들로 구성됩니다.

현재 컴퓨터에서 개발 모드를 시작하세요.

```sh
wails3 dev
```

시작 애플리케이션 창이 표시되어야 합니다. 이름을 입력하고 인사말 기능을 사용해 보세요.
`frontend/index.html`에서 이름 입력란의 자리표시자를 변경하고 파일을 저장하면 프런트엔드가 새로 고쳐져야 합니다.
Go 재빌드를 시험하려면 `greetservice.go`에서 인사말을 수정하세요. 작업을 마치면 터미널에서
**Ctrl+C**를 누르세요.

개발은 로컬 호스트에서 진행하는 워크플로입니다. 릴리스 프로필에 여러 크로스 빌드 대상이 포함되어 있어도
개발 창을 실행할 수 있는 컴퓨터는 달라지지 않습니다. 프로덕션 애플리케이션을 로컬에서 빌드하고 실행하려면
`wails3 run`을 사용하세요. 자세한 내용은 [실행 참고 문서](/reference/wails-yaml-run/)를 참조하세요.

이제 소스 프로젝트, 검토를 마친 빌드 프로필 및 정상 작동하는 로컬 개발 루프가 준비되었습니다.
소스와 `wails.yaml`을 버전 관리 시스템에 커밋하세요.
생성된 `.wails/` 작업 파일은 구성의 원본이 아닙니다.

## 다음 단계

| 목표 | Wake 지원 | 먼저 확인할 사항 |
| --- | --- | --- |
| 다른 데스크톱용으로 빌드 | 두 macOS 아키텍처와 유니버설 출력을 포함한 Windows, macOS 및 Linux 대상. | Pure Go와 CGo는 필요한 컴파일러가 서로 다릅니다. 대상 운영 체제와 아키텍처에서 테스트하세요. |
| 설치 프로그램 또는 패키지 만들기 | MSIX, NSIS, macOS 앱/DMG, DEB, RPM, Arch, Void 및 AppImage. | NSIS에는 `makensis`이 필요합니다. AppImage에는 대상 런타임이 필요하며, GUI 크로스 패키징에는 제공된 Linux 런타임 트리도 필요합니다. |
| 릴리스 서명 | Windows, macOS 및 DEB/RPM/Arch용 이식 가능한 내보낸 키 서명을 지원하며, 네이티브 ID 저장소도 계속 사용할 수 있습니다. | ID, 형식 및 호스트마다 제한 사항이 있습니다. AppImage와 Void에는 기본 제공 서명 절차가 없습니다. |
| macOS 앱 공증 | 팀 API 키를 사용한 제출 및 티켓 스테이플링 또는 macOS 키체인 프로필. | 적합한 Developer ID 서명과 타임스탬프가 여전히 필요합니다. Go에서 생성한 테스트 서명이 네이티브 검사를 통과하더라도 Apple이 릴리스를 승인한다는 증거는 아닙니다. |
| 여러 프로그램 빌드 | GUI, CLI 또는 서버 기본 프로그램과 이름이 지정된 보조 프로그램. | YAML에서 보조 패키지와 종류를 선언하세요. 마법사는 해당 소스 코드를 생성하지 않습니다. |
| 다른 곳에서 빌드한 파일 패키징 | `wails3 build setup --skip-build`. | `build.output`에 일치하는 실행 파일 이름과 아키텍처를 지정하세요. 이 플래그는 명령을 실행할 때 한 번만 적용하는 선택 사항이며 영구적인 설정 항목이 아닙니다. |
| 릴리스 자동화 추가 | 이름이 지정된 프로필, 범위가 제한된 수명 주기 훅, 캐싱 및 병렬 패키지 작업. | 리터럴 YAML과 프로젝트에서 관리하는 선언된 스크립트를 사용하세요. 임의의 Taskfile 동작은 Wake의 확장 메커니즘이 아닙니다. |

`setup` 프로필을 변경하려면 `wails3 setup`을 다시 여세요. 이름이 지정된 다른 프로필과 고급 설정은 `wails.yaml`에서 편집합니다. 전체 예제와 패키지 요구 사항은 [YAML 빌드 가이드](/experimental/yaml-builds/)를 참조하세요. GUI 애플리케이션에는 여전히 대상 시스템의 라이브러리가 필요합니다. Pure Go를 사용해도 완전한 정적 애플리케이션이 되지는 않습니다.

iOS와 Android는 여전히 실험 단계이며 해당 플랫폼 SDK와 CGo가 필요하므로 이 첫 데스크톱 강의에서는 다루지 않습니다. 마법사를 사용해도 모바일 빌드를 임의의 호스트 간에 이식할 수 있게 되지는 않습니다.

## 기존 프로젝트 마이그레이션

정상적으로 작동하는 **Wails v3** 프로젝트의 별도 브랜치나 작업 복사본에서 진행하세요. 이는 빌드 구성 마이그레이션이며 Wails v2에서의 업그레이드가 아닙니다. 활성화 후 동작을 비교할 수 있도록 기존 빌드 결과와 테스트를 유지하세요.

@note{type="note" title="검토된 마이그레이션으로 시작하기"}
현재 기본 제공되는 기존 템플릿으로 생성한 새 프로젝트는 프런트엔드를 빌드하기 전에도 마이그레이션할 수 있습니다. Wake는 Taskfile을 실행하거나 사용자 정의 표현식을 평가하지 않고도 이러한 템플릿의 기본 작업 선택기와 개발 수명 주기를 인식합니다.

사용자 정의 작업, 변수 재정의 및 개발 정책은 여전히 검토해야 합니다. 분석에서 프로젝트를 표현할 수 없다면 기존 빌드에 그대로 두고 진단 결과를 보고하세요. 활성화를 통과시키기 위해 필요한 동작을 제거해서는 안 됩니다. 위의 새 프로젝트 튜토리얼에는 마이그레이션이 필요하지 않습니다.
@end

### 1. 활성 빌드를 변경하지 않고 분석

Wake를 활성화하고 이 페이지의 시작 부분에 있는 프리뷰 CLI를 사용하세요. 기존 프로젝트 루트에서 다음을 실행하세요.

```sh
wails3 migrate --dry-run
```

보고된 지원 설정과 차단 요인을 확인하세요. 분석기는 레거시 선언을 읽지만 그 명령을 실행하지는 않습니다. 시험 실행에서는 활성 매니페스트를 생성하지 않습니다. 기계 판독 가능한 진단 결과가 필요하면 `wails3 migrate --json`을 사용하세요. 초안 작성도 방지하려면 `--dry-run --json`을 사용하세요.

### 2. 비활성 제안 생성 및 검토

```sh
wails3 migrate
```

이 작업은 `wails.yaml`이 아니라 <strong>`wails.migrated.yaml`</strong>을 생성합니다. 기존 Taskfile 및 `build/config.yml`과 함께 검토하세요. 프로젝트 메타데이터, 프런트엔드 명령, 대상 아키텍처, 패키지 내용, 에셋 및 서명 설정을 확인하세요. 비밀 정보는 환경 변수나 자격 증명 저장소에 보관하세요.

알려진 기본 제공 태스크는 네이티브 설정에 매핑할 수 있습니다. 인수가 없고 프로젝트에서 관리하는 스크립트를 호출하는 보수적인 수명 주기 태스크는 훅으로 변환할 수 있습니다. 그 밖의 도달 가능한 사용자 정의 태스크 동작은 차단 요인입니다. Wake가 이를 알리지 않고 누락하거나 대체 수단으로 Task를 통해 실행하지는 않습니다.

초안이 이미 있으면 마이그레이션 과정에서 검토한 편집 내용을 덮어쓰지 않습니다. 의도적으로 교체하거나 다시 생성하기 전에 사본을 보관하세요. 활성화 검사를 우회하려고 차단된 초안의 이름을 `wails.yaml`으로 변경하지 마세요. 지원되지 않는 레거시 동작을 줄이거나 교체한 다음 활성화 전에 분석을 다시 실행하세요. 아직 프로젝트를 표현할 수 없다면 레거시 빌드를 유지하고 지원되지 않는 부분을 보고하세요.

### 3. 명시적으로 활성화

초안을 검토하고 차단 요인을 해결한 후 다음을 실행하세요.

```sh
wails3 migrate --activate --dry-run
wails3 migrate --activate
```

첫 번째 명령은 활성화를 실제로 적용하지 않고 검사합니다. 두 번째 명령은 레거시 선언을 다시 검사하고 초안을 검증한 후 `wails.yaml`을 원자적으로 생성합니다. 활성화에 성공하면 비활성 `wails.migrated.yaml`이 제거됩니다. Taskfile, `build/config.yml`, 스크립트 및 에셋은 변경되지 않습니다. 이 시점부터 활성 매니페스트가 Wake 빌드를 제어합니다. 이전 파일은 보조 구성 소스가 아닙니다.

일부 오래된 프로젝트에는 최상위 `info:` 섹션이 있는 메타데이터 전용 `wails.yaml`이 이미 존재합니다. 이는 네이티브 Wake 매니페스트가 아니지만 활성화 대상 경로를 이미 차지하고 있습니다. 활성화하기 전에 해당 레거시 파일을 보존한 후 의도적으로 이동하세요. 마이그레이터가 대신 덮어쓰거나 이름을 변경해 주지 않습니다.

### 4. 마이그레이션된 애플리케이션 검증

```sh
wails3 config check
wails3 build
wails3 dev
```

사용자 정의 릴리스 동작을 포함하여 애플리케이션과 패키지 내용을 이전 빌드와 비교하세요. 프로젝트 테스트를 실행하세요. 초안에 `release` 프로필이 있다면 `wails3 config check release` 및 `wails3 build release`과 같이 마이그레이션된 각 프로필을 명시적으로 확인하세요.

이제 `wails3 setup`을 실행하여 전용 `setup` 프로필을 추가하거나 교체할 수 있습니다. 이 명령은 기존 `release` 프로필을 자동으로 선택하거나 편집하지 않습니다.

### 실험을 중단해야 하는 경우

`WAILS_EXP_USE_WAKE` 설정을 해제하면 옵트인이 비활성화되지만, 활성 `wails.yaml`이 있으면 여전히 자동 Taskfile 라우팅이 차단됩니다. YAML이 유효하지 않은 경우에도 오류와 함께 중단됩니다. 역방향 마이그레이션 명령은 없습니다.

이전 워크플로로 돌아가려면 활성 매니페스트가 없는 상태를 포함해 마이그레이션 전의 전체 프로젝트 리비전을 버전 관리에서 복원하고, 호환되는 CLI와 종속성을 사용하세요. 그 전에 필요한 새 소스 변경 사항을 보존하세요. 별도의 시험 브랜치를 유지하면 이러한 의도적인 복구가 훨씬 쉬워집니다.

## 문제 진단 및 피드백 제공

| 증상 | 먼저 확인할 사항 |
| --- | --- |
| 설정 시 일반 마법사가 표시됨 | 실행에 사용한 터미널에서 `WAILS_EXP_USE_WAKE`을 설정하고 `PATH`에 어떤 `wails3` 실행 파일이 있는지 확인하세요. |
| 설정 시 마이그레이션을 요구함 | 레거시 프로젝트 또는 레거시 구성을 사용하는 커뮤니티 템플릿을 열었습니다. 활성화하기 전에 마이그레이션을 검토하세요. |
| 저장된 빌드에서 누락된 도구를 보고함 | 저장은 의도한 구성을 기록합니다. **도구**로 돌아가 호스트 요구 사항을 충족한 후 다시 확인하세요. |
| 크로스 빌드한 실행 파일이 이 호스트에서 시작되지 않음 | 선택한 운영 체제와 아키텍처에서 실행하세요. 로컬 개발에는 호스트 대상을 사용하세요. |
| 사전 빌드 모드에서 바이너리를 찾지 못함 | 다중 대상 하위 디렉터리를 포함하여 [사전 빌드 파일 이름과 경로](/experimental/yaml-builds/#use-prebuilt-desktop-executables)를 확인하세요. |
| 매니페스트 변경 실패 | 해당 프로필에 대해 `wails3 config check`을 실행하고 필드 진단에 따르세요. Wake는 Taskfile로 대체 실행하지 않습니다. |

`wails3 build setup --plan --json`을 사용하여 빌드를 실행하기 전에 검사하세요.
`wails3 config check`은 구성을 검증하고, `wails3 eject`는 활성 매니페스트를 변경하지 않고 비활성 `wails.ejected.yaml` 스냅샷을 작성합니다.
명령 출력을 공유하기 전에 검토하세요. 프로젝트 경로와 자격 증명 위치를 통해 로컬 환경을 식별할 수 있습니다.

[Experiments Discussions](https://github.com/wailsapp/wails/discussions/categories/experiments)에서 피드백을 공유하거나 [재현 가능한 버그를 제출](https://github.com/wailsapp/wails/issues)하세요. CLI 및 프레임워크 리비전, 호스트 OS/아키텍처, 선택한 대상, 정확한 명령, Pure Go 선택 여부 및 관련 진단 결과를 포함하세요. 컴파일, 패키징, 서명 또는 애플리케이션 실행 중 어느 단계에서 실패했는지 명시하세요. 비밀 정보를 제거한 최소 매니페스트와 필요한 경우 `wails3 doctor` 출력을 포함하세요.

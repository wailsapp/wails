스트림 전송을 변경하는 모든 사람과 에이전트를 위한 참고 자료입니다. 사용자용 API는 [스트림](/guides/streams/)에 설명되어 있습니다. 이 페이지에서는 기반 메커니즘과 그 설계 근거를 다룹니다. 몇몇 결정은 어떤 문제를 방지하기 위한 것인지 알기 전까지는 임의로 정한 것처럼 보이기 때문입니다.

## 파일

| 파일 | 역할 |
| --- | --- |
| `v3/pkg/application/stream.go` | 공개 API, `StreamConn`, `streamSink`, 관리자와 해당 레지스트리 |
| `v3/pkg/application/stream_session.go` | 한 창의 한 페이지 로드: 송신 큐, 프레임 종류, 연결 테이블 |
| `v3/pkg/application/stream_transport.go` | 두 HTTP 엔드포인트, 바이너리 프레이밍, 청크 재조립, 런타임 프렐류드 |
| `v3/pkg/application/stream_server.go` | `-tags server` 전용: 실제 WebSocket 싱크 |
| `v3/pkg/application/stream_prelude_{server,desktop}.go` | 번들을 제공할 때 클라이언트 전송 방식을 선택 |
| `v3/internal/runtime/desktop/@wailsio/runtime/src/stream.ts` | `WebSocket` 형태의 클라이언트 |
| `v3/tests/stream-performance/` | 부하 테스트 하네스(`-upload`, `-reloads`, 시나리오 스윕) |

## 구조

Go→JS와 JS→Go는 서로 다른 메커니즘을 사용하며, 이러한 비대칭성이 설계의 핵심입니다.

```
Go                                  webview
──                                  ───────
Send() ─► per-window queue ─────────► GET  /wails/stream/poll   (held open)
                                      └─ one held request per window,
                                         carrying frames for every connection

Receive() ◄─ per-conn inbox ◄──────── POST /wails/stream/send   (one or more frames)
```

**Go→JS는 대기 상태로 유지되는 폴을 사용합니다.** 전달할 항목이 생길 때까지 요청이 대기합니다. 의도적으로 폴링 간격도 적응형 동작도 사용하지 않습니다. 프레임이 생길 때까지 서버가 요청을 유지하므로 전달 지연 시간은 이미 약 0이며, 클라이언트 측 간격은 지연 시간만 늘릴 수 있기 때문입니다. 응답을 전송하는 동안 도착한 프레임은 누적되어 다음 응답에 실립니다. 따라서 왕복 시간 자체가 일괄 처리 구간이 되며, 별도로 측정하지 않아도 부하가 증가함에 따라 이 구간이 넓어집니다. 측정 결과, 응답당 프레임 수는 100/s에서 1.0, 5000/s에서도 1.0, 20000/s에서 3.4였으며, 처리율이 높아질수록 p99 지연 시간은 *감소합니다*.

**JS→Go는 일반 POST를 사용합니다.** 동시 `fetch` 호출은 순서를 보장하지 않고 Go는 전송 순서대로 관찰할 수 있어야 하므로, 프로미스 체인을 사용해 연결별 전송을 직렬화합니다. 진행 중인 요청 뒤에 누적된 프레임은 다음 POST에서 일괄 전송됩니다. Go는 응답하기 *전에* 수락한 프레임 또는 배치 접두부를 연결의 수신함에 추가하므로, Go가 큐에 넣지 않은 바이트보다 클라이언트가 앞서 진행할 수 없습니다.

**창마다 하나의 폴만 진행하며 모든 연결을 다중화합니다.** 하나의 큐와 하나의 드레이너만 있고 첫 번째 전달 경로를 추월할 수 있는 두 번째 경로가 없으므로, 구조적으로 올바른 순서가 보장됩니다. 또한 실제 Chromium 네트워크 요청이 `http://wails.localhost`을 대상으로 이루어지는 Windows에서 HTTP/1.1의 호스트당 연결 6개 제한도 피할 수 있습니다.

## 이러한 결정을 내린 구체적인 이유

각 결정은 이벤트 전송 작업에서 얻은 교훈의 흔적입니다. 하나라도 제거하면 측정으로 확인된 버그가 다시 발생합니다.

**Go→JS 경로에서는 어떤 작업도 메인 스레드에 접근하지 않습니다.** `Send`은 뮤텍스 잠금 상태에서 항목을 추가한 후 반환합니다. 이전에는 앞선 goroutine의 emit이 아직 큐에 있는 동안 메인 스레드에서 이벤트를 내보내면 해당 eval이 인라인으로 실행되었습니다. 그 결과 세 플랫폼 모두에서 이벤트의 4.4%가 역순으로 처리되었습니다. 하나의 드레이너가 처리하는 단일 큐에서는 이런 문제가 발생할 수 없습니다.

**크기와 관계없이 어떤 작업도 `evaluateJavaScript`에 접근하지 않습니다.** eval 소스에 페이로드를 삽입하면 플랫폼별 임계점을 넘었을 때 호스트 메모리가 해제되지 않고 남습니다. 100 × 1 MB/sec에서 남는 메모리는 macOS에서 11.6GB, WebKitGTK에서 6.2GB입니다. 스트림은 이 경로를 전혀 사용하지 않으므로, 일정 바이트 전송률 스윕 결과가 모든 프레임 크기에서 평탄합니다.

**제어 데이터는 항상 헤더로 전송하며, 본문이나 쿼리 문자열로는 전송하지 않습니다.** WebKitGTK 6.0는 사용자 지정 URI 스킴의 POST 본문을 쿼리 매개변수로 전달할 수 있으며(바로 이 상황을 위해 `transport_http.go`에 대체 경로가 있음), WebView2는 본문 전달 용량을 약 2MB로 제한합니다.

**폴 응답은 JSON이 아니라 바이너리입니다.** 프레임은 `[]byte`입니다. JSON 엔벌로프 안에서 base64를 사용하면 모든 프레임에 33%의 오버헤드가 발생하고 UI 스레드에서 구문 분석까지 해야 합니다.

```
magic "WS1\0" | flags u8 | count u32 | count × ( connID u32 | kind u8 | len u32 | payload )
```

`kind`은 data / open / close / error입니다. 시퀀스 번호도 ack도 없습니다. WebSocket은 이전 프레임을 재전송하지 않으며, 연결이 끊기면 전송 중이던 항목은 손실됩니다. 이를 모방하는 편이 제한된 버퍼로는 항상 충족할 수 없는 커서를 구현하는 것보다 간단하고 정직합니다.

**요청을 대기 상태로 유지해도 안전합니다**. 모든 webview 요청에는 이미 별도의 goroutine이 할당되기 때문입니다. `assetserver_webview.go`의 `dispatchWorkers`은 바로 이 사례를 명시한 주석과 함께 0로 고정되어 있습니다. 해당 풀을 활성화하려면 먼저 요청 수명에 상한을 설정해야 합니다.

## 버퍼 상수

모두 `stream.go`에 있습니다. **이 값들은 옵션이 아니라 컴파일 시간 상수입니다**. `Options.Streams`도 없고 스트림별 설정도 없습니다. 변경하려면 파일을 편집해야 합니다.

| 상수 | 값 | 제한 대상 |
| --- | ---: | --- |
| `streamOutQueueBytes` | 8 MB | 수집을 기다리며 창별로 버퍼링된 바이트 |
| `streamOutQueueDepth` | 256 | 창별로 버퍼링된 프레임 |
| `streamOutQueueBytesGlobal` / `streamOutQueueDepthGlobal` | 256 MB / 8192 | 애플리케이션 전체에서 버퍼링된 송신 데이터 |
| `streamInQueueBytesGlobal` / `streamInQueueDepthGlobal` | 256 MB / 8192 | 애플리케이션 전체에서 `Receive`을 기다리는 수신 데이터 |
| `streamMaxConnections` | 256 | 한 세션의 활성 연결과 큐에 대기 중인 닫기 작업 |
| `streamMaxConnectionsGlobal` | 4096 | 애플리케이션 전체의 활성 연결 |
| `streamOutCloseDepthGlobal` | 4096 | 애플리케이션 전체에서 전달되지 않은 닫기 알림 |
| `streamMaxSessionsPerWindow` | 16 | 새 세대가 이전 세대를 대체해야 하기 전까지 한 창에서 유지할 수 있는 세션 |
| `streamMaxSessions` | 1024 | 애플리케이션 전체의 세션 |
| `streamOutControlDepth` / `streamOutControlDepthGlobal` | 256 / 4096 | 세션별 및 애플리케이션 전체에서 대기 중인 close 이외의 제어 프레임 |
| `streamMaxChunkSets` / `streamMaxChunkTotal` | 256 / 4096 | 세션별 미완료 업로드 수 및 단일 업로드의 파트 수 |
| `streamMaxChunkBytesGlobal` / `streamMaxChunkPartsGlobal` | 128 MB / 4096 | 애플리케이션 전체의 청크 페이로드 및 파트 메타데이터 |
| `streamMaxChunkIDLen` | 64바이트 | 클라이언트가 제공하는 단일 청크 세트 식별자 |
| `streamMaxResponseBytes` | 1 MB | 단일 폴 응답 |
| `streamHoldTimeout` | 20초 | 빈 폴이 대기하는 시간 |
| `streamSessionTTL` | 60초 | 이 시간 동안 폴이 없고 활성 연결도 없음 ⇒ 세션이 종료된 것으로 간주 |
| `streamSessionGrace` | 10분 | 활성 연결이 있는 상태에서 이 시간 동안 폴이 없음 ⇒ 세션이 종료된 것으로 간주 |
| `streamSessionSweep` | 20초 | 정리 작업이 종료된 세션을 확인하는 주기 |
| `streamMaxFrameBytes` | 64 MB | 어느 방향이든 단일 프레임 |
| `streamMaxNameLen` | 256바이트 | 등록되거나 요청된 단일 스트림 이름 |
| `streamInQueueDepth` / `streamInQueueBytes` | 256 / 8 MB | 수신되었지만 아직 `Receive`에서 가져가지 않은 프레임 |

### 값을 정하는 방법

**`streamOutQueueDepth`은 의도적으로 `eventQueueCapacity`(64)이 아닙니다.** 해당 상수는 eval 한 번에 하나씩 비우는 큐를 기준으로 측정했으며, 이 경우 깊이가 늘어나도 꼬리 지연 시간만 증가했습니다. 폴은 배치 단위로 큐를 비우므로 여기서의 깊이는 한 번의 왕복 시간 동안 생성되는 양을 수용해야 합니다. 5000프레임/초이고 왕복 시간이 5ms라면 약 25프레임입니다. 256이면 생산자를 정지시키지 않고도 버스트를 수용할 여유가 생깁니다.

실제로 중요한 제한은 **`streamOutQueueBytes`입니다**. 1 MB인 프레임 256개는 256 MB이기 때문입니다. 프런트엔드가 수집을 중단했을 때 이 제한이 호스트 메모리 사용량의 최종 안전장치가 됩니다.

여기서는 두 규칙이 서로 영향을 주며, 두 번째 규칙은 실수로 위반하기 쉽습니다.

- 깊이 제한과 바이트 제한은 <em>누적량</em>을 제한합니다.
- **빈 큐는 프레임 크기와 관계없이 항상 프레임 하나를 받아들입니다.** 바이트 제한을 무조건 적용하면 제한보다 큰 프레임은 전혀 보낼 수 없었습니다. 대기 조건이 절대로 참이 될 수 없으므로 `Send`은 영원히 차단되고 `TrySend`은 계속 가득 찬 상태로 보고했습니다. 프레임 크기를 호출자가 항상 선택할 수 있는 것은 아닙니다. `[]byte` 필드가 있는 구조체를 마샬링하면 그 결과 그대로의 크기가 됩니다.

**`streamMaxResponseBytes`은 Windows 때문에 존재합니다.** WebView2 응답 작성기는 본문 전체를 메모리에 누적한 뒤 `Finish`에서 한 번에 넘기므로, 응답 크기를 제한하지 않으면 그곳에서 메모리 할당도 무제한으로 늘어납니다. 이 값을 높여도 Windows 처리량은 *증가하지 않습니다*. 측정 결과 Windows의 병목은 응답당 비용이 아니라 바이트당 비용이었습니다. 프레임 크기를 훑어 측정하는 동안 초당 응답 수는 4배 차이가 났지만 MB/s는 약 90로 일정했습니다.

**인바운드 제한으로 인해 프런트엔드가 대기하게 됩니다.** 데스크톱에서는 `deliver`이 가득 찬 상태를 보고하고 엔드포인트가 `429`으로 응답하면, 클라이언트가 제한된 백오프를 적용해 동일한 프레임 또는 수락되지 않은 배치 접미부를 다시 시도합니다. 이렇게 하면 핸들러가 처리 속도를 따라잡는 동안 webview 요청 슬롯을 점유하지 않습니다. 서버 모드에서는 소켓 읽기 펌프가 대기하고 TCP가 백프레셔를 적용하도록 합니다. 이 제한이 없으면 `Receive` 호출이 느린 핸들러 때문에 호스트 메모리가 무제한으로 증가할 수 있습니다.

**제어 프레임은 데이터 제한을 우회하지만, 별도의 수명 주기 제한을 적용받습니다.** 백프레셔로 데이터 프레임이 유실되면 속도가 느려지는 데 그치지만, open ack가 유실되면 프런트엔드는 영원히 `CONNECTING` 상태에 머물고 close가 유실되면 종료된 연결이 여전히 활성 상태라고 인식합니다. 따라서 close 이외의 제어 프레임은 close가 사용하는 큐와 분리된 자체 제한 큐를 사용합니다. 그러므로 거부된 open이 몰려도 수락된 연결이 종료 사실을 알리는 데 필요한 용량을 소진할 수 없습니다. 또한 각 세션은 수락된 연결마다 close 슬롯 하나를 예약합니다. 해당 용량이 사용 중이면 새 open은 등록되기 전에 재시도 가능한 백프레셔 응답을 받습니다.

**세션별 제한에는 애플리케이션 전체에 적용되는 대응 제한도 있습니다.** 이런 제한이 없으면 허용된 모든 세션이나 연결이 각자의 로컬 허용량을 동시에 전부 점유할 수 있습니다. 따라서 아웃바운드 데이터와 인바운드 데이터는 데스크톱 및 서버 전송 계층 전체에서 서로 분리된 256 MiB / 8192프레임 예산을 공유합니다. 활성 연결에는 4096개 항목 예산이 있으며, 전달되지 않은 close 알림에도 같은 크기의 별도 예산이 있습니다. 공유 허용량에 도달하면 로컬 허용량에 도달했을 때와 동일하게 차단 방식의 `Send` 또는 비차단 방식의 `TrySend` 동작이 적용되며, 큐 비우기, 수신, close, 쓰기 실패 및 종료의 모든 경로에서 예약량을 반환합니다.

두 예산을 하나로 합쳐 연결이 자신의 close 프레임에 넘겨주도록 하지 않고 의도적으로 분리했습니다. 각 예약은 정확히 한 소유자만 해제합니다. 연결 슬롯은 한 번만 실행되는 `shutdown`에서 해제하고, close 프레임 슬롯은 해당 프레임을 폐기하는 동작, 즉 큐 비우기 또는 세션 해제에서 해제합니다. 두 주체 사이에서 소유권을 옮기려면 원자적으로 이전해야 합니다. 이전 리비전에서는 close가 연결 슬롯을 상속하도록 했는데, close를 시도한 시점과 그 시도가 실패한 시점 사이에 해제가 실행될 때마다 슬롯 하나가 영구적으로 누수되었습니다.

**Go 프레임은 소유권을 이전하고 JavaScript 프레임은 스냅샷을 만듭니다.** Go `Send`은 전송 계층에서 쓰기를 완료할 때까지 호출자의 슬라이스를 유지하므로, 호출이 성공한 뒤 호출자는 해당 저장 공간을 변경하거나 재사용해서는 안 됩니다. JavaScript `send()`은 반환 전에 변경 가능한 바이너리 입력을 복사하여 네이티브 WebSocket의 소유권 의미 체계와 일치시킵니다. 이 비대칭 규칙은 브라우저 대상 API의 동작을 예상하기 쉽게 유지하면서 Go 내부에서 전체 프레임을 한 번 더 복사하지 않도록 합니다.

**JavaScript 전송은 WebSocket 버퍼링 계약을 따릅니다.** `send()`은 차단할 수 없으므로, 네이티브 WebSocket의 처리 속도를 앞지를 수 있는 것처럼 애플리케이션은 데스크톱 요청 채널이 수락하는 속도보다 더 빠르게 데이터를 큐에 넣을 수 있습니다. `bufferedAmount`에는 해당 소켓이 유지하는 모든 바이트가 포함되며, 이 값이 호출자에게 백프레셔 신호가 됩니다. 호스트 측 큐에는 위의 제한이 독립적으로 계속 적용됩니다. 복구 불가능한 실패, 피어의 close 또는 로컬 `close()`가 발생하면 유지 중인 페이로드가 해제됩니다. 또한 로컬 close는 예약된 close 제어 프레임을 게시하기 전에 `429`에서 대기 중인 open 또는 데이터 요청을 취소하므로, 허용 단계나 수신자 측 백프레셔 때문에 소켓이 `CLOSING` 상태에 멈춰 있을 수 없습니다.

**청크 재조립에는 공유 호스트 메모리 할당량이 있습니다.** 각 세션은 최대 64 MiB의 단일 프레임을 조립할 수 있지만, 허용된 세션마다 이 할당량을 배수로 늘려서는 안 됩니다. 따라서 미완성 및 재시도 가능한 청크 집합은 128 MiB의 허용된 페이로드 예산을 공유합니다. 집합을 완성할 때는 그 구성 부분과 연속된 메모리로 조립된 프레임을 잠시 모두 유지하므로, 이 논리적 할당량을 두 배로 잡아도 256 MiB의 실효 메모리 상한 내에 머뭅니다. 유지되는 구성 부분은 항목 4096개짜리 메타데이터 할당량도 공유하므로, 작거나 비어 있는 청크 때문에 바이트 제한에 근접하지 않은 상태에서 맵과 슬라이스 관리 정보가 계속 늘어날 수 없습니다. 두 할당량 중 하나라도 초과하게 되는 요청에는 재시도 가능한 백프레셔가 적용됩니다. 전달, 거부, 만료 또는 세션 종료가 발생하면 바이트와 구성 부분 항목이 모두 공유 예산으로 반환됩니다.

**폴링은 복구 가능한 실패만 재시도합니다.** 네트워크 오류, 요청 시간 초과 응답(`408`), 얼리 데이터 응답(`425`), 백프레셔(`429`), 서버 오류(`5xx`)에는 250 ms부터 최대 5초까지 지수 백오프를 적용합니다. 그 밖의 `4xx` 응답은 프로토콜 또는 소유권 오류이므로 페이지의 Streams를 즉시 닫습니다. `410`은 폐기된 세션을 나타내는 정상 종료 신호입니다. 마지막 연결을 닫으면 진행 중인 폴이나 백오프 타이머가 중단되며, 이 종료 과정에서 연결이 열리면 대체 폴 루프 하나가 시작됩니다.

<strong>`streamSessionTTL`은 `streamHoldTimeout`</strong>보다 충분히 커야 합니다. 그렇지 않으면 자체 폴이 정상적으로 대기 중인 세션이 정리될 수 있습니다.

작은 메시지가 많은 워크로드에 맞춰 조정하는 경우에는 깊이 상한에 먼저 도달하고, 큰 페이로드의 경우에는 바이트 상한에 먼저 도달합니다. 일반적인 앱에서는 어느 쪽도 변경할 필요가 없습니다. macOS에서 기본값은 초당 634000 프레임과 초당 2100 MB의 처리량을 유지합니다.

## 연결 및 세션 수명 주기

<strong>세션</strong>은 한 창에서 한 번 페이지를 로드한 단위이며, 클라이언트가 생성한 ID(예: 런타임의 `clientId`)를 키로 사용합니다. 세션은 먼저 도착하는 요청에 의해 지연 생성됩니다. 플랫폼이 요청한 창을 식별할 수 없는 경우(`windowID == 0`)에도 세션 ID 수에는 전체 범위의 상한이 적용되지만, 세대는 의도적으로 비교하지 않습니다. 서로 관련 없는 세대 카운터를 사용하는 독립적인 브라우저 클라이언트의 세션일 수 있기 때문입니다. 이러한 세션은 서로를 대체하는 대신 닫기 또는 TTL을 통해 만료됩니다.

항목을 닫는 메커니즘은 감지 속도가 빠른 순서대로 세 가지입니다.

1. **한 창에서 더 새로운 세션 폴이 이전 세대를 대체합니다.** 페이지를 다시 로드하면 새 세션 ID가 부여되고 해당 창의 `sessionStorage`에 저장된 세대가 증가합니다. 같은 값은 `window.name`에도 복제됩니다. 이 값은 저장소가 비활성화된 경우에도 다시 로드한 뒤 유지되며, `performance.timeOrigin`(구형 엔진에서는 `Date.now()`)에 고정되므로 두 저장소를 모두 지워도 1부터 다시 시작하지 않습니다. 모든 요청에는 세션 ID와 세대가 포함됩니다. 폴은 더 낮은 페이지 세대만 폐기하므로, 서버 스케줄링 때문에 이전 페이지에서 지연된 요청이 그 페이지를 대체한 새 페이지보다 더 새로운 것으로 보일 수 없습니다. 정책에서 저장소와 `window.name`을 모두 차단하면 순서 결정은 페이지 시계로 대체되므로, 나중 페이지에 더 늦은 시간 원점이 부여되어야 합니다. 관리자는 창별로 폐기된 세대의 상한 표시를 유지하므로, 과거의 모든 세션 ID를 보관하지 않고도 이미 진행 중인 요청이 이전 페이지를 다시 생성하지 못하게 할 수 있습니다. 이전 세션의 연결은 즉시 닫힙니다.
2. <strong>창 삭제</strong>는 `eventPayloadStore.dropWindow`처럼 해당 창의 모든 세션을 제거합니다.
3. <strong>TTL 정리</strong>는 렌더러 충돌이나 시스템 절전처럼 그 밖의 모든 경우를 처리합니다.

앞의 두 메커니즘만 페이지 세대를 폐기합니다. TTL 정리는 폐기된 세대의 상한 표시를 높이지 않고 유휴 세션을 제거합니다. 페이지는 마지막 연결이 닫히면 폴링을 중지하지만, 아직 로드된 같은 페이지가 나중에 다른 스트림을 열 수 있어야 하기 때문입니다. 실제로 대체된 세대는 계속 차단됩니다. 이전 세션이 제거되기 전에 새 페이지의 폴이 상한 표시를 높이기 때문입니다.

**Apple WebView는 취소된 요청을 보고합니다.** macOS와 iOS에서는 WebKit의 `stopURLSchemeTask` 콜백이 일치하는 요청 컨텍스트를 취소하므로, 다른 곳으로 이동한 페이지에 속한 폴의 대기가 즉시 해제됩니다. 레지스트리는 유지된 네이티브 작업의 식별자를 키로 사용하며, 요청 처리 과정에서 작업을 닫으면 항목을 제거합니다. 현재 브리지에서 Linux와 Windows는 이에 상응하는 조기 중단 콜백을 아직 제공하지 않습니다. 따라서 이들 플랫폼에서는 대기 중인 요청이 유지 시간이 만료될 때까지 남습니다. 규칙 1에 따라 <em>연결</em>은 어느 경우든 신속하게 닫힙니다. 그 밖의 경우 취소는 Linux에서는 `EPIPE`으로 나타나고, Windows에서는 `Finish`에 이르러서야 나타납니다.

## 전송 방식 선택

`Stream(name)`은 `window._wails.streamFactory`을 참조합니다. 서버 빌드는 실제 `WebSocket`을 반환하는 팩토리를 설치하고, WebView 빌드는 이를 설정하지 않은 채 폴 클라이언트를 사용합니다.

생성된 바인딩이 모듈 범위에서 스트림을 생성하므로, 어떤 모듈 본문이 실행되기 전에 팩토리 설치를 **반드시** 완료해야 합니다. `custom.js`에서는 이 작업을 할 수 없습니다. `loadOptionalScript`이 HEAD 요청을 수행한 다음 `<script>` 태그를 추가하므로 시점이 지나치게 늦기 때문입니다. 대신 런타임 번들이 제공될 때 팩토리를 그 앞에 추가합니다(`stream_prelude_server.go`). ES 모듈 의존성은 이를 가져오는 모듈보다 먼저 평가되므로 이 방식은 구조적으로 동기적입니다.

세 번째 전송 방식을 추가한다면 프리루드에도 넣으십시오. `custom.js` 방식으로 되돌아가려 하지 마십시오.

## 개발 모드의 프런트엔드 패키지

생성된 프로젝트는 애셋 서버가 제공하는 번들 `/wails/runtime.js`가 아니라 <strong>npm</strong>에서 `@wailsio/runtime`을 가져옵니다. `wails3 dev`에서는 Vite가 이를 `node_modules`에서 해석하므로, 배포된 런타임을 기준으로 빌드한 앱에서는 브랜치에 추가한 클라이언트 측 기능을 볼 수 없습니다.

스트림이 아직 릴리스되지 않은 동안에는 테스트 앱이 이 작업 트리의 패키지를 사용하도록 지정하세요:

```bash
task v3:install-runtime -- ./path/to/your-app/frontend
```

그러면 먼저 `dist/`을 다시 빌드하므로 항상 최신 소스가 설치됩니다. 되돌리려면 같은 디렉터리에서  
`npm install @wailsio/runtime@latest`을 실행하세요.

클라이언트 빌드 출력은 <strong>두 개</strong>이며, 하나만 다시 빌드하고 다른 하나는 빌드하지 않기 쉽다는 점에 유의하세요. `task v3:runtime:build:package`은 npm 패키지의 `dist/`(앱의  
프런트엔드가 가져오는 항목)을 생성하고, `task v3:runtime:build:assets`은  
`bundledassets/runtime.js`(WebView가 애셋 서버에서 로드하는 항목)을 생성합니다.  
`stream.ts`을 변경하면 둘 다 빌드해야 합니다.

## 테스트

```bash
go test ./pkg/application/ -run TestStream -race        # protocol, ordering, backpressure
go test -tags server ./pkg/application/ -run TestServerMode
pnpm --dir v3/internal/runtime/desktop/@wailsio/runtime test
```

중요한 것은 순서 테스트입니다. 8개의 goroutine이 큐 잠금 아래에서 할당되는 카운터를 기준으로 동시에 전송하며, 드레인된 순서는 수락된 순서와 정확히 일치해야 합니다. 이 테스트가 실패한다면 단일 드레이너 불변 조건이 깨진 것입니다.

go run ./tests/stream-performance -duration 20s              # full sweep
go run ./tests/stream-performance -upload -duration 10s      # JS→Go matrix

Windows에서는 대화형 콘솔 세션에서 실행해야 합니다. 일반 SSH 호출은 세션 0에서 빈 출력만 남기고 종료됩니다. 또한 `C:\Users\<user>`에는 소유자만 접근할 수 있도록 ACL이 설정되어 있으므로, 바이너리는 SSH 계정과 콘솔 계정 모두 읽을 수 있는 위치에 배치해야 합니다.

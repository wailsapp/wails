Потоки предоставляют именованный упорядоченный двунаправленный канал передачи байтов между Go и фронтендом с той же моделью программирования, что и WebSocket, — **без привязки к TCP-порту**.

WebSocket не может работать поверх пользовательской схемы URL, поэтому единственный способ использовать его внутри webview — запустить настоящий HTTP-сервер, прослушивающий порт. В настольном приложении это означает открытый локальный порт, доступный любому другому процессу на компьютере. Для безопасности требуются проверка источника и токен, а сам порт виден всем межсетевым экранам и средствам защиты конечных точек, которыми пользуются ваши пользователи. Потоки позволяют избежать всего этого: они работают через уже используемый приложением сервер ресурсов, который уже привязан к источнику.

Переносите существующую реализацию WebSocket? Следуйте руководству [«Переход с WebSocket на потоки»](/guides/streams-from-websockets/) — оно рассчитано на пошаговое механическое выполнение и начинается с трёх различий, из-за которых возникают незаметные сбои.

## Быстрый старт

Объявите поток в Go. Обработчик запускается один раз для каждого соединения в отдельной горутине:

```go
app.HandleStream("telemetry", func(c *application.StreamConn) {
    defer c.Close()

    for {
        frame, err := c.Receive()   // blocks until a frame arrives
        if err != nil {
            return                  // page reloaded, window closed, or app shutting down
        }
        _ = c.Send(process(frame))  // blocks like a socket write
    }
})
```

Подключитесь из фронтенда по имени. Объект реализует интерфейс `WebSocket`:

```js
import { Stream } from "@wailsio/runtime";

const s = Stream("telemetry");
s.onopen    = () => s.send(new TextEncoder().encode("hello"));
s.onmessage = (ev) => console.log(new Uint8Array(ev.data));
s.onclose   = (ev) => console.log("closed", ev.code);
```

`Stream(name)` **синхронно** возвращает объект с `readyState === CONNECTING`, точно как `new WebSocket(url)`, поэтому объект можно создать в области видимости модуля:

```js
export const Telemetry = Stream("telemetry");
```

## Кадры состоят из байтов

Каждый кадр представлен как `[]byte` в Go и как `ArrayBuffer` в JavaScript. Никакая схема или кодировка не навязывается — используйте JSON, protobuf, CBOR или необработанные байты по своему усмотрению.

Кадр — это **сообщение, а не поток байтов**: он либо доставляется целиком, либо не доставляется вовсе, причём его длина передаётся вместе с ним. Ни одной из сторон не нужно заранее знать размер, поэтому структура с полем `[]byte` сериализуется в данные произвольного размера, которые затем отправляются одним кадром.

## Отправка объектов

Кадры состоят из байтов, но обычно работать непосредственно с байтами неудобно. Обе стороны предоставляют согласованные вспомогательные средства для JSON:

```go
type Reading struct {
    Sensor string  `json:"sensor"`
    Value  float64 `json:"value"`
}

app.HandleStream("telemetry", func(c *application.StreamConn) {
    defer c.Close()

    var cmd map[string]any
    if err := c.ReceiveJSON(&cmd); err != nil {
        return
    }

    _ = c.SendJSON(Reading{Sensor: "cpu", Value: 42.5})
})
```

```js
import { JSONStream } from "@wailsio/runtime";

const s = JSONStream("telemetry");
s.onopen    = () => s.send({ subscribe: "cpu" });   // stringified for you
s.onmessage = (ev) => console.log(ev.data.value);   // already an object
```

`JSONStream` — тот же объект, что и `Stream`, только кодирование выполняется на границе. Отдельного протокола нет, и обработчик Go не видит разницы. Кадр с недопустимым JSON вызывает событие `error` и отбрасывается, а соединение остаётся открытым.

Используйте обычный `Stream`, когда нужны байты: для protobuf, CBOR, двоичных форматов и любых других случаев, в которых вы предпочитаете выполнять кодирование самостоятельно.

## API Go

```go
// Register a handler. Runs once per connection, on its own goroutine.
func (a *App) HandleStream(name string, handler StreamHandler)

// The connection.
func (c *StreamConn) Send(data []byte) error        // blocks when the buffer is full
func (c *StreamConn) TrySend(data []byte) error     // ErrStreamFull instead of blocking
func (c *StreamConn) Receive() ([]byte, error)      // blocks until a frame or close
func (c *StreamConn) SendJSON(v any) error          // marshal and send as one frame
func (c *StreamConn) ReceiveJSON(v any) error       // receive one frame and unmarshal
func (c *StreamConn) Context() context.Context      // cancelled on disconnect
func (c *StreamConn) Window() Window                // nil in server mode
func (c *StreamConn) Name() string
func (c *StreamConn) Close() error
```

**Время жизни горутины обработчика совпадает со временем жизни соединения.** Возврат из обработчика закрывает соединение, поэтому блокируйтесь на `Receive` (или на `c.Context()`), пока соединение должно оставаться открытым. Такая структура соответствует обработчику WebSocket с `gorilla`/`coder`.

Возможные ошибки: `ErrStreamClosed` (другая сторона отключилась) и `ErrStreamFull` (только из `TrySend`).

## API JavaScript

`Stream(name)` возвращает объект, реализующий полезное подмножество `WebSocket`:

| поддерживается | примечания |
| --- | --- |
| `readyState` + `CONNECTING`/`OPEN`/`CLOSING`/`CLOSED` |  |
| `onopen`, `onmessage`, `onclose`, `onerror` | а также `addEventListener` |
| `send(data)` | строка, `ArrayBuffer`, типизированный массив или `Blob` — сведения о владении см. ниже |
| `JSONStream(name)` | тот же объект; объекты на входе и выходе |
| `close(code, reason)` |  |
| `binaryType` | по умолчанию **имеет значение `"arraybuffer"`**, а не `"blob"` |
| `bufferedAmount` | байты, поставленные `send` в очередь, но ещё не достигшие Go |
| `protocol`, `extensions` | всегда `""` — согласование не выполняется |

Значение `binaryType` по умолчанию — единственное намеренное отличие от стандарта: кадры всегда двоичные, а `Blob` потребовал бы дополнительного асинхронного перехода для чтения каждого сообщения. Если требуется стандартное поведение, задайте значение `"blob"`.

Допускается множество соединений с потоком под одним именем из одного или нескольких окон. Каждое соединение получает собственный `StreamConn` и отдельную горутину обработчика.

**Правила владения буфером зависят от направления передачи.** JavaScript `send()` синхронно создаёт моментальные копии изменяемых двоичных входных данных в соответствии с поведением нативного WebSocket, поэтому вызывающий код может повторно использовать их сразу после возврата из `send()`. Go `Send` передаёт владение срезом транспортному уровню и не копирует его; после успешного вызова не изменяйте и не используйте этот срез повторно. Если производителю нужно повторно использовать его хранилище, передайте новый срез.

## Жизненный цикл

Поток ведёт себя как сокет, и события, закрывающие сокет, также закрывают поток:

| событие | что происходит |
| --- | --- |
| Перезагрузка страницы или переход на другую страницу | соединение закрывается, `Receive` обработчика возвращает ошибку, новая страница устанавливает новое соединение |
| `window.close()` / уничтожение окна | закрываются все соединения этого окна |
| `s.close()` в JS | `Receive` обработчика возвращает `ErrStreamClosed` |
| Возврат из обработчика | фронтенд получает `onclose` |
| Завершение работы приложения | контекст каждого соединения отменяется |

**Автоматического переподключения нет**, как и у `WebSocket`. Если оно требуется приложению, существующая логика переподключения WebSocket будет работать без изменений — заново создавайте поток в `onclose`.

## Обратное давление

`Send` блокируется, если фронтенд не успевает обрабатывать данные, подобно тому как запись в сокет блокируется при заполненном буфере отправки. Используйте `TrySend`, если предпочитаете отбрасывать данные, а не ждать:

```go
if err := c.TrySend(sample); errors.Is(err, application.ErrStreamFull) {
    // frontend is behind — skip this sample rather than stalling the producer
}
```

Приостановленный фронтенд — из-за точки останова в инструментах разработчика, скрытого окна или App Nap — перестаёт забирать данные, и после достижения предела буфера производитель блокируется. Это сделано намеренно: так потребление памяти остаётся ограниченным, вместо того чтобы непрочитанный поток рос без ограничений.

## Серверный режим

При сборке с `-tags server` транспорт заменяется на **настоящий WebSocket** по адресу `/wails/stream/ws`, поскольку в серверном режиме уже есть прослушивающий сокет, на котором можно повысить уровень соединения. Обработчик Go и код фронтенда остаются прежними — в приложении ничего не меняется. Среда выполнения выбирает транспорт до запуска кода любого модуля. По умолчанию соединения WebSocket разрешены только с того же источника. Если сервер намеренно размещает фронтенд на другом доверенном источнике, этот узел можно добавить с помощью `ServerOptions.WebSocketOriginPatterns`.

## Производительность

При измерении с `v3/tests/stream-performance` без ограничения скорости на примерно 41 миллионах кадров зафиксировано 0 потерянных и 0 переставленных кадров:

|  | Пиковая скорость Go→JS | Пиковая скорость JS→Go |
| --- | ---: | ---: |
| macOS / WebKit-Cocoa | **3117 МБ/с** | 2793 МБ/с |
| Linux / WebKitGTK | 226 МБ/с | 727 МБ/с |
| Windows / WebView2 | 100 МБ/с | 99 МБ/с |

Характеристики важнее пиковых значений:

- **Для небольших кадров направление Go→JS намного быстрее**: 634000 кадров/с в macOS против примерно 6200 кадров/с в обратном направлении. В один ответ объединяется до 256 кадров; при передаче JS→Go также пакетируются кадры, накопившиеся за выполняющимся запросом, но каждое соединение по-прежнему последовательно обрабатывает собственную цепочку POST-запросов. Если вы отправляете много небольших сообщений, выбирайте направление Go→JS либо перед отправкой в Go объединяйте их в пакеты на уровне приложения.
- **В Windows оптимальный размер отправляемых данных — 512 КБ.** Кадры большего размера разбиваются на несколько запросов, а передача кадра размером 4 МБ по результатам измерений выполняется *медленнее*, чем кадра размером 512 КБ.
- **Задержка мала и остаётся малой**: примерно 1–2 мс для p99 в macOS; с ростом нагрузки она не ухудшается — при 20000 кадров/с измеренное значение p99 оказалось *ниже*, чем при 100 кадров/с.

Полные таблицы по платформам и методика приведены в отчёте об измерениях, прилагаемом к этой функции.

## Ограничения

|  | ограничение | что происходит при его достижении |
| --- | --- | --- |
| Буфер на одно окно в ожидании получения | 8 МБ или 256 кадров — в зависимости от того, какой предел будет достигнут раньше | `Send` блокируется; `TrySend` возвращает `ErrStreamFull` |
| Буфер во всём приложении в ожидании получения/записи | 256 МБ или 8192 кадра данных | то же самое |
| Получено в одном соединении в ожидании `Receive` | 8 МБ или 256 кадров | среда выполнения повторяет `send()` фронтенда, пока обработчик не наверстает отставание |
| Получено во всём приложении в ожидании `Receive` | 256 МБ или 8192 кадра | то же самое |
| Соединений на одно окно | 256 | среда выполнения повторяет попытку открытия, пока не освободится место |
| Активных соединений во всём приложении | 4096 | то же самое |
| Сеансов на одно окно | 16 | перезагрузка заменяет собственный предыдущий сеанс; в остальных случаях попытка открытия повторяется |
| Один кадр в любом направлении | 64 МБ | Go возвращает `ErrStreamTooLarge`; при отправке из JS поток выдаёт `error` и закрывается |
| Имя потока | 256 байт UTF-8 | открытие отклоняется, и поток выдаёт `error` |
| Удержание ожидающего опроса | 20 с | опрос возвращает пустой результат, и среда выполнения немедленно отправляет его снова |

Ни одно из перечисленных выше ограничений не приводит к незаметной потере данных. Две строки с текстом *среда выполнения повторяет* описывают обычное обратное давление: среда выполнения удерживает кадр и повторяет попытку после короткой задержки, поэтому ваш код получает более медленный поток, а не ошибку. Строки, в которых выдаётся `error`, относятся к ошибкам программирования, а не к нагрузке; такие ошибки сообщаются явно, а не маскируются.

Сейчас это константы времени компиляции, а не параметры. Если их необходимо изменить, обратитесь к руководству по внутреннему устройству.

## Когда не следует использовать поток

- **Для взаимодействия по схеме «запрос — ответ» используйте привязки.** Потоки предназначены для непрерывных или незапрошенных данных; вызов, возвращающий значение, проще реализовать как привязанный метод.
- **Для событий приложения используйте `Emit`/`On`.** События рассылаются всем слушателям и обрабатываются отдельной, проверенной временем системой. Потоки обеспечивают связь «точка — точка».
- **Недоступно для окон `InitialHTML`.** Они загружаются с `origin === "null"`, поэтому вообще не могут обращаться к серверу ресурсов.

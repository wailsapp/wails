Справочный материал для всех — людей и агентов, — кто изменяет транспорт потоков. Пользовательский API описан в разделе [«Потоки»](/guides/streams/); на этой странице рассматриваются лежащие в его основе механизмы и обоснование их устройства, поскольку некоторые решения кажутся произвольными, пока не станет понятно, каких проблем они позволяют избежать.

| файл | назначение |

## Архитектура

Для Go→JS и JS→Go используются разные механизмы, и эта асимметрия лежит в основе всей архитектуры.

```
Go                                  webview
──                                  ───────
Send() ─► per-window queue ─────────► GET  /wails/stream/poll   (held open)
                                      └─ one held request per window,
                                         carrying frames for every connection

Receive() ◄─ per-conn inbox ◄──────── POST /wails/stream/send   (one or more frames)
```

**Для Go→JS используется удерживаемый опрос.** Запрос приостанавливается до появления данных для доставки. Интервал опроса и какая-либо адаптивность намеренно отсутствуют: сервер удерживает запрос до появления кадра, поэтому задержка доставки уже составляет около 0, а любой интервал на стороне клиента мог бы её только увеличить. Кадры, поступившие во время передачи ответа, накапливаются и передаются со следующим ответом, поэтому само время кругового обмена становится окном пакетирования: по мере роста нагрузки оно расширяется без каких-либо измерений. Результаты измерений: 1.0 кадров на ответ при 100/с, по-прежнему 1.0 при 5000/с и 3.4 при 20000/с; при этом с ростом частоты задержка p99 *снижается*.

**Для JS→Go используются обычные POST-запросы.** Отправки сериализуются отдельно для каждого подключения с помощью цепочки промисов, поскольку параллельные вызовы `fetch` не сохраняют порядок, а Go предполагает, что порядок отправки совпадает с порядком наблюдения. Кадры, накопившиеся за выполняющимся запросом, объединяются в пакет для следующего POST-запроса. Go добавляет принятый кадр или префикс пакета во входящую очередь подключения *до отправки ответа*, поэтому клиент не может перейти за пределы байтов, ещё не поставленных Go в очередь.

**В каждый момент для одного окна выполняется один опрос, мультиплексирующий все подключения.** Благодаря этому правильный порядок гарантируется самой архитектурой: одна очередь, один обработчик и отсутствие второго пути доставки, который мог бы обогнать первый. Это также позволяет обойти ограничение HTTP/1.1 в шесть подключений на хост в Windows, где они представляют собой настоящие сетевые запросы Chromium к `http://wails.localhost`.

## Почему приняты именно эти решения

Каждое из этих решений — следствие проблем, выявленных при работе над транспортом событий. Отказ от любого из них вновь приводит к воспроизводимой ошибке.

**Ничто в тракте Go→JS не обращается к главному потоку.** `Send` добавляет данные под мьютексом и возвращает управление. Раньше события выполняли свой eval непосредственно при отправке из главного потока, пока более ранняя отправка из горутины ещё находилась в очереди: на всех трёх платформах порядок менялся у 4.4% событий. При одной очереди и одном обработчике это невозможно.

**Ничто не обращается к `evaluateJavaScript` независимо от размера.** Встраивание полезной нагрузки в исходный код eval удерживает память хоста после превышения зависящего от платформы порога: 11.6 ГБ в macOS и 6.2 ГБ в WebKitGTK при 100 × 1 МБ/с. Потоки никогда не используют этот механизм, поэтому график прогона с постоянной скоростью передачи байтов остаётся ровным при любом размере кадра.

**Управляющие данные передаются в заголовках, но никогда — в теле или строке запроса.** В пользовательских схемах URI WebKitGTK 6.0 может передавать тела POST-запросов как параметры запроса (именно для этого в `transport_http.go` предусмотрен резервный механизм), а WebView2 ограничивает размер передаваемого тела примерно 2 МБ.

**Ответ на опрос имеет двоичный формат, а не JSON.** Кадры имеют формат `[]byte`; кодирование base64 внутри оболочки JSON увеличивало бы размер каждого кадра на 33% и дополнительно требовало бы разбора в потоке пользовательского интерфейса.

```
magic "WS1\0" | flags u8 | count u32 | count × ( connID u32 | kind u8 | len u32 | payload )
```

`kind` — это data / open / close / error. Порядкового номера и подтверждения нет: WebSocket не воспроизводит данные повторно, а при разрыве подключения теряются передававшиеся в этот момент данные. Имитировать такое поведение проще и честнее, чем использовать курсор, требования которого ограниченный буфер не всегда мог бы выполнить.

**Удерживать запрос безопасно**, поскольку для каждого запроса webview уже создаётся отдельная горутина. Значение `dispatchWorkers` в `assetserver_webview.go` зафиксировано на 0, а в комментарии прямо указан этот сценарий; прежде чем включать этот пул, потребуется ограничить время жизни запроса.

## Константы буферов

Все они находятся в `stream.go`. **Это константы времени компиляции, а не параметры**: нет ни `Options.Streams`, ни отдельной настройки для каждого потока. Чтобы изменить их, необходимо отредактировать файл.

| константа | значение | что ограничивает |
| --- | ---: | --- |
| `streamOutQueueBytes` | 8 МБ | число байтов, буферизуемых в одном окне в ожидании получения |
| `streamOutQueueDepth` | 256 | число кадров, буферизуемых в одном окне |
| `streamOutQueueBytesGlobal` / `streamOutQueueDepthGlobal` | 256 МБ / 8192 | исходящие данные, буферизуемые во всём приложении |
| `streamInQueueBytesGlobal` / `streamInQueueDepthGlobal` | 256 МБ / 8192 | входящие данные во всём приложении, ожидающие `Receive` |
| `streamMaxConnections` | 256 | активные подключения и поставленные в очередь закрытия в одном сеансе |
| `streamMaxConnectionsGlobal` | 4096 | активные подключения во всём приложении |
| `streamOutCloseDepthGlobal` | 4096 | недоставленные уведомления о закрытии во всём приложении |
| `streamMaxSessionsPerWindow` | 16 | число сеансов, которые может хранить одно окно, прежде чем более новое поколение должно заменить более старое |
| `streamMaxSessions` | 1024 | сеансы во всём приложении |
| `streamOutControlDepth` / `streamOutControlDepthGlobal` | 256 / 4096 | поставленные в очередь управляющие кадры, кроме закрывающих, для сеанса и всего приложения |
| `streamMaxChunkSets` / `streamMaxChunkTotal` | 256 / 4096 | незавершённые выгрузки для одного сеанса и части в одной выгрузке |
| `streamMaxChunkBytesGlobal` / `streamMaxChunkPartsGlobal` | 128 МБ / 4096 | полезная нагрузка фрагментов и метаданные частей во всём приложении |
| `streamMaxChunkIDLen` | 64 байт | один предоставленный клиентом идентификатор набора фрагментов |
| `streamMaxResponseBytes` | 1 МБ | один ответ на опрос |
| `streamHoldTimeout` | 20 с | как долго пустой опрос остаётся в ожидании |
| `streamSessionTTL` | 60 с | если опросов не было в течение этого времени и нет активных соединений ⇒ сеанс считается завершённым |
| `streamSessionGrace` | 10 мин | если опросов не было в течение этого времени при наличии активных соединений ⇒ сеанс считается завершённым |
| `streamSessionSweep` | 20 с | как часто очиститель ищет завершённые сеансы |
| `streamMaxFrameBytes` | 64 МБ | один кадр в любом направлении |
| `streamMaxNameLen` | 256 байт | одно зарегистрированное или запрошенное имя потока |
| `streamInQueueDepth` / `streamInQueueBytes` | 256 / 8 МБ | полученные кадры, которые ещё не забрал `Receive` |

### Как выбирать значения

**`streamOutQueueDepth` намеренно не равна `eventQueueCapacity` (64).** Эта константа была определена измерениями для очереди, из которой за раз извлекался один eval: увеличение глубины давало лишь дополнительную задержку хвоста. Опрос извлекает данные пакетами, поэтому глубина здесь должна покрывать объём, создаваемый за один цикл обмена: при 5000 кадрах/с и длительности цикла 5 мс это около 25 кадров. Значение 256 оставляет запас для всплеска, не приостанавливая производителя.

На практике важен именно предел **`streamOutQueueBytes`**, поскольку 256 кадров по 1 МБ дают 256 МБ. Это предохранительный предел для памяти хоста на случай, если фронтенд перестанет извлекать данные.

Здесь взаимодействуют два правила, причём второе легко случайно нарушить:

- Ограничения глубины и количества байтов сдерживают *накопление*.
- **Пустая очередь всегда принимает один кадр независимо от его размера.** Безусловное применение ограничения по байтам делало отправку кадра, превышающего этот предел, вообще невозможной: условие ожидания никогда не могло выполниться, поэтому `Send` блокировался навсегда, а `TrySend` постоянно сообщал о заполнении. Размер кадра не всегда выбирает вызывающая сторона: структура с полем `[]byte` при сериализации получает тот размер, который получается.

**`streamMaxResponseBytes` существует из-за Windows.** Средство записи ответов WebView2 накапливает всё тело в памяти и передаёт его только в `Finish`, поэтому неограниченный ответ приводит там к неограниченному выделению памяти. Повышение этого значения *не* увеличивает пропускную способность в Windows: измерения показывают, что узкое место в Windows связано с каждым байтом, а не с каждым ответом — в ходе перебора размеров кадров число ответов в секунду изменяется в 4 раз, тогда как скорость в МБ/с остаётся на уровне около 90.

**Именно ограничение входящих данных заставляет фронтенд ждать.** В настольном режиме `deliver` сообщает о заполнении, конечная точка отвечает `429`, а клиент с ограниченной задержкой между повторными попытками повторяет отправку того же кадра или непринятой оставшейся части пакета. Это позволяет не занимать слот запроса webview, пока обработчик наверстывает отставание. В серверном режиме цикл чтения из сокета ожидает, позволяя TCP создавать обратное давление. Без этого ограничения обработчик, который медленно вызывает `Receive`, мог бы неограниченно увеличивать потребление памяти хоста.

**Управляющие кадры обходят ограничения для данных, но имеют собственные ограничения жизненного цикла.** Потеря кадра данных при обратном давлении лишь замедляет работу; потеря подтверждения открытия навсегда оставляет фронтенд в состоянии `CONNECTING`, а потеря уведомления о закрытии заставляет его считать завершённое соединение активным. Поэтому управляющие кадры, кроме закрывающих, помещаются в отдельную ограниченную очередь, не связанную с очередью закрывающих кадров: всплеск отклонённых открытий не может исчерпать ёмкость, необходимую принятому соединению для сообщения о своём завершении. Кроме того, каждый сеанс резервирует по одному слоту закрытия для каждого принятого соединения. Если эта ёмкость занята, новое открытие получает допускающее повторную попытку обратное давление ещё до регистрации.

**Ограничения для отдельных сеансов также имеют аналоги на уровне всего приложения.** Без них каждый допущенный сеанс или каждое соединение могли бы одновременно удерживать весь свой локальный лимит. Поэтому исходящие и входящие данные используют отдельные общие бюджеты в 256 МиБ / 8192 кадров для настольного и серверного транспортов. Для активных соединений предусмотрен бюджет на 4096 записей, а для недоставленных уведомлений о закрытии — второй бюджет того же размера. Исчерпание общего лимита приводит к тому же поведению — блокирующему `Send` или неблокирующему `TrySend`, — что и исчерпание локального лимита; при каждом извлечении, получении, закрытии, сбое записи и завершении работы резерв возвращается.

Эти два бюджета намеренно разделены, а не объединены в один лимит, который соединение передаёт собственному закрывающему кадру. Каждый резерв освобождается ровно одним владельцем: слот соединения — функцией `shutdown`, которая выполняется один раз, а слот закрывающего кадра — тем, кто удаляет этот кадр: операцией извлечения или уничтожением его сеанса. Передачу владения между двумя сторонами нужно выполнять атомарно. В более ранней редакции закрывающий кадр наследовал слот соединения, и этот слот навсегда утекал всякий раз, когда уничтожение выполнялось между попыткой закрытия и сбоем этой попытки.

**Кадры Go передают владение, а для кадров JavaScript создаются моментальные копии.** Go `Send` сохраняет срез вызывающей стороны до его записи транспортом, поэтому после успешного вызова вызывающая сторона не должна изменять или повторно использовать эту область памяти. JavaScript `send()` перед возвратом копирует изменяемые двоичные входные данные в соответствии с семантикой владения нативного WebSocket. Это асимметричное правило позволяет избежать второй полной копии кадра внутри Go, сохраняя при этом ожидаемое поведение API для браузера.

**Отправка из JavaScript следует контракту буферизации WebSocket.** `send()` не может блокироваться, поэтому приложение способно ставить данные в очередь быстрее, чем канал запросов настольного режима их принимает, — так же, как оно может обогнать нативный WebSocket. `bufferedAmount` включает каждый байт, удерживаемый этим сокетом, и служит для вызывающей стороны сигналом обратного давления; очереди на стороне хоста независимо ограничиваются указанными выше пределами. Неустранимый сбой, закрытие другой стороной или локальный `close()` освобождает удерживаемую полезную нагрузку. Локальное закрытие также отменяет запрос открытия или передачи данных, ожидающий `429`, прежде чем отправить зарезервированную управляющую команду закрытия, поэтому обратное давление при допуске или на стороне получателя не может оставить сокет зависшим в состоянии `CLOSING`.

**Для повторной сборки фрагментов предусмотрен общий лимит памяти хоста.** Каждый сеанс может собирать один кадр размером до 64 МиБ, но этот лимит нельзя умножать на количество всех допущенных сеансов. Поэтому неполные наборы фрагментов и наборы, обработку которых можно повторить, совместно используют бюджет допущенной полезной нагрузки в 128 МиБ. При завершении сборки набора в памяти кратковременно остаются и его части, и собранный из них непрерывный кадр, поэтому даже удвоенный логический лимит не превышает фактический предел памяти в 256 МиБ. Для сохраняемых частей также действует общий лимит метаданных в 4096 записей, поэтому крошечные или пустые фрагменты не могут бесконтрольно увеличивать объём карт и служебных данных срезов, не приближаясь к ограничению по байтам. Запрос, который привёл бы к превышению любого из этих лимитов, получает сигнал обратного давления с возможностью повторной попытки; доставка, отклонение, истечение срока действия или завершение сеанса возвращает и байты, и записи частей в общие бюджеты.

**Опрос повторяется только после устранимых сбоев.** При сетевых ошибках, ответах об истечении времени ожидания запроса (`408`), ответах о слишком ранних данных (`425`), обратном давлении (`429`) и серверных ошибках (`5xx`) применяется экспоненциальная задержка от 250 мс до 5 секунд. Другие ответы `4xx` означают нарушение протокола или владения и немедленно закрывают Streams страницы; `410` служит штатным завершающим сигналом для выведенного из эксплуатации сеанса. Закрытие последнего соединения прерывает выполняющийся опрос или таймер задержки, а соединение, открытое во время этого завершения, запускает один замещающий цикл опроса.

**`streamSessionTTL` должен оставаться с достаточным запасом больше `streamHoldTimeout`**, иначе сеанс будет удалён, пока его собственный опрос правомерно находится в ожидании.

Если вы настраиваете систему для нагрузки из множества небольших сообщений, первым срабатывает ограничение глубины; для крупных полезных нагрузок — ограничение по байтам. В типичном приложении менять их не требуется: в macOS значения по умолчанию обеспечивают 634000 кадров/с и 2100 МБ/с.

## Жизненный цикл соединений и сеансов

**Сеанс** — это одна загрузка страницы в одном окне; его ключом служит идентификатор, созданный клиентом (например, `clientId` среды выполнения). Сеансы создаются отложенно тем запросом, который поступит первым. Если платформа не может определить окно, отправившее запрос (`windowID == 0`), количество идентификаторов сеансов всё равно ограничивается глобально, но их поколения намеренно не сравниваются: они могут принадлежать независимым браузерным клиентам с несвязанными счётчиками поколений. Срок действия таких сеансов истекает при закрытии или по TTL; они не вытесняют друг друга.

Объекты закрываются тремя механизмами, перечисленными в порядке скорости обнаружения:

1. **Опрос более нового сеанса окна вытесняет предыдущие поколения.** При перезагрузке страница получает новый идентификатор сеанса, а поколение, хранящееся в `sessionStorage` этого окна, увеличивается. То же значение дублируется в `window.name`, который сохраняется при перезагрузках, когда хранилище отключено, и привязывается к `performance.timeOrigin` (или к `Date.now()` в старых движках), чтобы после очистки обоих хранилищ отсчёт не начинался заново с единицы. Каждый запрос содержит идентификатор и поколение сеанса. Опрос выводит из эксплуатации только более ранние поколения страницы, поэтому из-за планирования на сервере задержанный запрос от предыдущей страницы не может выглядеть новее заменившей её страницы. Если политика блокирует и хранилище, и `window.name`, порядок определяется по часам страницы и потому зависит от того, получают ли более поздние страницы более позднюю точку отсчёта времени. Менеджер хранит для каждого окна порог выведенных из эксплуатации поколений, поэтому уже выполняющийся запрос не может воссоздать старую страницу и при этом не требуется хранить идентификаторы всех предыдущих сеансов. Соединения предыдущего сеанса закрываются немедленно.
2. **Уничтожение окна** удаляет все сеансы этого окна, как и `eventPayloadStore.dropWindow`.
3. **Удаление по TTL** охватывает все остальные случаи, например аварийное завершение процесса визуализации или переход компьютера в спящий режим.

Только первые два механизма выводят поколение страницы из эксплуатации. Очистка по TTL удаляет бездействующий сеанс, не продвигая порог выведенных из эксплуатации поколений: страница прекращает опрос после закрытия последнего соединения, но эта же всё ещё загруженная страница должна иметь возможность позднее открыть другой поток. Действительно вытесненное поколение остаётся заблокированным, поскольку опрос новой страницы продвигает порог до удаления старого сеанса.

**Apple WebView сообщает об отменённых запросах.** В macOS и iOS обратный вызов WebKit `stopURLSchemeTask` отменяет контекст соответствующего запроса, поэтому опрос страницы, с которой уже выполнен переход, немедленно разблокируется. Реестр использует в качестве ключа сохранённую идентичность нативной задачи и удаляет записи, когда обработка запросов закрывает их. В текущем мосте Linux и Windows по-прежнему не предоставляют эквивалентного обратного вызова для раннего прерывания; там ожидающий запрос сохраняется до истечения периода удержания. Благодаря правилу 1 *соединение* в любом случае закрывается без задержки. В остальных случаях отмена проявляется как `EPIPE` в Linux и только на этапе `Finish` в Windows.

## Выбор транспорта

`Stream(name)` обращается к `window._wails.streamFactory`. Серверные сборки устанавливают фабрику, возвращающую настоящий `WebSocket`; в сборках для webview она не задана, поэтому используется клиент с опросом.

Фабрика **должна** быть установлена до выполнения тела любого модуля, поскольку сгенерированные привязки создают потоки в области видимости модуля. `custom.js` для этого не подходит: `loadOptionalScript` выполняет HEAD-запрос, а затем добавляет тег `<script>`, поэтому фабрика появляется слишком поздно. Вместо этого фабрика добавляется в начало пакета среды выполнения при его выдаче (`stream_prelude_server.go`), что по определению происходит синхронно: зависимости ES-модуля вычисляются раньше импортирующих их модулей.

Если вы добавляете третий транспорт, также поместите его в прелюдию. Не возвращайтесь к `custom.js`.

## Что ещё не завершено

|  | статус |
| --- | --- |
| Отмена запросов на уровне платформы | **для Apple готово; для Linux/Windows ещё не реализовано** — см. выше |
| Настройка констант буферов через параметры | не реализовано; доступны только во время компиляции |
| Типизированные потоки | намеренно не реализовано: согласно принятому решению, кадры имеют тип `[]byte` |
| Конвейерная обработка (второй выполняющийся опрос) | не реализовано; потребуется упорядоченная повторная сборка в JS |
| Справедливое распределение ресурсов между соединениями | не реализовано — соединения в одном окне используют общую очередь, поэтому соединение, переполняющее её данными, замедляет соседние соединения |
| Объединение кадров JS→Go | **готово** — кадры, накопившиеся за выполняющимся запросом, отправляются ограниченными пакетами; соединения с небольшой нагрузкой по-прежнему отправляют по одному кадру на каждый POST-запрос |
| Пропускная способность в Windows | ~100 МБ/с, ограничивается маршалингом `WebResourceRequested`. Возможное решение — общие буферы (`PostSharedBufferToScript`); привязки находятся в `internal/webview2/pkg/webview2/`, но ещё не подключены к `pkg/edge` |
| `wails3 dev` / Vite | **работает** — проверено на сгенерированном проекте `vanilla-js`: сервер разработки Vite проксирует по адресу `/`, а `/wails/stream/*` сопоставляется промежуточным ПО сервера ресурсов до прокси, поэтому потоки не затрагиваются |
| Несколько окон | не тестировалось под нагрузкой, хотя по архитектуре область действия сеансов ограничена окном |

## Пакет фронтенда в режиме разработки

Сгенерированный проект импортирует `@wailsio/runtime` из **npm**, а не из пакета `/wails/runtime.js`, который выдаёт сервер ресурсов. При `wails3 dev` Vite разрешает его из `node_modules`, поэтому приложение, собранное с опубликованной средой выполнения, не увидит клиентские дополнения, внесённые в ветке.

Пока потоки не выпущены, подключите тестовое приложение к пакету из этой рабочей копии:

```bash
task v3:install-runtime -- ./path/to/your-app/frontend
```

Сначала эта команда пересобирает `dist/`, поэтому всегда устанавливает текущие исходники. Чтобы отменить это, выполните  
`npm install @wailsio/runtime@latest` в том же каталоге.

Обратите внимание: у клиента есть **два** выходных артефакта сборки, и легко пересобрать один, но не  
другой: `task v3:runtime:build:package` создаёт `dist/` пакета npm (его импортирует  
фронтенд приложения), а `task v3:runtime:build:assets` создаёт  
`bundledassets/runtime.js` (его WebView загружает с сервера ресурсов). При изменении  
`stream.ts` необходимо пересобрать оба артефакта.

## Тестирование

```bash
go test ./pkg/application/ -run TestStream -race        # protocol, ordering, backpressure
go test -tags server ./pkg/application/ -run TestServerMode
pnpm --dir v3/internal/runtime/desktop/@wailsio/runtime test
```

Ключевым является тест порядка: восемь горутин конкурентно отправляют данные, используя счётчик, значения которого выдаются под блокировкой очереди, а порядок извлечения должен в точности совпадать с порядком приёма. Если этот тест когда-либо завершится с ошибкой, значит, инвариант единственного обработчика извлечения нарушен.

Средство нагрузочного тестирования:

```bash
go run ./tests/stream-performance -duration 20s              # full sweep
go run ./tests/stream-performance -upload -duration 10s      # JS→Go matrix
go run ./tests/stream-performance -reloads 6                 # connection lifecycle
```

В Windows его необходимо запускать в интерактивном сеансе консоли: при обычном запуске через SSH процесс завершается в  
сеансе 0 с выводом нулевой длины. Кроме того, исполняемый файл необходимо разместить там, где его смогут прочитать как учётная запись SSH, так и учётная запись консоли, поскольку ACL для `C:\Users\<user>` разрешает доступ только его владельцу.

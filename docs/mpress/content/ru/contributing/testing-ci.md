Надёжным фреймворкам для настольных приложений требуется безотказное тестирование. В Wails v3 применяется **многоуровневая стратегия**:

| Уровень | Цель | Инструменты |
| --- | --- | --- |
| Модульные тесты | Быстрая обратная связь для изолированных функций | `go test ./...` |
| Тесты генератора и CLI | Проверка `wails3 generate bindings` и внутренней инфраструктуры CLI | `task test:generator`, `task test:cli` |
| Тесты шаблонов | Проверка того, что каждый поставляемый шаблон по-прежнему собирается | `task test:templates` |
| Обнаружение состояний гонки | Выявление гонок данных в среде выполнения и мосте | `go test -race ./...` |
| Матрица CI | Уверенность в работе на разных ОС для каждого PR | GitHub Actions |

В этом документе объясняется, **где находятся тесты**, **как их запускать** и **какие задачи координирует Taskfile**.

В `v3/TESTING.md` описана сборка примеров для разных платформ; это не каталог средств подавления сообщений о гонках.

---

## 1. Соглашения о структуре каталогов

```
v3/
├── internal/.../_test.go     # Unit tests for internal packages
├── pkg/.../_test.go          # Public API tests
├── tasks/events/generate.go  # Code generator for event constants (NOT a test harness)
├── tests/                    # Top-level integration test harness
└── TESTING.md                # Cross-platform example-build guidance
```

Рекомендации:

- **Размещайте модульные тесты рядом с кодом** (`foo.go` ↔ `foo_test.go`).
- Для пакетов `pkg/` используйте **тестирование методом чёрного ящика** (`package application_test`), если это помогает поддерживать чистоту API.
- Общие фикстуры размещаются там, где они используются (в этом рабочем дереве нет центрального пакета `internal/testutil/` — вместо этого подключайте вспомогательные средства отдельно для каждого пакета).

## 2. Модульные тесты

### Написание тестов

```go
func TestEventConstants(t *testing.T) {
    assert.NotEmpty(t, events.Common.WindowFocus)
}
```

Рекомендации:

- Используйте [`stretchr/testify`](https://github.com/stretchr/testify) — эта зависимость уже присутствует в `go.mod`.
- Отдавайте предпочтение **табличным** тестам, когда несколько входных данных, граничных случаев или ожидаемых результатов проверяют одно и то же поведение. Давайте каждому случаю описательное имя.
- При необходимости изолируйте особенности платформ с помощью заглушек за тегами сборки (`foo_windows_test.go`, `foo_darwin_test.go`, …).

### Требования к покрытию

Для новой и изменённой логики ожидается 100%-е покрытие операторов Go. Измеряйте покрытие изменённого пакета, а не полагайтесь на процент для всего репозитория:

```bash
go test ./pkg/application -coverprofile=coverage.out
go tool cover -func=coverage.out
```

Некоторые пути выполнения обоснованно невозможно протестировать в обычной тестовой среде — например, сбои, возникающие только на определённой платформе, поведение, зависящее от оборудования, или защитный резервный сценарий, который нельзя безопасно вызвать. Сводите такие исключения к минимуму и описывайте каждый непокрытый путь в описании PR.

### Локальный запуск

```bash
cd v3
go test ./... -cover
```

Или через Taskfile (фактические цели — сокращённой команды `task test` нет):

```
task test:cli            # CLI plumbing tests
task test:generator      # bindings generator round-trip tests
task test:templates      # build every shipped template
task test:infrastructure # supporting helpers
task test:examples       # exercise the example matrix (downloads as needed)
task test:all            # everything above
task sanity              # default GTK4 smoke check (legacy: sanity:gtk3)
task precommit           # what you should run before pushing
```

## 3. Интеграционные тесты

В `v3/tests/` находится инфраструктура интеграционного тестирования нескольких пакетов. Цели Taskfile `test:example:*` и `test:examples:*` выполняют проверки компиляции для darwin / windows / linux (включая матрицы GTK3 / GTK4 на базе Docker для Linux).

> Запускаемые примеры находятся в `v3/examples/`. Тестовые цели выбирают и собирают
>
> примеры, подходящие для платформы хоста или матрицы CI.

Запустите набор дымовых тестов для платформы хоста следующей командой:

```
task test:examples       # host
task test:examples:all   # full matrix (slow)
```

## 4. Обнаружение состояний гонки

Гонки данных фатальны для сред выполнения графического интерфейса.

### Исследование состояния гонки

Проверьте оба конфликтующих обращения и воспроизведите проблему на затронутой платформе. Не считайте отчёт безобидным и не подавляйте его без доказательств. В `v3/TESTING.md` описана компиляция примеров; успешная сборка не доказывает отсутствие гонок или корректность поведения нативной среды выполнения.

### Локальный набор тестов на состояния гонки

```
go test -race ./...
```

> У `wails3 dev` нет флага `-race` — CLI поддерживает флаги `--config`, `--port`,
>
> и `-s` (включает HTTPS). Чтобы протестировать среду выполнения с детектором гонок,
>
> соберите тестовое приложение с помощью `go build -race` и запустите его напрямую.

## 5. Рабочие процессы GitHub Actions

Фактические файлы рабочих процессов в `.github/workflows/` (проверено по рабочему дереву):

| Файл | Назначение |
| --- | --- |
| `build-and-test-v3.yml` | Матрица Go 1.26/1.27, проверки среды выполнения и генератора, компиляция шаблонов и примеров, а также проверки сборки приложений. В Linux по умолчанию используется GTK4/WebKitGTK 6.0; устаревший вариант задаёт `BUILD_TAGS=gtk3`. Нативный запуск и взаимодействие необходимо проверять отдельно. |
| `cross-compile-test-v3.yml` | Базовые проверки кросс-компиляции |
| `auto-changelog-v3.yml`, `changelog-v3.yml` | Автоматизация журнала изменений |
| `nightly-release-v3.yml` | Артефакты ночных выпусков v3 |
| `bump-webview2-v3.yml`, `release-webview2.yml` | Управление зависимостью WebView2 и её выпусками |
| `build-cross-image.yml` | Сборка образа контейнера с кросс-компилятором |
| `publish-npm.yml` | Публикация встроенной среды выполнения JS `@wailsio/runtime` в npm |
| `pr-master.yml` | Проверки со стороны PR относительно ветки `master` |
| `semgrep.yml` | Статический анализ Semgrep |
| `stale-issues.yml`, `generate-sponsor-image.yml`, `build-and-test.yml`, `weekly-release-v2.yml` | Обслуживание репозитория и рабочие процессы v2; старые рабочие процессы синхронизации и отправки в Crowdin выведены из эксплуатации. |

Шаги CI соответствуют указанным выше целям Taskfile (`task test:cli`, `task test:generator`, `task test:templates`, `task test:examples`, …), поэтому CI можно локально воспроизвести один в один. Дымовой шаг `wails3 build` в `build-and-test-v3.yml` вызывается **без дополнительных флагов** — у `wails3 build` нет флага `-skip-package`.

---

## 6. Локальное воспроизведение CI

Единой общей цели `task ci` не существует. Чтобы воспроизвести CI, последовательно запустите реальные цели:

```
task precommit
task test:cli
task test:generator
task test:templates
task test:examples
```

## 7. Устранение неполадок при сбоях тестов

| Симптом | Вероятная причина | Решение |
| --- | --- | --- |
| **Состояние гонки в `webview_window_darwin.go`** | Изменение состояния окна вне главного потока | Передайте вызов через `application.InvokeAsync` / `Invoke`, чтобы он выполнялся в главном потоке |
| **Тест Linux зависает в CI без графического интерфейса** | Для GTK требуется дисплей | Запустите через `xvfb-run`, например `xvfb-run task test:examples:linux` |
| **Сбой сборки шаблона** | Файл блокировки зависимостей фронтенда устарел | Повторно выполните `wails3 init` в чистом каталоге, чтобы обновить шаблон |
| **Ошибки coverpkg** | Интеграционный тест импортирует `main` | Перейдите на тег сборки `//go:build integration` и выполняйте импорт только при наличии этого тега |

---

## 8. Добавление новых тестов

1. **Модульные тесты** — создайте `*_test.go` и выполните `go test ./...`
2. **Генератор / CLI** — дополните тестовые случаи в `internal/generator/testcases/` или `internal/commands/*_test.go` и повторно выполните `task test:generator` / `task test:cli`
3. **Шаблоны / примеры** — убедитесь, что поставляемые шаблоны по-прежнему собираются с помощью `task test:templates`

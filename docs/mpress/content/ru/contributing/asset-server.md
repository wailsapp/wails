## Обзор

Каждое приложение Wails поставляется как **единый нативный исполняемый файл**, объединяющий:

1. Серверную часть на *Go*
2. Клиентскую часть на основе *веб-технологий* (HTML + JS + CSS)

**Сервер ресурсов** связывает эти части воедино. У него есть **два режима работы**, выбираемые во время компиляции с помощью тегов сборки Go:

| Режим | Тег | Назначение |
| --- | --- | --- |
| **Разработка** | `//go:build !production` | Быстрая итеративная разработка с горячей перезагрузкой |
| **Рабочая сборка** | `//go:build production` | Встроенные ресурсы без внешних зависимостей |

Реализация находится в `v3/internal/assetserver/` и чётко разделена по файлам:

```
build_dev.go              # ⬅️ dev-only entrypoint (!production build tag)
build_production.go       # ⬅️ production-only entrypoint (production build tag)
assetserver.go            # Shared core
assetserver_dev.go        # Dev proxy/disk handler
assetserver_webview.go    # WebView-side adapter
assetserver_darwin.go     # OS-specific helpers (also linux/windows variants)
asset_fileserver.go       # Shared static file logic
content_type_sniffer.go   # MIME type detection
mimecache.go              # Cached MIME lookups
ringqueue.go              # Tiny in-memory LRU
options.go                # Configuration struct
middleware.go             # http.Handler middleware type
bundled_assetserver.go    # Hand-written wrapper around embedded bundles
bundledassets/            # Embedded runtime JS assets
```

## Режим разработки

### Жизненный цикл

1. `wails3 dev` запускается и **порождает сервер разработки клиентской части** (Vite, SvelteKit, React-SWC …), выполняя задачу, определённую в `build/Taskfile.yml` (обычно `npm run dev`).
2. CLI задаёт `WAILS_VITE_PORT` равной порту разработки Wails, а `FRONTEND_DEVSERVER_URL` — **полному** URL-адресу (`http://host:port` / `https://host:port`), указывающему на запущенный сервер разработки фреймворка. См. `internal/commands/dev.go`.
3. Сервер ресурсов для разработки (включаемый при компиляции посредством `//go:build !production` в `build_dev.go`) считывает `FRONTEND_DEVSERVER_URL` через `GetDevServerURL()` и передаёт ему через обратный прокси трафик, не относящийся к среде выполнения.
4. Статические файлы (`/assets/logo.svg`) могут **обслуживаться непосредственно с диска** через `asset_fileserver.go` (для повышения скорости), а все неизвестные запросы **проксируются** на сервер разработки фреймворка, обеспечивая *мгновенную* горячую замену модулей.

```
┌─────────┐  /wails/runtime.js     ┌─────────────┐
│ Browser │ ── embedded runtime ──▶│   Runtime   │
├─────────┤                        └─────────────┘
│   JS    │  / (index.html)        proxy / -> Vite via FRONTEND_DEVSERVER_URL
└─────────┘ ◀─────────────┐
              AssetServer │
                          ▼
                   ┌────────────┐
                   │  Vite Dev  │
                   │   Server   │
                   └────────────┘
```

### Возможности

- **Автоматическая перезагрузка** — Vite, SvelteKit и другие инструменты внедряют HMR через WebSocket; сервер ресурсов для разработки прозрачно проксирует это соединение.
- **Поддержка карт исходного кода** — поскольку ресурсы не объединяются в пакет, инструменты разработчика в браузере сопоставляют ошибки с исходным кодом.
- **Без повторной компиляции Go** — пересобирается только клиентская часть; код Go продолжает выполняться, пока вы не измените файлы `.go`.

### Смена фреймворка

Прокси-сервер разработки **не зависит от фреймворка**. При запуске задачи разработки CLI Wails задаёт две переменные окружения:

| Переменная окружения | Источник | Значение |
| --- | --- | --- |
| `WAILS_VITE_PORT` | `internal/commands/dev.go` (константа `wailsVitePort`) | Порт разработки по умолчанию (9245, если не передан `--port`) — конфигурации Vite следует учитывать этот порт |
| `FRONTEND_DEVSERVER_URL` | `internal/commands/dev.go` | Полный URL-адрес, на который Wails будет проксировать запросы; в Go считывается через `assetserver.GetDevServerURL()` (`build_dev.go`) |

В дереве исходного кода v3 нет переменных окружения `VITE_PORT`, `FRONTEND_DEV_PORT` или `WAILSDEV_VERBOSE`.

Добавьте новый шаблон → определите для него задачу разработки → сервер ресурсов будет работать без дополнительной настройки.

## Рабочий режим

При выполнении `wails3 build` конвейер:

1. Запускает **рабочую сборку** клиентской части (`npm run build`), создавая `frontend/dist/**`.
2. **Встраивает** этот каталог в приложение через `go:embed` в собственном пакете приложения (обычно `//go:embed all:frontend/dist` рядом с `main.go`).
3. Компилирует исполняемый файл Go с `-tags production` (обёртка Taskfile передаёт его через `EXTRA_TAGS`).

`internal/assetserver/build_production.go` — заглушка с тегом сборки, которая включает рабочий путь выполнения. `internal/assetserver/bundled_assetserver.go` **написан вручную**: он оборачивает JS среды выполнения в `bundledassets/` и не является сгенерированным файлом.

### Обработка запросов

Фактический обработчик — `internal/assetserver/assetserver.go` / `asset_fileserver.go`. В общих чертах он выполняет следующие действия:

1. Пытается получить встроенный статический ресурс по запрошенному пути.
2. Если это не удаётся, использует `index.html` для маршрутизации SPA.
3. Определяет тип содержимого по данным, если расширение неизвестно (`content_type_sniffer.go`).
4. Устанавливает подходящие заголовки кеширования.

- **Определение MIME-типа** — для файлов без расширения тип содержимого определяется по первым ~512 байтам (`content_type_sniffer.go`), а результат кешируется в `mimecache.go` / `ringqueue.go`.
- **Заголовки безопасности** — запрещают навигацию `file://` и устанавливают `nosniff`.

Поскольку все ресурсы встроены, поставляемый исполняемый файл **не имеет внешних зависимостей** (даже в Windows).

## Связь между разработкой и рабочей сборкой

С точки зрения `pkg/application` оба режима предоставляют **одинаковый открытый интерфейс**: структуру `AssetOptions` с `Handler http.Handler`, а также промежуточные обработчики и привязку жизненного цикла внутри `internal/assetserver/`. Переключение между режимами разработки и рабочей сборки полностью выполняется с помощью тегов сборки Go, поэтому код приложения в обоих режимах одинаков.

```go
app := application.New(application.Options{
    Assets: application.AssetOptions{
        Handler: application.AssetFileServerFS(assetsFS),
    },
})
```

## Интеграция фреймворков клиентской части

### Шаблоны

Каждый поставляемый шаблон (React, Vue, Svelte, Solid, Vanilla, …) содержит:

- `build/Taskfile.yml`
- `frontend/vite.config.ts` (или эквивалент)

Конфигурация Vite или аналогичного инструмента считывает `WAILS_VITE_PORT` и привязывает сервер разработки к этому порту. Затем CLI публикует фактический `FRONTEND_DEVSERVER_URL` для использования прокси-сервером внутри приложения.

Фреймворки остаются полностью независимыми от Go:

- Импортировать какой-либо JavaScript SDK Wails во время сборки не требуется — `/wails/runtime.js` предоставляется сервером ресурсов во время выполнения.
- Можно подключить любой фреймворк с HTTP-сервером разработки.

## Расширение и настройка

Нужны пользовательские заголовки, аутентификация или gzip-сжатие?

1. Определите `middleware.Middleware` (псевдоним для `func(http.Handler) http.Handler`, объявленный в `internal/assetserver/middleware.go`).
2. Подключите его к своему `application.AssetOptions` через конфигурацию, предоставляемую `internal/assetserver/options.go`.
3. Поведение в режимах разработки и продакшена одинаково — отдельного списка промежуточных обработчиков для каждого режима нет.

## Основные файлы исходного кода

| Файл | Назначение |
| --- | --- |
| `build_dev.go` / `build_production.go` | Обёртки с тегами сборки, выбирающие режим разработки или продакшена |
| `assetserver.go` / `asset_fileserver.go` | Основной HTTP-обработчик |
| `assetserver_dev.go` | Обратный прокси-сервер для `FRONTEND_DEVSERVER_URL` |
| `bundled_assetserver.go` | Написанная вручную обёртка над `bundledassets/` |
| `options.go` | Конфигурация для взаимодействия с `application.AssetOptions` |
| `mimecache.go` / `ringqueue.go` | Кеш MIME-типов и небольшой LRU-кеш |

## Типичные проблемы и отладка

- **Белый экран в продакшене** — обычно проблема связана с маршрутизацией SPA: убедитесь, что сервер разработки возвращает `index.html` для неизвестных путей и что выполняется резервная обработка встроенного обработчика продакшена.
- **404 в режиме разработки** — конфигурация Vite не выполняет привязку к `WAILS_VITE_PORT` либо CLI не смог подключиться к серверу разработки, чтобы заполнить `FRONTEND_DEVSERVER_URL`.
- **Крупные ресурсы** — встраивание увеличивает размер исполняемого файла. Предоставляйте крупные медиафайлы из отдельного источника или передавайте их потоково через пользовательский `http.Handler`.

---

Теперь вы знаете, как **сервер ресурсов** Wails передаёт веб-код в нативное окно как в режиме **разработки**, так и в режиме **продакшена**. Освоив этот уровень, вы сможете уверенно отлаживать проблемы загрузки, добавлять промежуточные обработчики и даже полностью заменять инструментарий фронтенда.

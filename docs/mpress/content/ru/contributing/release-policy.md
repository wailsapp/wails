## Вся модель в одной таблице

Выпуски Wails v3 создаются **по расписанию, а не по готовности функций**. После базового выпуска `v3.0.0`:

| Выпуск | Тег | Периодичность | Выпуск GitHub | npm `@wailsio/runtime` |
| --- | --- | --- | --- | --- |
| Ночной | `v3.<next>.0-nightly.<YYYYMMDD>` (дата по UTC; при повторном запуске в тот же день добавляется `.N`) | автоматически, ежедневно, только если в `UNRELEASED_CHANGELOG.md` есть содержимое | предварительный выпуск, **не** Latest | та же версия без `v`, dist-tag `nightly` |
| Еженедельный | `v3.<next>.0` | автоматически, в воскресенье 20:00 по времени Australia/Sydney **(день не подтверждён)** | обычный выпуск, Latest | та же версия, dist-tag `latest` |
| Исправление | `v3.<current>.<N>`, `N > 0` | редко, вручную | обычный релиз, Latest | та же версия, dist-tag `latest` |
| Мажорный | `v4.0.0` | только для несовместимых изменений | обычный выпуск | `latest` |

`<next>` — это наивысшая **выпущенная** v3 минорная версия плюс один. Ночная сборка — это предварительная версия **следующего еженедельного релиза**, поэтому её базовая версия определяется по наивысшему тегу релиза (предварительные версии игнорируются): после хотфикса `v3.1.1` следующая ночная сборка по-прежнему будет иметь версию `v3.2.0-nightly.*`. Она должна иметь более высокий номер версии, поскольку предварительная версия при сортировке располагается ниже соответствующего ей релиза: `v3.0.0-nightly.<date>` располагалась бы перед `v3.0.0`.

**Повышение минорной версии не является этапом выпуска функций.** `v3.4.0` означает «еженедельный выпуск после `v3.3.0`». Чтобы узнать, что изменилось, читайте примечания к выпуску, а не номер версии.

Политика выбирается по **формату** версии: суффикс `-nightly.` обозначает ночной выпуск; любой другой суффикс (`-alpha`, `-beta`, `-rc`) обозначает устаревшую сборку, предшествующую GA; отсутствие суффикса обозначает выпуск.

### Синхронизированные версии

CLI, модуль Go и пакет npm `@wailsio/runtime` имеют **одинаковую версию**, взятую из `v3/internal/version/version.txt` (`3.2.0-nightly.20261102` в npm для тега `v3.2.0-nightly.20261102`). Проекты, созданные с помощью `wails3 init`, фиксируют `@wailsio/runtime` на собственной версии CLI; в сборках CLI для разработки используется резервная версия `latest`.

## Подробный пример

| Дата | Событие | Тег | `go install ...@latest` разрешается в |
| --- | --- | --- | --- |
| вс, 25 окт. | GA, выпуск вручную | `v3.0.0` | `v3.0.0` |
| пн, 26 — сб, 31 окт. | ночные выпуски | `v3.1.0-nightly.20261026` ... `v3.1.0-nightly.20261031` | `v3.0.0` |
| вс, 1 нояб., 20:00 по времени Сиднея | еженедельный выпуск | `v3.1.0` | `v3.1.0` |
| пн, 2 нояб. | ночной выпуск (предварительная версия следующего еженедельного выпуска) | `v3.2.0-nightly.20261102` | `v3.1.0` |
| ср, 4 нояб. | исправление, вручную, из ветки выпуска | `v3.1.1` | `v3.1.1` |
| вс, 8 нояб. | еженедельный выпуск | `v3.2.0` | `v3.2.0` |

Еженедельный выпуск всегда сортируется выше всех ночных выпусков с тем же номером, а ночной выпуск никогда не становится `@latest`.

## Что запускают пользователи

| Цель | Команда |
| --- | --- |
| Новейший выпуск (еженедельный или исправление) | `go install github.com/wailsapp/wails/v3/cmd/wails3@latest` или `wails3 update cli` |
| **Воспроизводимая сборка (рекомендуется)** | зафиксируйте точный тег: `v3.1.0` в `go.mod`, CI и документации |
| Ночной выпуск | его точный тег (`@v3.2.0-nightly.20261102`), либо `wails3 update cli -nightly` |
| Новейшая сборка любого типа | `wails3 update cli -pre` |
| Пакет среды выполнения npm | `@wailsio/runtime` (`latest` = еженедельный выпуск или исправление, `nightly` = ночной выпуск) |

Почему это работает: Go разрешает `@latest` в максимальный тег **без суффикса предварительного выпуска** и учитывает предварительные выпуски, только если обычных выпусков нет. Флажок GitHub «pre-release» невидим для прокси-сервера Go, поэтому ночные выпуски имеют суффикс предварительной версии semver, а не полагаются на этот флажок. В рабочей среде всегда фиксируйте версию.

## Ветки

| Ветка | Назначение |
| --- | --- |
| `master` | Разработка и ночные выпуски. |
| `releases/**` | Краткоживущие ветки для разовых выпусков: GA `v3.0.0` и исправления. Требования к CI те же, что и для `master`. |

Еженедельные выпуски создаются из `master`, но **не из вершины этой ветки**: рабочий процесс выбирает новейший коммит после предыдущего еженедельного выпуска, для которого успешно завершились все обязательные проверки (`v3 Build Results`, `Run Go Tests`, `Bundled runtime matches source`), и помечает тегом именно этот коммит. Если подходящего коммита нет, выпуск не создаётся. Ночные выпуски создаются из `master`; если HEAD не прошёл проверки, выводится только предупреждение.

## Как создать выпуск

Права на выпуск есть только у руководителя проекта (см. документ об управлении проектом). Участники никогда не создают теги и не публикуют выпуски; они добавляют записи в `v3/UNRELEASED_CHANGELOG.md`.

Всё выполняется из **Nightly + Weekly Release v3** (`.github/workflows/nightly-release-v3.yml`):

- **Ночной выпуск (автоматически)** в 15:00 UTC. Пропускается, если журнал невыпущенных изменений пуст.
- **Еженедельный релиз (автоматический)** в 20:00 по сиднейскому времени. GitHub cron поддерживает только UTC, поэтому запланированы два cron-задания (09:00 и 10:00 UTC), а защитное задание продолжает выполнение, только когда в Сиднее 20:00, с учётом перехода на летнее время. Еженедельный выпуск проходит проверку допуска к релизу, выбирает самый новый коммит с успешно пройденными проверками, увеличивает минорную версию, помечает этот коммит тегом, не изменяя журнал изменений, а затем обновляет только поля версий в `master` (`version.txt` и версии пакетов среды выполнения), поэтому изменения зависимостей и файлов блокировки, объединённые после выбранного коммита, сохраняются. Публикация в npm выполняется из тега, а не из `master`.
- **Вручную.** Запустите рабочий процесс с `channel`, `dry_run` (включено по умолчанию) и, при необходимости, с `release_version`. Пробный запуск выводит версию, тип, флаги GitHub, dist-tag npm и примечания, не изменяя ничего в GitHub или npm.
- **GA-релиз или хотфикс.** Задайте `release_version` (`v3.0.0`, `v3.1.1`). Для хотфикса более старой ветки также можно задать `ref: releases/...`; его релизный коммит переносится обратно в `master` с помощью cherry-pick.

Локальный пробный запуск: `cd v3/tasks/release && go run release.go --dry-run --channel weekly`; `go run release.go --print-policy v3.2.0-nightly.20261102` показывает вычисленные флаги.

### Механизмы защиты

- Автоматически определённая версия должна быть строго выше (в порядке semver, где предварительная версия < релиза) каждого существующего тега, иначе инструмент откажется продолжать.
- Одновременно выполняется только одно задание выпуска (общая группа параллелизма).
- Публикация в npm запускается **тегом релиза** и собирает коммит, на который указывает этот тег.

## Проверка допуска к выпуску

**Еженедельный выпуск** (но не ночной) не создаёт тег, пока существует хотя бы одно из следующего:

1. открытые задачи или запросы на включение изменений с меткой `P0` или `release-blocker`;
2. открытые задачи с меткой `regression`, созданные после последнего еженедельного выпуска;
3. открытые оповещения Dependabot критической или высокой степени серьёзности, открытые оповещения о результатах сканирования кода критической или высокой степени серьёзности, а также любые открытые оповещения о результатах сканирования секретов — **только для поставляемого кода**. Оповещения, относящиеся исключительно к `v3/examples/`, `v2/examples/`, `website/`, `docs/`, `.github/` или любому каталогу `examples/`, игнорируются (`SHIPPED_ALERT_IGNORE` в `v3/tasks/releasegate/main.go`, **владелец должен проверить**);
4. рекомендации по безопасности репозитория, которые всё ещё имеют статус `triage`.

**Кто может установить блокирующую метку.** Метка учитывается, только если последнее событие `labeled` для неё (без последующего `unlabeled`) было создано участником команды `wailsapp/maintainers` или соавтором с правами `maintain`/`admin`. Такая же метка, установленная кем-либо ещё, игнорируется и регистрируется в журнале, поэтому посторонние не могут заблокировать или разблокировать релиз. Автоматически устанавливаемая метка `high-priority` намеренно **не** используется. Учётные записи ботов, например `taliesin-ai`, проходят проверку по списку разрешённых, если у них есть право `maintain`; это предусмотрено намеренно, и агент сортировки может устанавливать блокирующие метки при наличии подтверждающих данных.

**Поведение при сбое.** Проверка не разрешает выпуск при сбое (**closed**): если не удаётся прочитать API оповещений или список разрешённых, еженедельный выпуск останавливается. При сбое он не создаёт никаких тегов, записывает список (со ссылками) в сводку задания и обновляет комментарий в единственной задаче «Weekly release status», если задана переменная репозитория `WEEKLY_STATUS_ISSUE`.

**Настройка, которую владелец должен выполнить на GitHub** (ничего не создаётся автоматически): создать метки `P0`, `release-blocker` и `regression`; создать задачу «Weekly release status» и присвоить `WEEKLY_STATUS_ISSUE` её номер; предоставить `WAILS_REPO_TOKEN` доступ на чтение к Issues, Pull requests, Administration (разрешения соавторов), Dependabot alerts, Code scanning alerts, Secret scanning alerts, Repository security advisories и участникам организации, а также доступ на запись к Issues для комментария о состоянии. Стандартный `GITHUB_TOKEN` не может читать эти данные.

**Переопределение.** `override_reason` (входной параметр workflow-dispatch) пропускает проверку допуска. Причина, инициатор и каждый пропущенный блокирующий фактор записываются в сводку и задачу о состоянии. Использовать этот параметр должен только руководитель выпуска. GitHub не позволяет ограничить входной параметр одним пользователем, поэтому запускайте задание выпуска в окружении с обязательным рецензированием (рекомендуется), чтобы переопределение требовало явного одобрения.

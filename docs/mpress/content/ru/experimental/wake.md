Wake — экспериментальная система сборки Wails. Один файл `wails.yaml` описывает приложение, фронтенд, целевые платформы, пакеты и параметры подписывания. На основе этой конфигурации Wake планирует и выполняет сборки, кэширует неизменившиеся результаты работы и сообщает о созданных файлах.

В этом руководстве вы создадите небольшое настольное приложение, настроите его в браузере, соберёте для своего компьютера и запустите в режиме разработки. Начните с одной локальной целевой платформы и неподписанной сборки. Добавляйте кросс-компиляцию и распространение после того, как первая сборка заработает.

Уже есть приложение? Перейдите к разделу [Перенос существующего проекта](#--). Описание отдельных полей и расширенных рабочих процессов см. в [руководстве по сборке с YAML](/experimental/yaml-builds/) и [справочнике по манифесту](/reference/wails-yaml-fields/).

## Чего ожидать от эксперимента

@note{type="caution" title="Используйте тестовый проект или отдельную ветку"}
Wake включается явно, а его конфигурация, команды и поведение могут меняться между предварительными сборками. На него пока не распространяются гарантии совместимости стабильной системы сборки. Сохраняйте заведомо рабочую ревизию проекта и фиксируйте версии CLI и фреймворка, с которыми проводите тестирование. Перед распространением тестируйте пакеты в целевых системах.
@end

Wake и бэкенд **Pure Go** включаются независимо друг от друга. Включение Wake не включает Pure Go автоматически. В этом уроке используется стандартный бэкенд, поэтому для сборки приложений с графическим интерфейсом под macOS и Linux по-прежнему требуются обычные нативные инструменты разработки.

Мастер проверяет требования и сохраняет конфигурацию. Сохранение не является сборкой и не подтверждает готовность всех выбранных целевых платформ. Недостающие инструменты или учётные данные можно добавить позднее, например на узле CI. Недопустимые сочетания целевых платформ и пакетов необходимо исправить перед сохранением.

Миграция **необратима**. Wake не выполняет Taskfile, не разворачивает шаблоны Task и не преобразует YAML обратно в Taskfile. В проектах, которые не были перенесены, по-прежнему используется отдельная устаревшая среда выполнения Task. Активный файл `wails.yaml` никогда не переключается на неё без явного уведомления.

## Перед началом

Вам понадобятся Go, Node.js с npm для стартового фронтенда и [зависимости платформы](/getting-started/installation/#platform-specific-dependencies) для вашего компьютера. Начните в каталоге, в котором нужно создать папку нового проекта. Для работы с мастером также потребуется браузер.

Используйте ревизии CLI и фреймворка, в которые включена эта предварительная версия. Установка стабильного CLI `v3.0.0` не добавляет описанные здесь экраны настройки Wake. Следующие команды фиксируют предварительную версию из [PR №6531](https://github.com/wailsapp/wails/pull/6531):

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@44e449c91
wails3 version
```

Убедитесь, что каталог с исполняемым файлом Go входит в `PATH`; это описано в [руководстве по установке](/getting-started/installation/). Далее в руководстве вы зафиксируете зависимость приложения Go на той же ревизии. При тестировании более новой предварительной версии обновляйте оба аргумента ревизии одновременно.

### Включение Wake в терминале

В Bash или Zsh:

```bash
export WAILS_EXP_USE_WAKE=1
```

В PowerShell:

```powershell
$env:WAILS_EXP_USE_WAKE = '1'
```

Не закрывайте этот терминал до конца руководства. Задавайте переменную повторно в каждом новом терминале или задании CI, где выполняются команды Wake. Wake включается самим фактом её **наличия**: значение `false` или пустая строка не отключают его. Старое имя `WAILS_USE_WAKE` игнорируется.

## Создание приложения

Запустите мастер создания проекта:

```sh
wails3 init -ui
```

В браузере откроется мастер проекта. Он создаёт исходные файлы; отдельный мастер `wails3 setup`, описанный ниже, настраивает их сборку.

| Экран | Что выбрать в этом руководстве | Что произойдёт дальше |
| --- | --- | --- |
| **Проект — создание проекта Wails** | Введите `wake-demo`, затем нажмите **Продолжить**. | Проект будет создан в новой папке `wake-demo` внутри показанного каталога. |
| **Фреймворк — выбор фреймворка** | Выберите **Vanilla**, затем нажмите **Продолжить**. | Вы получите небольшой фронтенд, для которого не нужно отдельно изучать конкретный фреймворк. |
| **Язык — выбор языка** | Выберите **JavaScript**, затем нажмите **Продолжить**. | Экран **Привязки**, предназначенный только для TypeScript, будет пропущен. |
| **Сведения — сведения о проекте** | Укажите название продукта `Wake Demo`, идентификатор пакета `com.example.wakedemo` и версию `0.1.0`. Нажмите **Создать проект**. | Если Wake включён, сведения записываются в `wails.yaml`. |

В этом уроке не выбирайте **Использовать глобальные значения по умолчанию**: этот вариант пропускает выбор фреймворка и языка. Если в другом проекте выбрать TypeScript, на экране **Привязки** можно выбрать интерфейсы или классы для создаваемых привязок данных Go.

Вернитесь в терминал и дождитесь завершения создания проекта. Затем выполните:

```sh
cd wake-demo
go get github.com/wailsapp/wails/v3@44e449c91
```

Теперь у вас должны быть `main.go`, модуль Go, каталог `frontend` и нативный файл `wails.yaml`. Встроенный шаблон использует Wake напрямую, поэтому переносить этот новый проект не нужно. В шаблоне от сообщества могут быть собственные устаревшие задачи; в таком случае может потребоваться описанная ниже проверка миграции.

## Пошаговая настройка сборки на каждом экране

В каталоге `wake-demo` выполните:

```sh
wails3 setup
```

Теперь в браузере отображается **НАСТРОЙКА WAKE**. Если вместо неё отображается общий процесс настройки, проверьте, что переменная `WAILS_EXP_USE_WAKE` задана в терминале, из которого запущена команда, и что используется предварительная версия CLI.

На снимках экрана ниже показано выполнение этих действий в Linux. В Windows или macOS целевая платформа хоста и необходимые инструменты будут другими.

### Проект — только при отсутствии метаданных

Для только что созданного приложения этот экран **пропускается**: файл `init` уже записал метаданные. Это ожидаемое поведение.

При настройке существующего каталога с исходным кодом Go без нативного манифеста или устаревшей конфигурации сборки экран **О проекте** запрашивает название продукта, имя проекта, идентификатор приложения, версию, компанию и описание. Эти значения остаются в мастере до нажатия **Сохранить**. Настройка не создаёт исходные файлы приложения. Если мастер обнаружит Taskfile или устаревшие метаданные, сначала выполните миграцию.

### Приложение — что вы создаёте?

Выберите **Настольное приложение**. Не устанавливайте флажок **Упаковать существующие бинарные файлы** и выберите **Стандартный бэкенд**. Нажмите **Продолжить**.

![Экран приложения с выбранными вариантами «Настольное приложение» и «Стандартный бэкенд» и отключённой упаковкой предварительно собранных файлов.](/assets/screenshots/wake/application.png)

- Вариант **Настольное приложение** создаёт приложение с графическим интерфейсом и веб-фронтендом.
- Варианты **Приложение командной строки** и **Сервер** описывают программы без окна настольного приложения. Изменение этого выбора не переписывает исходный код приложения; используйте проект с исходным кодом, соответствующим выбранному типу.
- **Pure Go (экспериментальный)** включается отдельно. Для поддерживаемых сборок настольных приложений он устраняет требование к компилятору C при условии, что зависимости также собираются без CGo. Он не отменяет необходимость в библиотеках среды выполнения целевой платформы и во всех инструментах упаковки и подписывания.
- **Упаковать существующие бинарные файлы** подготавливает команду с использованием `--skip-build`.
  Для этого требуются уже собранные бинарные файлы; для нового проекта не включайте этот параметр.

Бэкенд — это **настройка уровня проекта**. Если изменить её здесь, может измениться поведение других профилей, наследующих эти настройки.

### Целевые платформы — где должно работать приложение?

Оставьте только целевую платформу, соответствующую используемому компьютеру, затем нажмите **Продолжить**.
Изначально мастер выбирает операционную систему и архитектуру компьютера, на котором он запущен.

![Экран целевых платформ, где для компьютера из этого руководства выбрана только linux/amd64.](/assets/screenshots/wake/targets.png)

Имя целевой платформы сочетает операционную систему и архитектуру процессора: например, `windows/amd64`, `darwin/arm64` для Mac с Apple Silicon или `linux/amd64`.
`darwin` означает macOS. При выборе другой целевой платформы запрашивается исполняемый файл для соответствующего компьютера; это не означает, что такой файл можно будет запустить на текущем компьютере.

Дополнительные архитектуры, универсальные сборки macOS и экспериментальные мобильные целевые платформы оставьте до следующего запуска настройки.

### Пакеты — выбор выходных файлов релиза

Не устанавливайте флажки форматов пакетов и оставьте параметр **Подписывать выходные файлы релиза** выключенным.
Нажмите **Продолжить**.

![Экран пакетов без выбранных дополнительных форматов пакетов Linux и с выключенным подписыванием.](/assets/screenshots/wake/packages.png)

Если дополнительные форматы не выбраны, Wake создаёт стандартный выходной файл для целевой платформы: исполняемый файл настольного приложения либо пакет приложения macOS для графического приложения macOS. Этого достаточно, чтобы проверить приложение локально. Если выбрать форматы позднее, будут добавлены выходные файлы для распространения, например DMG, MSIX, NSIS, DEB или AppImage, где они поддерживаются.

Для этой первой локальной сборки подписывание необязательно. Успешная сборка без подписи не означает, что приложение готово к общедоступному распространению.

### Инструменты — инструменты для сборки

Ознакомьтесь с требованиями для выбранных параметров. Список формируется из плана сборки Wake; это не требование устанавливать каждый инструмент на каждой платформе.

![Экран инструментов с определёнными требованиями для локальной сборки из исходного кода в Linux.](/assets/screenshots/wake/tools.png)

Для этого урока потребуются Go, инструменты фронтенда и нативные средства разработки, необходимые стандартному графическому бэкенду основной системы. Docker не является обязательным во всех случаях. Для кросс-компиляции с CGo могут потребоваться компилятор и библиотеки целевой платформы либо поддерживаемая контейнерная инструментальная цепочка.

До запуска локальной сборки устраните проблемы в строках с пометками **Не готово**, **Требуется настройка** или **Требуется обновление**. Используйте отображаемые инструкции, если они доступны, либо [руководство по установке для платформы](/getting-started/installation/), затем нажмите **Проверить снова**. Если установка изменила `PATH` терминала, может потребоваться перезапустить настройку. Когда требования для основной системы будут выполнены, нажмите **Продолжить**.

Мастер может сохранить корректную конфигурацию, даже если на этом компьютере отсутствуют необходимые инструменты. Это полезно при настройке CI, но в этом руководстве нужна сборка, которую можно запустить здесь.

### Подписывание — только если выбрано

Этот экран **пропущен**, поскольку вы не включили подписывание. Если при следующем запуске включить параметр **Подписывать выходные файлы релиза**, отобразятся имеющиеся элементы управления подписыванием для выбранных настольных платформ. Параметр **Настроить подписывание позднее** отключает подписывание в сохраняемом профиле настройки. Подписывание мобильных приложений настраивается в YAML, а не с помощью этих элементов управления.

Настройки подписывания по умолчанию хранятся в пользовательских настройках. Wake может использовать настроенные файлы сертификатов за пределами проекта, не копируя закрытые ключи или пароли в `wails.yaml`. Явно заданные настройки подписывания проекта имеют приоритет. Перед подготовкой общедоступного релиза следуйте [рекомендациям по настройке подписывания](/getting-started/setup/) и [руководству по упаковке и подписыванию](/experimental/yaml-builds/#package-and-sign-for-distribution).

### Сохранение — сохранение конфигурации сборки

Проверьте сводку: настольное приложение, стандартный бэкенд, сборка из исходного кода, целевая платформа основной системы и отключённое подписывание. Нажмите **Сохранить wails.yaml**.

![Экран сохранения со сводкой: графическое приложение, стандартный бэкенд, сборка из исходного кода и неподписанная целевая платформа linux/amd64.](/assets/screenshots/wake/save.png)

Должны появиться сообщение **Конфигурация сборки сохранена**, путь к манифесту и следующая информация:

```sh
wails3 build setup
```

Нажмите **Готово** и вернитесь в терминал. Мастер настройки сохранил выбранные целевые платформы и пакеты в `profiles.setup`. Он также обновил тип приложения, включение фронтенда и настройки бэкенда. Существующие команды фронтенда, вспомогательные программы, хуки и не связанные с ними параметры конфигурации сохранены.

Имя профиля имеет значение: `wails3 build setup` использует сохранённые в нём параметры. Обычная команда `wails3 build` не выбирает профиль `setup` автоматически.

## Сборка и запуск первого приложения

Выполните команду, показанную мастером:

```sh
wails3 build setup
```

При первой сборке устанавливаются зависимости фронтенда, создаются привязки и компилируется приложение. Последующие сборки могут повторно использовать результаты неизменившихся операций. Дождитесь сообщения **сборка выполнена успешно** и просмотрите пути к выходным файлам, выведенные CLI. Стандартный каталог выходных файлов — `bin`; графическое приложение macOS компонуется в пакет `.app`.

Запустите режим разработки на своём компьютере:

```sh
wails3 dev
```

Должно открыться окно стартового приложения. Введите своё имя и проверьте приветствие. Измените заполнитель поля для имени в `frontend/index.html` и сохраните файл — фронтенд должен обновиться. Измените приветствие в `greetservice.go`, чтобы проверить повторную сборку Go. По завершении нажмите **Ctrl+C** в терминале.

Разработка выполняется локально в основной системе. Профиль релиза может содержать несколько целевых платформ для кросс-компиляции, но это не меняет того, на каком компьютере можно запустить окно приложения в режиме разработки. Чтобы локально собрать и запустить приложение для эксплуатации, используйте `wails3 run`; см. [справочник по запуску](/reference/wails-yaml-run/).

Теперь у вас есть проект с исходным кодом, проверенный профиль сборки и работающий локальный цикл разработки. Добавьте исходный код и `wails.yaml` в систему контроля версий. Созданные рабочие файлы `.wails/` не являются источником конфигурации.

## Что можно сделать дальше

| Цель | Поддержка Wake | Что проверить в первую очередь |
| --- | --- | --- |
| Собрать для другой настольной платформы | Целевые платформы Windows, macOS и Linux, включая обе архитектуры macOS и универсальный выходной файл. | Для Pure Go и CGo требуются разные компиляторы. Проверьте приложение в целевой операционной системе и на целевой архитектуре. |
| Создать установщики или пакеты | MSIX, NSIS, приложение macOS/DMG, DEB, RPM, Arch, Void и AppImage. | Для NSIS требуется `makensis`. Для AppImage требуется среда выполнения целевой платформы; для кросс-упаковки графического приложения также необходимо предоставить дерево среды выполнения Linux. |
| Подписать релиз | Переносимое подписывание экспортированным ключом для Windows, macOS и DEB/RPM/Arch; нативные хранилища удостоверений также остаются доступными. | Для каждого удостоверения, формата и основной системы действуют свои ограничения. В AppImage и Void нет встроенного процесса подписывания. |
| Нотаризовать приложение macOS | Отправка с помощью командного API-ключа и прикрепление талона либо профиль связки ключей macOS. | Подходящая подпись Developer ID и метка времени по-прежнему обязательны. То, что созданные в Go тестовые подписи проходят нативные проверки, не доказывает, что Apple примет ваш релиз. |
| Собрать несколько программ | Основная программа с графическим интерфейсом, CLI или сервером и именованные вспомогательные программы. | Объявите пакеты и типы вспомогательных программ в YAML. Мастер не создаёт их исходный код. |
| Упаковать файлы, собранные в другом месте | `wails3 build setup --skip-build`. | Укажите в `build.output` соответствующие имена исполняемых файлов и архитектуры. Этот флаг задаёт однократный выбор для команды, а не постоянный параметр настройки. |
| Добавить автоматизацию выпуска | Именованные профили, ограниченные хуки жизненного цикла, кэширование и параллельная сборка пакетов. | Используйте литеральный YAML и объявленные скрипты проекта. Произвольное поведение Taskfile не является механизмом расширения Wake. |

Снова откройте `wails3 setup`, чтобы изменить профиль `setup`. Другие именованные профили и расширенные параметры редактируются в `wails.yaml`. Полные примеры и требования к пакетам приведены в [руководстве по сборке с YAML](/experimental/yaml-builds/). Приложениям с графическим интерфейсом по-прежнему нужны системные библиотеки целевой платформы; Pure Go не делает их полностью статическими приложениями.

Поддержка iOS и Android остаётся экспериментальной, требует SDK соответствующих платформ и CGo и не рассматривается в этом первом уроке по настольным приложениям. Мастер не делает мобильные сборки переносимыми между произвольными хост-системами.

## Миграция существующего проекта

Работайте в отдельной ветке или с копией рабочей версии проекта **Wails v3**. Это миграция конфигурации сборки, а не обновление с Wails v2. Сохраните результат существующей сборки и тесты, чтобы после активации можно было сравнить поведение.

@note{type="caution" title="Миграция охватывает не все случаи"}
Зафиксированная версия предварительной сборки может сообщать о блокирующих проблемах даже для проекта, созданного из текущих стандартных устаревших шаблонов. Известные примеры включают динамически выбираемые задачи и нераспознанное поле `exit_policy` в устаревшей конфигурации сборки. Не удаляйте необходимое вам поведение только ради успешной активации. Если анализатор не может представить ваш проект, оставьте для него устаревшую систему сборки и сообщите о диагностических сообщениях. Описанное выше руководство по созданию нового проекта не требует миграции.
@end

### 1. Проанализируйте проект, не изменяя активную сборку

Включите Wake и используйте предварительную версию CLI, указанную в начале этой страницы. Выполните следующую команду из корня существующего проекта:

```sh
wails3 migrate --dry-run
```

Ознакомьтесь с указанными поддерживаемыми параметрами и блокирующими проблемами. Анализатор читает устаревшие объявления, но не выполняет содержащиеся в них команды. Пробный запуск не создаёт активный манифест. Для диагностики в машиночитаемом формате используйте `wails3 migrate --json`; если также не требуется записывать черновик, используйте `--dry-run --json`.

### 2. Создайте и проверьте неактивное предложение

```sh
wails3 migrate
```

Будет создан **`wails.migrated.yaml`**, а не `wails.yaml`. Проверьте его вместе с существующими Taskfile и `build/config.yml`. Проверьте метаданные проекта, команды фронтенда, целевые архитектуры, содержимое пакетов, ресурсы и параметры подписания. Храните секреты в переменных окружения или в хранилище учётных данных.

Известные встроенные задачи можно сопоставить с нативными параметрами. Консервативные задачи жизненного цикла без аргументов, вызывающие принадлежащий проекту скрипт, могут стать хуками. Прочее достижимое пользовательское поведение задач является блокирующей проблемой: Wake не отбрасывает его без предупреждения и не запускает через Task в качестве запасного варианта.

Если черновик уже существует, миграция не перезапишет внесённые вами и проверенные изменения. Перед намеренной заменой или повторным созданием черновика сохраните его копию. Не переименовывайте заблокированный черновик в `wails.yaml`, чтобы обойти проверки активации. Сократите или замените неподдерживаемое устаревшее поведение и перед активацией повторите анализ. Если проект пока невозможно представить, оставьте для него устаревшую систему сборки и сообщите о недостающей поддержке.

### 3. Выполните явную активацию

После проверки черновика и устранения блокирующих проблем выполните:

```sh
wails3 migrate --activate --dry-run
wails3 migrate --activate
```

Первая команда проверяет возможность активации, не применяя её. Вторая повторно проверяет устаревшие объявления и валидирует черновик, а затем атомарно создаёт `wails.yaml`; при успешной активации неактивный `wails.migrated.yaml` удаляется. Taskfile, `build/config.yml`, скрипты и ресурсы остаются без изменений. С этого момента сборками Wake управляет активный манифест. Старые файлы не служат вторым источником конфигурации.

В некоторых старых проектах уже есть содержащий только метаданные `wails.yaml` с разделом верхнего уровня `info:`. Хотя этот файл не является нативным манифестом Wake, он всё же занимает путь назначения для активации. Перед активацией сохраните этот устаревший файл и намеренно переместите его: средство миграции не перезапишет и не переименует его за вас.

### 4. Проверьте приложение после миграции

```sh
wails3 config check
wails3 build
wails3 dev
```

Сравните приложение и содержимое пакетов с предыдущей сборкой, включая пользовательское поведение при выпуске. Запустите тесты проекта. Явно проверьте каждый перенесённый профиль, например `wails3 config check release` и `wails3 build release`, если черновик содержит профиль `release`.

Теперь можно выполнить `wails3 setup`, чтобы добавить или заменить отдельный профиль `setup`. Эта команда не выбирает и не редактирует существующий профиль `release` автоматически.

### Если эксперимент нужно прекратить

Удаление переменной `WAILS_EXP_USE_WAKE` отключает экспериментальную функцию, однако активный `wails.yaml` по-прежнему блокирует автоматическую маршрутизацию через Taskfile. При недопустимом YAML работа также завершается с ошибкой. Команды обратной миграции нет.

Чтобы вернуться к прежнему рабочему процессу, восстановите в системе управления версиями полную ревизию проекта до миграции, включая отсутствие активного манифеста, и используйте совместимые с ней CLI и зависимости. Перед этим сохраните все необходимые новые изменения исходного кода. Отдельная ветка для эксперимента значительно упрощает такое осознанное восстановление.

## Диагностика проблем и отправка обратной связи

| Симптом | Что проверить в первую очередь |
| --- | --- |
| При настройке открывается общий мастер | Задайте `WAILS_EXP_USE_WAKE` в терминале, из которого выполняется запуск, и проверьте, какой исполняемый файл `wails3` находится в `PATH`. |
| При настройке предлагается выполнить миграцию | Вы открыли устаревший проект или шаблон сообщества с устаревшей конфигурацией. Перед активацией проверьте миграцию. |
| Сохранённая сборка сообщает об отсутствующих инструментах | При сохранении записывается намерение. Вернитесь в раздел **«Инструменты»**, устраните несоответствия требованиям к хост-системе и повторите проверку. |
| Исполняемый файл, созданный кросс-компиляцией, не запускается в этой системе | Запустите его в выбранной операционной системе с выбранной архитектурой; для локальной разработки используйте целевую платформу хост-системы. |
| В режиме готовых бинарных файлов не удаётся найти бинарный файл | Проверьте [имена и пути готовых бинарных файлов](/experimental/yaml-builds/#use-prebuilt-desktop-executables), включая подкаталоги для нескольких целевых платформ. |
| Изменение манифеста приводит к ошибке | Выполните `wails3 config check` для соответствующего профиля и следуйте диагностическому сообщению для поля. Wake не использует Taskfile в качестве запасного варианта. |

Перед запуском проверьте сборку с помощью `wails3 build setup --plan --json`.
`wails3 config check` проверяет конфигурацию, а `wails3 eject` записывает неактивный снимок `wails.ejected.yaml`, не изменяя активный манифест.
Перед публикацией вывода команды проверьте его: пути проекта и расположение учётных данных могут раскрыть сведения о вашей локальной среде.

Оставьте отзыв в [обсуждениях экспериментов](https://github.com/wailsapp/wails/discussions/categories/experiments) или [сообщите о воспроизводимой ошибке](https://github.com/wailsapp/wails/issues). Укажите ревизии CLI и фреймворка, ОС и архитектуру хост-системы, выбранную целевую платформу, точную команду, сведения о выборе Pure Go и соответствующее диагностическое сообщение. Уточните, на каком этапе произошёл сбой: при компиляции, упаковке, подписании или запуске приложения. При необходимости приложите минимальный манифест без секретов и вывод `wails3 doctor`.

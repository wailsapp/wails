@note{type="caution" title="Экспериментальная предварительная версия"}
Первая принятая версия поддерживает только литеральную конфигурацию. В рамках этого эксперимента также создаётся прототип ограниченных хуков жизненного цикла, чтобы оценить их структуру до предложения к выпуску. Пользовательские этапы, выражения YAML и типизированные вызовы инструментов Wails пока отложены. Существующие проекты продолжают использовать Taskfile, пока вы явно не активируете проверенную миграцию.
@end

## Включение сборок YAML

Задайте `WAILS_EXP_USE_WAKE` в каждом терминале, из которого запускаются экспериментальные команды. Для Bash или Zsh:

```bash
export WAILS_EXP_USE_WAKE=1
```

Для PowerShell:

```powershell
$env:WAILS_EXP_USE_WAKE = '1'
```

Подключение определяется наличием переменной: эксперимент включается даже при пустом значении или значении `false`. Чтобы отключить эксперимент, удалите переменную (`unset WAILS_EXP_USE_WAKE` в Bash/Zsh или `Remove-Item Env:WAILS_EXP_USE_WAKE` в PowerShell). После активации `wails.yaml` команды требуют повторного включения Wake и никогда не возвращаются к Taskfile. Без этой переменной маршрутизация сборки и разработки через YAML, а также создание проектов YAML отключены; команды `migrate`, `config` и `eject` недоступны. Проекты, которые ещё не были перенесены, продолжают работать через отдельную встроенную среду выполнения Task.

## Настройка проекта

Включив экспериментальную функцию, добавьте `wails.yaml` в корень проекта. Наличие этого файла выбирает нативную систему сборки и заставляет Wails игнорировать все Taskfile в данном проекте. Не отключайте эту функцию при выполнении всех приведённых ниже команд. Строка режима схемы обеспечивает автодополнение и встроенную проверку в редакторах с поддержкой языкового сервера YAML.

```yaml
# yaml-language-server: $schema=https://v3.wails.io/schemas/wails.v3.json
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
frontend:
  directory: frontend
  install: [pnpm, install, --frozen-lockfile]
  build: [pnpm, run, build]
  dev: [pnpm, run, dev]
  output: frontend/dist
build:
  output: bin
  trim_path: true
  strip: true
profiles:
  release:
    targets:
      linux/amd64:
        formats: [deb, rpm, appimage]
```

Запустите стандартную сборку для текущей хост-системы или полный именованный запрос на выпуск:

```bash
wails3 build
wails3 build release
```

Для разовой сборки выберите разделённые запятыми целевые платформы и форматы, не добавляя профиль:

```bash
wails3 build --targets linux/amd64 --formats deb,rpm
```

## Кросс-компиляция настольных приложений

Для экспериментального настольного бэкенда на чистом Go задайте `CGO_ENABLED: "0"` в среде сборки. Wake выбирает тег `purego` для программ с графическим интерфейсом под macOS и Linux и напрямую использует Go на хостах Windows, macOS и Linux. В этом режиме для сборки настольных исполняемых файлов не требуются Docker, эмуляция, компилятор C или SDK целевой платформы. Зависимости приложения также должны поддерживать `CGO_ENABLED=0`.

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
build:
  output: bin
  environment:
    CGO_ENABLED: "0"
```

```bash
wails3 build --targets windows/amd64,windows/arm64,linux/amd64,linux/arm64,darwin/amd64,darwin/arm64
wails3 build --targets darwin/universal --formats dmg
```

Вторая команда объединяет обе архитектуры macOS и создаёт неподписанный DMG с помощью Go. Её можно выполнить на любой поддерживаемой настольной хост-системе. Подписание кода и нотариальное заверение Apple остаются отдельными операциями, выполняемыми в macOS.

Итоговый режим выбирается независимо для каждого исполняемого файла. Объявленное значение `build.environment.CGO_ENABLED`, среда целевой платформы или среда бинарного файла переопределяют значение терминала, из которого вызвана команда. В противном случае при явно выбранном теге `purego`, программе CLI/сервере или целевой платформе Windows по умолчанию используется `0`; для программ с графическим интерфейсом под macOS и Linux по умолчанию используется `1`. `--plan --json` сообщает выбранные для каждого исполняемого файла компилятор, режим CGo и теги. При кросс-компиляции создаются файлы для целевой платформы; для запуска несовместимой настольной цели по-прежнему требуется соответствующая хост-система.

При использовании `CGO_ENABLED=1` Wake сначала применяет совместимый нативный набор инструментов или настроенный кросс-компилятор `CC`, затем — Zig для кросс-сборки под Windows, если он доступен, после чего — существующий резервный вариант с Docker/Podman там, где он поддерживается. При явном выборе `CC` необходимо предоставить компилятор, библиотеки и sysroot целевой платформы; сам по себе Zig не предоставляет sysroot Linux с GTK/WebKit. Для упаковки и подписания могут потребоваться дополнительные инструменты, описанные ниже. Для мобильных целевых платформ требуются CGo и соответствующие SDK.

Компиляция только средствами Go не включает системные библиотеки целевой платформы.
Для Linux-приложений с графическим интерфейсом, включая сопутствующие исполняемые файлы с графическим интерфейсом, по-прежнему требуется среда выполнения GTK/WebKitGTK, выбранная их тегами сборки. Её должны предоставлять зависимости пакета или соответствующая среда развёртывания. Пакеты, содержащие только CLI- или серверные приложения, по умолчанию не добавляют эти зависимости графического интерфейса; возможность явно переопределить зависимости сохраняется.

## Сборка нескольких исполняемых файлов

Проект определяет основную программу. Задайте в `project.package` её пакет Go (по умолчанию `.`), а в `project.kind` — `gui`, `cli` или `server` (по умолчанию `gui`). Дополнительные программы задаются именованными записями в разделе `binaries`:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
binaries:
  notes-tool:
    package: cmd/notes-tool
    kind: cli
    tags: [tools]
    ldflags: [-X, main.Mode=release]
    environment:
      CGO_ENABLED: "0"
profiles:
  release:
    targets:
      linux/amd64: {}
```

У каждой программы есть собственные входные данные компиляции и кэша. Импортированные пакеты проекта и встроенные файлы отслеживаются; изменение независимой программы не приводит к пересборке остальных. Дополнительные исполняемые файлы поддерживаются на настольных платформах и включаются в стандартные пакеты приложений и установщики. Содержимое заменяющих файлов пакетов, принадлежащих пользователю, определяется самими этими файлами.

```bash
wails3 build --binaries notes,notes-tool --jobs 4
wails3 build --binaries notes-tool --skip-frontend --skip-bindings
```

Именованный профиль представляет собой полный запрос; эти переопределения выбора следует использовать с анонимной сборкой. `--jobs` ограничивает число выполняющих работу процессов. Если выбраны только программы CLI/серверы, работа с фронтендом пропускается.

Чтобы прочитать версию без выполнения кода приложения, настройте и `project.version_file`, и `project.version_symbol`. Файл должен содержать статическое объявление строки Go. После этого литерал `project.version` можно опустить. Задайте `commit_symbol: main.Commit` для проекта или именованного бинарного файла, чтобы внедрить ревизию репозитория в строковую переменную этого исполняемого файла. Если запрошено внедрение коммита, отсутствие метаданных репозитория считается ошибкой.

Значение от `upx_level: 1` до `9` при необходимости сжимает выпускаемые исполняемые файлы Linux и Windows; ноль отключает сжатие. UPX должен быть установлен. В сборках для разработки и macOS сжатие не применяется. При ошибке компиляции или сжатия сохраняется ранее опубликованная программа.

## Упаковка и подписание для распространения

К хост-системе и инструментам для создания неподписанного пакета предъявляются иные требования, чем для подписания:

| Выходной формат | Хост-системы и инструменты для создания | Подписание |
| --- | --- | --- |
| MSIX для Windows | Windows, macOS или Linux; средство записи на Go, SDK Windows не требуется. | Хост Windows и инструменты подписания. |
| Установщик NSIS для Windows | Windows, macOS или Linux; требуется нативный для хост-системы `makensis`. | Хост Windows и инструменты подписания. |
| Приложение macOS и DMG | Windows, macOS или Linux; сборка средствами Go, объединение универсальных бинарных файлов и переносимое средство записи DMG. | macOS с инструментами и учётными данными Apple. |
| DEB, RPM, Arch и Void для Linux | Windows, macOS или Linux; нативные средства записи пакетов на Go. | DEB/RPM используют соответствующие внешние инструменты подписания; Arch использует описанный ниже инструмент подписания на Go. Выходной пакет Void не подписывается. |
| AppImage для Linux | Хост Linux с той же архитектурой, что и целевая платформа; внешние linuxdeploy и подключаемый модуль развёртывания GTK. | Встроенный процесс подписания AppImage отсутствует. |

Архивы Windows MSIX создаются непосредственно средствами Go; для создания неподписанного пакета не требуются Windows SDK или Docker. Для подписывания под Windows по-прежнему требуются компьютер с Windows и соответствующие средства подписывания. NSIS использует внешний компилятор NSIS и принимает определения в виде литералов через `packages.nsis.defines`. В macOS Wails задаёт локаль UTF-8 только дочернему процессу компилятора NSIS, если унаследованная им локаль не использует UTF-8; окружения терминала и приложения не изменяются. Стандартный установщик NSIS не включает загрузчик WebView2, если каждый упакованный исполняемый файл является CLI- или серверным приложением. Если основной или сопутствующий исполняемый файл имеет графический интерфейс, WebView2 сохраняется. Пользовательские сценарии NSIS сохраняют загрузчик для совместимости со своей логикой установки среды выполнения.

В Linux поддерживаются пакеты AppImage, DEB, RPM, Arch Linux и Void. Для AppImage сохраняется граница с внешними linuxdeploy и подключаемым модулем GTK. Задайте `packages.appimage.update_info`, чтобы запросить файл zsync, и `packages.appimage.checksum: true` — файл SHA256. Сопутствующие файлы восстанавливаются из кэша пакетов и указываются в квитанции артефактов вместе с AppImage. В настоящее время для упаковки AppImage требуется Linux, а архитектуры хоста и целевой платформы должны совпадать. Механизм обнаружения GTK не находит библиотеки, динамически загружаемые графическим интерфейсом на чистом Go, поэтому этот адаптер пока не поддерживает развёртывание такого интерфейса. Для этого режима сборки используйте один из форматов менеджеров пакетов Linux.

Пакеты Arch сохраняют предварительные версии в нативных метаданных пакета: например, `1.2.3-beta.2` преобразуется в `1.2.3beta.2-1`, которое при сортировке располагается перед окончательным выпуском. В зависимостях Void допустимы простые имена пакетов, такие как `gtk4`; они нормализуются до `gtk4>=0`. Явные сравнения версий и полные значения `name-version_revision` сохраняются. Используйте имена пакетов Void, а не имена файлов библиотек.

Чтобы создать пакет Arch и отделённую подпись, используйте экспортированный файл закрытого ключа PGP в текстовом формате и при необходимости укажите имя переменной среды с парольной фразой:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
build:
  environment:
    CGO_ENABLED: "0"
linux:
  signing:
    certificate: signing/private-key.asc
    credential: ARCH_SIGNING_PASSPHRASE
profiles:
  release:
    targets:
      linux/amd64:
        formats: [archlinux]
        sign: true
```

Задайте указанную переменную окружения в локальной среде или хранилище секретов CI, затем выполните `wails3 build release`. Для незашифрованного ключа опустите `credential`. Реализованный на Go механизм подписи работает на всех поддерживаемых настольных платформах и не требует GPG. Он публикует исходный `.pkg.tar.zst` и соседний файл `.pkg.tar.zst.sig`; оба файла по отдельности регистрируются в квитанции об артефактах. Содержимое ключа не помещается ни в промежуточную область, ни в кеш сборки. Подписи и результаты их публикации никогда не используются повторно из кеша. При сбое подписания сохраняется ранее опубликованная пара, а если установить любой из файлов не удаётся, публикация откатывает оба файла. Однако это не делает два переименования в файловой системе атомарными для параллельных читателей.

Пакеты приложений macOS включают вспомогательные программы. Задайте `darwin.microphone_usage_description`, чтобы добавить текст об использовании, а при отсутствии пользовательского файла разрешений — также разрешение на аудиовход. Пользовательские исходные файлы plist и разрешений остаются без изменений. Для подписания и нотариального заверения в macOS используются имеющиеся инструменты и учётные данные Apple; для нотариального заверения требуется настоящий профиль нотариальной службы. Подписанные выходные файлы сохраняют расширение своей платформы, например `notes.signed.app` и `notes.signed.dmg`.

## Управление в режиме разработки

Во время `wails3 dev` введите команду и нажмите Enter:

| Команда | Действие |
| --- | --- |
| `r` | Принудительно пересобрать и перезапустить, включая неизменённый бэкенд. |
| `b` | Повторно сгенерировать привязки и пересобрать. |
| `f` | Перезапустить фронтенд. |
| `c` | Очистить терминал. |
| `q` | Остановить сеанс и его дочерние процессы. |
| `h` | Показать команды управления. |

При неудачной сборке текущее приложение продолжает работать. Для команд управления требуется интерактивный терминал; передача входных данных по каналу не изменяет поведение сеанса.

## Проверка плана работ перед запуском

При проверке плана разрешается тот же неизменяемый граф, который используется при выполнении. Текст предназначен для людей, а JSON представляет собой версионируемый машиночитаемый контракт.

```bash
wails3 build release --plan
wails3 build release --plan --json
```

## Проверка конфигурации без сборки

Используйте специальную команду предварительной проверки в CI, в задаче редактора или перед фиксацией конфигурации. Если профиль не указан, она проверяет базовый манифест и каждый именованный профиль; если профиль указан, проверяется только соответствующий полный запрос:

```bash
wails3 config check
wails3 config check release
```

Для ошибок синтаксиса, схемы, семантики, путей, целевой платформы, формата, подписания, планировщика и возможностей хоста, определённых конфигурацией, используется тот же механизм вывода диагностики, что и в Build и Dev. Диагностические сообщения указывают поле и диапазон в исходном файле, выводят строку исходного текста и каретку, а при необходимости содержат подсказку по исправлению. Значения переменных окружения скрываются во фрагментах исходного текста в диагностике. Ошибки хоста, вызванные исключительно параметрами командной строки, остаются обычными ошибками команды и не выдаются ошибочно за недопустимый YAML.

## Использование ресурсов проекта

Пути в манифесте ссылаются на принадлежащие вам файлы, например значки, манифесты платформ, шаблоны пакетов и сценарии сопровождающего. Wails никогда не изменяет эти исходные файлы. Перед использованием инструментом Wails копирует их в одноразовую рабочую область `.wails/`. Итоговые артефакты помещаются в `build.output`, а проверенная квитанция записывается в `.wails/artifacts/receipt.json`.

## Развёртывание на Android

Профили Android для рабочей среды создают AAB. Для локального развёртывания Wails внутренними средствами собирает отладочный APK для конкретного ABI, устанавливает его через ADB и запускает приложение:

```bash
wails3 android devices
wails3 android run --device SERIAL
wails3 android run --emulator AVD_NAME
```

Если селектор не указан явно, интерактивный терминал предлагает выбрать подключённое устройство или настроенное виртуальное устройство Android. Если автоматизации доступно несколько целей, необходимо указать `--device` или `--emulator`.

Подключите поток журналов уровня приложения и отслеживайте цель, пока приложение не завершится или вы не нажмёте Ctrl+C:

```bash
wails3 android run --emulator AVD_NAME --logs
wails3 android run --emulator AVD_NAME --logs --stop-emulator
```

Подключённые запуски продолжают отслеживание после перезапуска приложения и сообщают об отключении цели или её переходе в автономный режим. По умолчанию эмуляторы продолжают работать для быстрой итеративной разработки. Параметр `--stop-emulator` задаётся явно, требует `--logs` и при завершении подключённого сеанса останавливает только цель-эмулятор. Если Wails запускает новый эмулятор, но ожидание его готовности после загрузки завершается ошибкой или отменяется, соответствующий процесс завершается автоматически.

## Запуск ограниченных обработчиков жизненного цикла

Экспериментальный интерфейс обработчиков запускает по одному принадлежащему проекту сценарию на каждой объявленной фазе. Обработчик — не команда оболочки: Wails запускает файл напрямую, по умолчанию из корня проекта, если не задано `directory`.

На хостах Unix сценарий должен быть исполняемым и начинаться с шебанга. Хосты Windows принимают сценарии `.cmd`, `.bat` и `.ps1` через фиксированные адаптеры интерпретаторов; ни на одной из платформ Wails не разбирает встроенную команду оболочки.

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
hooks:
  before_build:
    script: scripts/generate-version.sh
  after_package:
    script: scripts/check-packages.sh
profiles:
  release:
    targets:
      linux/amd64: {}
```

Поддерживаются фазы `before_build`, `after_build`, `before_package`, `after_package`, `before_sign` и `after_sign`. В зависимости от назначения обработчики сборки запускаются один раз для общего проекта или по одному разу для каждой цели. Обработчики упаковки и подписания образуют барьеры вокруг всех форматов, запрошенных для цели, при этом операции с форматами внутри барьера продолжают выполняться параллельно.

Обработчики получают одну переменную окружения, управляемую Wails: `WAILS_HOOK_CONTEXT_FILE`. Она указывает на защищённый JSON-файл, содержащий версионируемый контекст вызова:

```json
{
  "version": 1,
  "phase": "after_build",
  "command": "build",
  "scope": "target",
  "project_dir": "/work/notes",
  "working_directory": "/work/notes",
  "profile": "release",
  "target": { "os": "linux", "arch": "amd64" },
  "output": "/work/notes/bin/notes",
  "declared_outputs": ["/work/notes/generated/version.go"]
}
```

Контекст содержит разрешённые пути, но никогда не копирует унаследованное окружение процесса или секреты. Wails атомарно создаёт его в `.wails/hooks/context/` с правами доступа к файлу только для владельца. После успешного завершения или отмены файл удаляется. При ошибке он сохраняется для диагностики, а путь к нему включается в сообщение об ошибке. Ненулевой код выхода приводит к сбою обычного шага Plan, а при отмене завершается группа процессов обработчика.

По умолчанию обработчики запускаются при каждом вызове. Включайте кеширование, только если у сценария полностью объявлены входы и выходы:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
hooks:
  before_build:
    script: scripts/generate-version.sh
    cache: true
    inputs: [version.txt]
    outputs: [generated/version.go]
profiles:
  release:
    targets:
      linux/amd64: {}
```

Сам сценарий и его режим исполняемого файла являются неявными входами. Несколько выходов должны находиться в одном каталоге, отличном от корневого; этот каталог представляет собой ограниченный артефакт, который Wails регистрирует и восстанавливает. Корень выходных данных не может содержать сценарий или объявленный вход, а кешированные деревья выходных данных могут содержать только обычные файлы и каталоги — никаких символических ссылок или специальных файлов. Обработчик, запускаемый всегда, запрещает кеширование последующих операций, поскольку для необъявленных побочных эффектов невозможно безопасно вычислить отпечаток. Кешируемый обработчик сохраняет кеширование последующих операций благодаря объявленной идентичности своего артефакта.

## Миграция существующего проекта

Создайте и проверьте неактивный черновик:

```bash
wails3 migrate
wails3 migrate --dry-run
wails3 migrate --json
```

Консервативные задачи жизненного цикла без аргументов, запускающие принадлежащий проекту сценарий, преобразуются в обработчики. Прочее достижимое пользовательское поведение Taskfile указывается как блокирующая проблема. После проверки `wails.migrated.yaml` явно активируйте его:

```bash
wails3 migrate --activate
```

При активации `wails.yaml` создаётся атомарно. Taskfiles, `build/config.yml`, сценарии и ресурсы не удаляются, не переименовываются и не изменяются. Недопустимый YAML приводит к ошибке YAML; перехода к устаревшему маршруту никогда не происходит.

## Материализация всех значений по умолчанию

Чтобы проверить или скопировать полную разрешённую конфигурацию, запишите неактивный снимок:

```bash
wails3 eject
```

При этом создаётся `wails.ejected.yaml`. Активная конфигурация никогда не перезаписывается.

## Период совместимости

`wails3 package` и `wails3 sign` — устаревшие псевдонимы одного и того же планировщика; в новой автоматизации следует использовать `wails3 build` с профилем или форматами. Развёртывание привязано к выпускам: в первом выпуске YAML становится основным вариантом для новых проектов, в следующем появляется предупреждение при маршрутизации через устаревший Taskfile, а ещё в следующем выполнение Taskfile удаляется вместе с псевдонимами. Для каждого перехода матрица приёмочных тестов на нативных хостах для соответствующего выпуска должна быть полностью успешной.

Все поля, типы, значения по умолчанию и правила применимости приведены в сгенерированном [`wails.yaml`справочнике полей](/reference/wails-yaml-fields/).

В [`wails3 run`справочнике по конфигурации](/reference/wails-yaml-run/) описаны значения по умолчанию для локального запуска, переопределения для платформ и резервный вариант `go run .` при отсутствии манифеста.

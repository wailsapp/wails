@note{type="caution" title="Экспериментальная предварительная версия"}
Первая принятая версия поддерживает только конфигурацию с литеральными значениями. В рамках этого эксперимента также создаётся прототип ограниченных по времени перехватчиков жизненного цикла, чтобы оценить их форму до предложения включить их в выпуск. Пользовательские этапы, выражения YAML и типизированные вызовы инструментов Wails пока отложены. Существующие проекты продолжают использовать Taskfile, пока вы явно не активируете проверенную миграцию.
@end

Впервые работаете с Wake? Начните с [руководства по началу работы](/experimental/wake/).
В нём описаны ограничения эксперимента, все экраны настройки проекта и сборки, первая локальная сборка и проверенная миграция. На этой странице более подробно рассматриваются отдельные процессы сборки, упаковки и настройки.

## Включение сборок YAML

Задайте `WAILS_EXP_USE_WAKE` в каждом терминале, из которого запускаются экспериментальные команды. Для Bash или Zsh:

```bash
export WAILS_EXP_USE_WAKE=1
```

Для PowerShell:

```powershell
$env:WAILS_EXP_USE_WAKE = '1'
```

Подключение определяется наличием переменной: функцию включает даже пустое значение или `false`. Чтобы отключить эксперимент, удалите переменную (`unset WAILS_EXP_USE_WAKE` в Bash/Zsh или `Remove-Item Env:WAILS_EXP_USE_WAKE` в PowerShell). После активации `wails.yaml` для выполнения команд необходимо снова включить Wake; возврата к Taskfile не происходит.
Без этой переменной маршрутизация сборки и разработки через YAML, а также создание проектов YAML отключены, а команды `migrate`, `config` и `eject` недоступны.
Проекты, которые ещё не были перенесены, продолжают использовать отдельную встроенную среду выполнения Task.

## Настройка проекта

Чтобы создать и настроить проект в браузере, запустите `wails3 init -ui` с включённой экспериментальной функцией и следуйте [руководству по Wake](/experimental/wake/). Параметры проекта хранятся в `wails.yaml`; чтобы изменить существующий проект, отредактируйте этот файл. `wails3 setup` задаёт общие настройки, инструменты и учётные данные для подписи.

После включения экспериментальной функции добавьте `wails.yaml` в корень проекта. Наличие этого файла выбирает нативную систему сборки, и Wails игнорирует все Taskfile в данном проекте. Не отключайте эту функцию при выполнении всех приведённых ниже команд. Строка режима схемы включает автодополнение и встроенную проверку в редакторах с поддержкой языкового сервера YAML.

```yaml
# yaml-language-server: $schema=https://v3.wails.io/schemas/wails.v3.json
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
frontend:
  directory: frontend
  install: [pnpm, install, --frozen-lockfile]
  build: [pnpm, run, build]
  dev: [pnpm, run, dev]
  output: frontend/dist
build:
  output: bin
  trim_path: true
  strip: true
profiles:
  release:
    targets:
      linux/amd64:
        formats: [deb, rpm, appimage]
```

Запустите стандартную сборку для текущей платформы или полный именованный запрос на выпуск:

```bash
wails3 build
wails3 build release
```

Для однократной сборки выберите разделённые запятыми целевые платформы и форматы, не добавляя профиль:

```bash
wails3 build --targets linux/amd64 --formats deb,rpm
```

## Кросс-компиляция настольных приложений

Для экспериментального настольного бэкенда, полностью реализованного на Go, задайте `CGO_ENABLED: "0"` в окружении сборки. Wake выбирает тег `purego` для программ с графическим интерфейсом в macOS и Linux и напрямую использует Go на хостах Windows, macOS и Linux. В этом режиме для сборки настольных исполняемых файлов не требуются Docker, эмуляция, компилятор C или SDK целевой платформы. Зависимости приложения также должны поддерживать `CGO_ENABLED=0`.

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
build:
  output: bin
  environment:
    CGO_ENABLED: "0"
```

```bash
wails3 build --targets windows/amd64,windows/arm64,linux/amd64,linux/arm64,darwin/amd64,darwin/arm64
wails3 build --targets darwin/universal --formats dmg
```

Вторая команда объединяет обе архитектуры macOS и создаёт неподписанный DMG средствами Go. Её можно выполнить на любой поддерживаемой настольной системе.

Итоговый режим выбирается отдельно для каждого исполняемого файла. Объявленное значение `build.environment.CGO_ENABLED`, окружение целевой платформы или окружение исполняемого файла переопределяет значение из терминала, в котором запущена команда. В остальных случаях при явно выбранном теге `purego`, программе CLI/сервере или целевой платформе Windows по умолчанию используется `0`, а для программ с графическим интерфейсом в macOS и Linux — `1`. `--plan --json` выводит выбранный компилятор, режим CGo и теги для каждого исполняемого файла. При кросс-компиляции создаются файлы для целевой платформы; для запуска несовместимой настольной цели по-прежнему требуется соответствующая хост-платформа.

При использовании `CGO_ENABLED=1` Wake сначала применяет совместимый нативный набор инструментов или настроенный кросс-компилятор `CC`, затем, если доступен, Zig для кросс-сборки под Windows, а после этого — существующий резервный вариант с Docker/Podman там, где он поддерживается. При явном указании `CC` должны быть предоставлены целевой компилятор, библиотеки и sysroot; сам по себе Zig не предоставляет sysroot Linux с GTK/WebKit. Для упаковки и подписания могут потребоваться дополнительные инструменты, описанные ниже. Для мобильных целевых платформ требуются CGo и соответствующие платформенные SDK.

Компиляция только средствами Go не включает в пакет системные библиотеки целевой платформы. Для приложений Linux с графическим интерфейсом, включая вспомогательные исполняемые файлы с графическим интерфейсом, по-прежнему требуется среда выполнения GTK/WebKitGTK, выбранная их тегами сборки. Её должны предоставить зависимости пакета или подходящее окружение развёртывания. Пакеты, содержащие только CLI/сервер, по умолчанию не добавляют эти зависимости графического интерфейса; явное переопределение зависимостей остаётся доступным.

## Сборка нескольких исполняемых файлов

В проекте определяется основная программа. Укажите её пакет Go в `project.package` (по умолчанию `.`), а в `project.kind` задайте `gui`, `cli` или `server` (по умолчанию `gui`).
Дополнительные программы задаются именованными элементами в разделе `binaries`:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
binaries:
  notes-tool:
    package: cmd/notes-tool
    kind: cli
    tags: [tools]
    ldflags: [-X, main.Mode=release]
    environment:
      CGO_ENABLED: "0"
profiles:
  release:
    targets:
      linux/amd64: {}
```

Для каждой программы используются отдельные входные данные компиляции и кеша. Импортированные пакеты проекта и встроенные файлы отслеживаются; изменение независимой программы не приводит к повторной сборке остальных. Дополнительные исполняемые файлы поддерживаются на настольных платформах и включаются в стандартные пакеты приложений и установщики. Содержимое заменяющих файлов пакетов, принадлежащих пользователю, определяется самими этими файлами.

```bash
wails3 build --binaries notes,notes-tool --jobs 4
wails3 build --binaries notes-tool --skip-frontend --skip-bindings
```

Именованный профиль представляет собой полный запрос; эти переопределения выбора следует использовать с анонимной сборкой. `--jobs` ограничивает количество параллельных исполнителей. Если выбраны только программы CLI/серверы, работа с фронтендом пропускается.

Чтобы прочитать версию без выполнения кода приложения, настройте и `project.version_file`, и `project.version_symbol`. Файл должен содержать статическое объявление строки Go. После этого литерал `project.version` можно не указывать. Задайте `commit_symbol: main.Commit` для проекта или именованного исполняемого файла, чтобы записать ревизию репозитория в строковую переменную этого исполняемого файла. Если запрошена запись коммита, отсутствие метаданных репозитория считается ошибкой.

Значение от `upx_level: 1` до `9` позволяет при необходимости сжимать исполняемые файлы выпуска для Linux и Windows; нулевое значение отключает сжатие. Для этого должен быть установлен UPX. В сборках для разработки и macOS сжатие не применяется. При сбое компиляции или сжатия ранее опубликованная программа сохраняется.

## Упаковка и подписание для распространения

### Использование предварительно собранных настольных исполняемых файлов

Используйте `--skip-build`, если исполняемые файлы уже созданы другой системой сборки или заданием CI:

```bash
wails3 build --targets linux/amd64 --formats deb,rpm --skip-build
wails3 run --skip-build -- --example-mode
```

Поместите каждый исполняемый файл в `build.output` (по умолчанию — `bin`), используя `project.binary_name` для основного исполняемого файла, а имя каждой записи `binaries` — для вспомогательных файлов. Имена файлов для Windows должны оканчиваться на `.exe`. При вызове для нескольких целевых платформ файлы каждой из них считываются из подкаталога `<os>-<arch>`. Для приложения с графическим интерфейсом macOS Wake считывает необработанный исполняемый файл из `bin/<name>`, если он существует, иначе — из `bin/<name>.app/Contents/MacOS/<name>`. Входной файл `darwin/universal` должен содержать срезы исполняемого файла как для amd64, так и для arm64.

Wake проверяет тип файла и архитектуру целевой платформы, копирует исполняемые файлы в созданную рабочую область и отслеживает их содержимое для кеширования пакетов. Отсутствующие, несовместимые или являющиеся символическими ссылками входные исполняемые файлы приводят к ошибке: Wake не пересобирает их и не восстанавливает прежние входные данные. Предоставленные исполняемые файлы не перезаписываются, и их права доступа не изменяются с помощью chmod. Изменение любого исполняемого файла инвалидирует использующие его пакеты.

В этом режиме пропускаются установка и сборка фронтенда, привязки, компиляция Go, UPX и перехватчики `before_build`/`after_build`. При этом по-прежнему создаются ресурсы пакета, формируются пакеты приложений macOS и выполняются настроенные перехватчики упаковки и подписания. Для инструментов упаковки и подписания по-прежнему действуют требования из приведённой ниже таблицы; инструменты сборки Go и фронтенда не требуются. Метаданные пакета берутся из текущего манифеста, включая `version_file`, если это значение настроено; версия не определяется по исполняемому файлу. Используйте согласованные настройки сборки и упаковки, в том числе тип GUI или CLI.

`wails3 package --skip-build` также поддерживается. При использовании `wails3 run` аргументы запуска и переменные окружения продолжают применяться, а исполняемый файл должен запускаться на хост-платформе. Для этого режима требуется активный проект YAML; он поддерживает только целевые настольные платформы для рабочей среды и не применяется к сеансам разработки или упаковке мобильных приложений.

Требования к хост-платформе и инструментам для создания неподписанного пакета отличаются от требований для подписания:

Полезная нагрузка IPA и ZIP-архивы для нотариального заверения в macOS записываются средствами Go с сохранением путей внутри пакета, разрешений на исполнение и относительных символических ссылок. Ни для одной из этих операций не требуется внешний исполняемый файл `zip` или `ditto`. Эти архивы содержат файлы приложения, а не метаданные Finder или вилки ресурсов; при подписании в macOS такие метаданные всё равно удаляются, поскольку они делают подписанные пакеты недействительными.

| Выходной формат | Хост-платформы и инструменты для создания | Подписание |
| --- | --- | --- |
| Windows MSIX | Windows, macOS или Linux; средство записи на Go, Windows SDK не требуется. | Подписание средствами Go с использованием экспортированного RSA PFX на любой настольной системе; для удостоверений из хранилища сертификатов или поставщика требуется Windows SignTool. |
| Установщик Windows NSIS | Windows, macOS или Linux; требуется нативный для хост-платформы `makensis`. | Подписание PE средствами Go с использованием экспортированного RSA PFX на любой настольной системе; для удостоверений из хранилища сертификатов или поставщика требуется Windows SignTool. |
| Приложение macOS и DMG | Windows, macOS или Linux; сборка средствами Go, объединение универсальных исполняемых файлов и переносимое средство записи DMG. | Подписание средствами Go с использованием экспортированного удостоверения RSA PKCS#12 либо специальной подписи ad hoc; для удостоверений из связки ключей по-прежнему используются инструменты macOS. Нотариальное заверение с ключом API и прикрепление билета выполняются средствами Go. |
| Linux DEB, RPM, Arch и Void | Windows, macOS или Linux; нативные средства создания пакетов на Go. | Для экспортированных ключей OpenPGP используется встроенный подписывающий модуль DEB/RPM/Arch. Для устаревших идентификаторов ключей DEB/RPM требуются внешние инструменты. Пакет Void не подписывается. |
| Linux AppImage | Windows, macOS или Linux; развёртывание и запись SquashFS средствами Go, а также среда выполнения AppImage для целевой архитектуры. Для кросс-пакетирования GUI необходимо предоставить дерево среды выполнения Linux. | Встроенный процесс подписания AppImage отсутствует. |

При создании подписанных DMG Wake обычно подписывает закрытую копию приложения до того, как средство записи на Go сожмёт образ, а затем подписывает сам образ. Это позволяет не подключать, не расширять и не сжимать DMG повторно с помощью `hdiutil`. Подписание выполняется при каждом запросе; подписанный пакет не используется повторно из кеша сборки. В проектах с обработчиками `after_package` или `before_sign` сохраняется исходная последовательность «упаковка, затем подписание», включая `hdiutil`, поэтому изменения, внесённые этими обработчиками в неподписанный образ, сохраняются. Этот совместимый с обработчиками способ редактирования образа требует macOS и `hdiutil`.

Для переносимого подписания Apple задайте `darwin.signing.identity: "-"`, чтобы использовать специальную подпись ad hoc, либо укажите в `darwin.signing.certificate` экспортированное удостоверение RSA PKCS#12. В `darwin.signing.credential` задаётся имя переменной среды с паролем. Для подписей на основе сертификатов используется общая реализация PFX/CMS на Go; закрытый ключ не экспортируется из связки ключей автоматически. Тонкие и универсальные исполняемые файлы, вложенные пакеты приложений, фреймворки и DMG успешно прошли строгие встроенные проверки подписей Apple, включая отклонение изменённых данных, с использованием созданных тестовых удостоверений.

Для нотариального заверения экспортированному удостоверению Developer ID также требуется совместимая служба 3161 `darwin.signing.timestamp_server` по RFC. Общий модуль проверки принимает поддерживаемые профили меток времени SHA-2 и отклоняет неподдерживаемые устаревшие алгоритмы. Специальную подпись ad hoc нельзя нотариально заверить. Встроенная проверка формата сертификата не подтверждает фактическое доверие к Developer ID и принятие отправленного материала Apple.

Реализованный на Go модуль прикрепления билетов проверяет подлинность подписи билета Apple и убеждается, что билет охватывает все архитектуры, прежде чем прикрепить его к закрытой копии. Он использует наблюдаемый протокол доставки билетов, который Apple не публикует как поддерживаемый API. Он не заменяет текущие проверки отзыва сертификатов Gatekeeper. Выходные пакеты приложений и подписанные DMG успешно прошли встроенную проверку `stapler validate` и строгие проверки подписей.

Архивы Windows MSIX создаются непосредственно на Go; для создания неподписанного пакета не требуются Windows SDK или Docker. Экспортированные удостоверения RSA PFX позволяют непосредственно на Go подписывать исполняемые файлы Windows и отдельные пакеты MSIX на любой настольной системе. В `windows.signing.certificate` укажите путь к PFX относительно проекта, а в `windows.signing.credential` — переменную среды с его паролем. Поддерживаются экспорты AES/PBKDF2 и устаревшие экспорты 3DES; экспорты RC2 необходимо повторно экспортировать либо подписывать с помощью резервного нативного средства Windows SignTool. Для удостоверений из хранилища сертификатов или поставщика, а также для подписания MSI требуется Windows SignTool. По умолчанию используется служба меток времени DigiCert; перед публикацией подписанных выходных файлов метки времени проверяются. Ограничения форматов приведены в [руководстве по подписанию](/guides/build/signing/).
NSIS использует внешний компилятор NSIS и принимает литеральные определения через `packages.nsis.defines`. В macOS, если унаследованная локаль не использует UTF-8, Wails задаёт локаль UTF-8 только для дочернего процесса компилятора NSIS; среды терминала и приложения не изменяются. Стандартный установщик NSIS не включает загрузчик WebView2, если каждый исполняемый файл в пакете представляет собой CLI или сервер. Если основной или вспомогательный исполняемый файл имеет графический интерфейс, WebView2 сохраняется. В пользовательских сценариях NSIS загрузчик сохраняется для совместимости с их собственной логикой установки среды выполнения.

В Linux поддерживаются пакеты AppImage, DEB, RPM, Arch Linux и Void. Wake собирает AppImage непосредственно средствами Go, включая развёртывание GTK/WebKit, сжатие SquashFS и создание zsync. Он не вызывает linuxdeploy, подключаемый модуль GTK, appimagetool или mksquashfs. Для целевой архитектуры загружается закреплённая версия среды выполнения AppImage типа 2 с проверенной контрольной суммой; вместо неё можно выбрать в `packages.appimage.runtime_path` ELF-файл среды выполнения по пути относительно проекта.

В Linux источником библиотек по умолчанию служит корневая файловая система основной системы. Чтобы упаковать GUI для другой архитектуры либо из Windows или macOS, задайте в `packages.appimage.runtime_root` путь относительно проекта к корневому дереву целевой системы Linux, содержащему её библиотеки, скомпилированные схемы и кеши модулей. Требуется полная структура корневой системы, включая `usr/`, а не сам каталог `usr/`. Используйте среду выполнения из самого старого дистрибутива Linux, который планируете поддерживать. Wake анализирует импорты ELF и явные профили GTK/WebKit, не запуская целевые программы. Он включает выбранное замыкание зависимостей, но не glibc и не динамический загрузчик. После обновления среды выполнения хеши содержимого библиотек и ресурсов делают кеш пакетов недействительным.

Поддерживаются сборки GUI исключительно на Go. Для исполняемых файлов с GUI, собранных с `gtk3`, Wake выбирает GTK 3, а во всех остальных случаях — GTK 4, в том числе для сопутствующих GUI-программ CLI или сервера. Все исполняемые файлы с GUI в одном образе должны использовать одну версию GTK. Для предварительно собранных двоичных файлов параметр `packages.appimage.gtk_version` позволяет явно выбрать `3` или `4`; импортированные библиотеки CGo должны соответствовать этому выбору.

Задайте `packages.appimage.update_info`, чтобы запросить файл zsync, и `packages.appimage.checksum: true` — чтобы запросить файл SHA256. Сопутствующие файлы восстанавливаются из кеша пакетов и указываются в квитанции артефакта вместе с AppImage. Упаковка в Windows и macOS была проверена с предоставленным деревом GTK/WebKit; полученные образы GUI исключительно на Go успешно прошли проверки выполнения в Linux. В одной сопоставимой сборке GUI с CGo встроенный способ занял 8.77 секунды, а linuxdeploy — 26.19 секунды. Размер встроенного образа gzip составил 133 МиБ по сравнению с 114 МиБ при прежнем способе с zstd, поэтому это сравнение измеряет весь процесс упаковки, а не только сжатие.

Пакеты Arch сохраняют предварительные выпуски в нативных метаданных пакета: например, `1.2.3-beta.2` преобразуется в `1.2.3beta.2-1`, который при сортировке предшествует финальному выпуску. В зависимостях Void допускаются простые имена пакетов, например `gtk4`, нормализуемое до `gtk4>=0`; явные сравнения версий и полные значения `name-version_revision` сохраняются. Используйте имена пакетов Void, а не имена файлов библиотек.

Для подписания DEB, RPM и Arch на любой поддерживаемой настольной системе можно использовать экспортированные закрытые ключи OpenPGP в текстовом или двоичном формате без GnuPG, `dpkg-sig` или `rpmsign`. В `linux.signing.certificate` укажите файл ключа, а в `credential` — имя переменной среды с его парольной фразой. DEB и RPM содержат встроенные подписи; для Arch публикуется отдельная подпись. Закрытые ключи считываются только на этапе подписания и не копируются в ресурсы пакета или повторно используемые артефакты кеша.

В существующих конфигурациях DEB/RPM, содержащих только идентификатор ключа GnuPG, по-прежнему используется внешний подписывающий модуль. Чтобы устранить эту зависимость, экспортируйте секретный ключ и укажите путь к нему. Используйте путь наподобие `./signing/release.asc`; если файл ключа отсутствует, недоступен для чтения или недействителен, операция завершается с ошибкой, а переход к связке ключей не выполняется. Подписи DEB сохраняют формат подписи пакета `dpkg-sig`; это не заменяет подписание метаданных выпуска репозитория apt.

Чтобы создать пакет Arch и отсоединённую подпись, используйте экспортированный файл закрытого ключа PGP в текстовом формате и при необходимости укажите имя переменной окружения с парольной фразой:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
build:
  environment:
    CGO_ENABLED: "0"
linux:
  signing:
    certificate: signing/private-key.asc
    credential: ARCH_SIGNING_PASSPHRASE
profiles:
  release:
    targets:
      linux/amd64:
        formats: [archlinux]
        sign: true
```

Задайте указанную переменную окружения в локальном окружении или хранилище секретов CI, затем выполните `wails3 build release`. Для незашифрованного ключа не указывайте `credential`. Средство подписания на Go работает на любом поддерживаемом хосте настольной системы и не требует GPG. Оно публикует исходный файл `.pkg.tar.zst` и соседний файл `.pkg.tar.zst.sig`; оба отдельно регистрируются в квитанции артефактов. Содержимое ключа не помещается во временную область и не сохраняется в кеше сборки. Подписи и результаты их публикации никогда не используются повторно из кеша. При сбое подписания сохраняется предыдущая опубликованная пара, а если установка любого из файлов завершается ошибкой, публикация обоих файлов откатывается. Это не делает две операции переименования в файловой системе атомарными для параллельных читателей.

Пакеты приложений macOS включают сопутствующие программы. Задайте `darwin.microphone_usage_description`, чтобы добавить текст об использовании, а при отсутствии пользовательского файла полномочий — также полномочие на аудиовход. Пользовательские исходные файлы plist и полномочий остаются без изменений. Для экспортированного удостоверения RSA PKCS#12 на любой настольной системе используется подписание средствами Go; `identity: "-"` включает переносимое подписание ad hoc. Для удостоверений из связки ключей в macOS по-прежнему используется `codesign`. Прикрепление билета выполняется средствами Go. Для отправки на нотариальное заверение можно использовать существующий профиль связки ключей нотариальной службы macOS либо командные учётные данные API App Store Connect:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
darwin:
  signing:
    certificate: signing/developer-id.p12
    credential: APPLE_CERT_PASSWORD
    timestamp_server: https://timestamp.digicert.com
  notarization:
    api_key: signing/AuthKey.p8
    key_id: ABCDEFGHIJ
    issuer_id: 00000000-0000-0000-0000-000000000000
```

В режиме API отправка, загрузка и опрос выполняются средствами Go без `notarytool`. Задайте все три поля и не указывайте `credential`; не храните закрытый ключ в системе управления версиями. Ключ считывается только во время подписания и не копируется в создаваемые ресурсы или кеш. Этот режим поддерживает командные ключи API и архивы размером до 5 ГиБ; многочастная загрузка и индивидуальные ключи API не реализованы. При отклонении сохраняется идентификатор отправки, а диагностический журнал Apple записывается в закрытый временный файл, путь к которому указывается в сообщении об ошибке. Отменённая или отклонённая отправка не заменяет ранее опубликованный результат. После принятия Wake получает и проверяет билет Apple и прикрепляет его средствами Go. С экспортированным удостоверением и командными учётными данными API подписание, отправку и прикрепление билета можно выполнять в Linux, Windows или macOS. Для профилей связки ключей по-прежнему требуются macOS и `notarytool`.

Переносимое подписание сертификатом поддерживает удостоверения RSA в файлах PKCS#12 с AES/PBKDF2 или устаревшим 3DES. Экспорты, зашифрованные с помощью RC2, необходимо повторно экспортировать с поддерживаемым шифром. Для нотариально заверяемых переносимых подписей необходимо явно указать службу меток времени SHA-2 по RFC 3161; реализованный на Go модуль проверки отклоняет устаревшие подписи меток времени SHA-1. Служба билетов следует наблюдаемому протоколу Apple и закрепляет Apple Root G3; Gatekeeper остаётся источником решения о доверии при распространении и об отзыве.

Подписанные выходные файлы сохраняют расширение своей платформы, например
`notes.signed.app` и `notes.signed.dmg`.

## Управление в режиме разработки

Во время `wails3 dev` введите команду и нажмите Enter:

| Команда | Действие |
| --- | --- |
| `r` | Принудительно пересобрать и перезапустить, включая неизменённую серверную часть. |
| `b` | Повторно сгенерировать привязки и пересобрать. |
| `f` | Перезапустить клиентскую часть. |
| `c` | Очистить терминал. |
| `q` | Остановить сеанс и его дочерние процессы. |
| `h` | Показать доступные команды управления. |

При неудачной сборке текущее приложение продолжает работать. Для команд управления требуется интерактивный терминал; перенаправленный через канал ввод не изменяет поведение сеанса.

## Проверка операций перед выполнением

При проверке плана разрешается тот же неизменяемый граф, который используется при выполнении. Текст предназначен для людей; JSON представляет собой версионируемый машиночитаемый контракт.

```bash
wails3 build release --plan
wails3 build release --plan --json
```

## Проверка конфигурации без сборки

Используйте специальную команду предварительной проверки в CI, в задаче редактора или перед фиксацией конфигурации. Если профиль не указан, она проверяет базовый манифест и все именованные профили; если профиль указан — только соответствующий полный запрос:

```bash
wails3 config check
wails3 config check release
```

Ошибки синтаксиса, схемы, семантики, путей, целевых систем, форматов, подписания, планировщика и возможностей хоста, обусловленных конфигурацией, выводятся тем же средством диагностики, что и в Build и Dev. Диагностика указывает поле и диапазон в исходном тексте, выводит исходную строку и каретку, а при необходимости содержит подсказку по исправлению. Значения окружения скрываются во фрагментах исходного текста, выводимых в диагностике. Ошибки хоста, вызванные исключительно параметрами командной строки, остаются обычными ошибками команды и не представляются ошибочно как недопустимый YAML.

## Использование ресурсов проекта

Пути в манифесте указывают на принадлежащие вам файлы, например значки, манифесты платформ, шаблоны пакетов и сценарии сопровождающего. Wails никогда не изменяет эти исходные файлы. Перед использованием инструментом они копируются в одноразовую рабочую область `.wails/`. Итоговые артефакты помещаются в `build.output`, а проверенная квитанция записывается в `.wails/artifacts/receipt.json`.

## Развёртывание на Android

Профили Android для рабочей среды создают AAB. Для локального развёртывания Wails самостоятельно собирает отладочный APK для конкретного ABI, устанавливает его с помощью ADB и запускает приложение:

```bash
wails3 android devices
wails3 android run --device SERIAL
wails3 android run --emulator AVD_NAME
```

Если селектор явно не указан, интерактивный терминал предлагает выбрать из подключённых устройств и настроенных виртуальных устройств Android. При автоматизации с несколькими доступными целевыми устройствами необходимо указать `--device` или `--emulator`.

Подключите поток журналов приложения и отслеживайте целевое устройство, пока приложение не завершится или вы не нажмёте Ctrl+C:

```bash
wails3 android run --emulator AVD_NAME --logs
wails3 android run --emulator AVD_NAME --logs --stop-emulator
```

Подключённые запуски отслеживают перезапуск приложения и сообщают об отключении целевого устройства или его переходе в автономный режим. По умолчанию эмуляторы продолжают работать, что ускоряет итерации. Параметр `--stop-emulator` задаётся явно, требует `--logs` и останавливает только целевой эмулятор при завершении подключённого сеанса. Если Wails запускает новый эмулятор, но ожидание его готовности завершается ошибкой или отменяется, соответствующий процесс автоматически завершается.

## Выполнение ограниченных обработчиков жизненного цикла

Экспериментальный интерфейс обработчиков запускает по одному принадлежащему проекту сценарию на каждом объявленном этапе. Обработчик не является командой оболочки: Wails выполняет файл напрямую из корня проекта, если не задано `directory`.

На хостах Unix сценарий должен быть исполняемым и начинаться со строки shebang. На хостах Windows сценарии `.cmd`, `.bat` и `.ps1` выполняются через фиксированные адаптеры интерпретаторов; ни на одной из платформ Wails не разбирает встроенную команду оболочки.

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
hooks:
  before_build:
    script: scripts/generate-version.sh
  after_package:
    script: scripts/check-packages.sh
profiles:
  release:
    targets:
      linux/amd64: {}
```

Поддерживаются этапы `before_build`, `after_build`, `before_package`, `after_package`, `before_sign` и `after_sign`. В зависимости от назначения обработчики сборки выполняются один раз для общего проекта или один раз для каждой целевой системы. Обработчики упаковки и подписания образуют барьеры вокруг всех форматов, запрошенных для целевой системы, при этом операции с форматами внутри барьера выполняются параллельно.

Обработчики получают одну переменную окружения, принадлежащую Wails: `WAILS_HOOK_CONTEXT_FILE`. Она указывает на защищённый JSON-файл с версионируемым контекстом вызова:

```json
{
  "version": 1,
  "phase": "after_build",
  "command": "build",
  "scope": "target",
  "project_dir": "/work/notes",
  "working_directory": "/work/notes",
  "profile": "release",
  "target": { "os": "linux", "arch": "amd64" },
  "output": "/work/notes/bin/notes",
  "declared_outputs": ["/work/notes/generated/version.go"]
}
```

Контекст содержит разрешённые пути, но в него никогда не копируются унаследованное окружение процесса или секреты. Wails создаёт его атомарно в каталоге `.wails/hooks/context/` с правами доступа к файлу только для владельца. После успешного выполнения или отмены файл удаляется. При сбое он сохраняется для диагностики, а путь к нему включается в сообщение об ошибке. Ненулевой код завершения приводит к сбою обычного шага Plan, а при отмене завершается группа процессов обработчика.

По умолчанию обработчики выполняются при каждом вызове. Включайте кеширование, только если для сценария полностью объявлены входы и выходы:

```yaml
version: 3
project:
  name: notes
  product_name: Notes
  identifier: com.example.notes
  version: 1.0.0
hooks:
  before_build:
    script: scripts/generate-version.sh
    cache: true
    inputs: [version.txt]
    outputs: [generated/version.go]
profiles:
  release:
    targets:
      linux/amd64: {}
```

Сам сценарий и его режим исполняемого файла являются неявными входами. Несколько выходов должны находиться в одном некорневом каталоге — это ограниченный артефакт, который Wails регистрирует и восстанавливает. Корневой каталог выходов не может содержать сценарий или объявленный вход, а кешированные деревья выходов могут включать только обычные файлы и каталоги, но не символические ссылки или специальные файлы. Обработчик, выполняемый всегда, запрещает кеширование последующих операций, поскольку невозможно безопасно получить цифровой отпечаток необъявленных побочных эффектов. Обработчик с поддержкой кеширования сохраняет кеширование последующих операций благодаря идентификатору своего объявленного артефакта.

## Миграция существующего проекта

Создайте и проверьте неактивный черновик:

```bash
wails3 migrate
wails3 migrate --dry-run
wails3 migrate --json
```

Консервативные задачи жизненного цикла без аргументов, запускающие принадлежащий проекту скрипт, преобразуются в хуки. Другое достижимое пользовательское поведение Taskfile указывается как блокирующая проблема. После проверки `wails.migrated.yaml` явно активируйте его:

```bash
wails3 migrate --activate
```

При активации `wails.yaml` создаётся атомарно. Taskfile, `build/config.yml`, скрипты и ресурсы не удаляются, не переименовываются и не изменяются. При недопустимом YAML операция завершается ошибкой YAML и никогда не возвращается к устаревшему маршруту.

## Материализация всех значений по умолчанию

Чтобы просмотреть или скопировать полную итоговую конфигурацию, сохраните неактивный снимок:

```bash
wails3 eject
```

При этом создаётся `wails.ejected.yaml`. Активная конфигурация никогда не перезаписывается.

## Период совместимости

`wails3 package` и `wails3 sign` — устаревшие псевдонимы одного и того же планировщика; в новой автоматизации следует использовать `wails3 build` с профилем или форматами. Развёртывание привязано к выпускам: в первом выпуске YAML становится способом настройки новых проектов, в следующем появляется предупреждение о маршрутизации через устаревший Taskfile, а ещё в следующем удаляется выполнение Taskfile вместе с псевдонимами. Для каждого перехода матрица приёмочных тестов на нативных хостах соответствующего выпуска должна быть полностью успешной.

Описание каждого поля, типа, значения по умолчанию и правила применимости см. в сгенерированном [справочнике по полям `wails.yaml`](/reference/wails-yaml-fields/).

В [справочнике по конфигурации `wails3 run`](/reference/wails-yaml-run/) описаны значения по умолчанию для локального запуска, переопределения для отдельных платформ и резервный вариант `go run .` при отсутствии манифеста.

今天，我们发布 Wails v3 Beta。

Wails 让 Go 开发者能够使用他们已熟悉的 Web 前端工具构建桌面应用，并使用各平台的原生 WebView，而不是嵌入式浏览器。v3是一次重大进步：它为应用提供了更直接的 API、更清晰的构建模型，也为人们一直希望 Wails 支持的桌面应用奠定了更好的基础。

这是 Beta 版本，并非最终的3.0版本。桌面 API 已经稳定，也已有团队在生产环境中使用v3，但你仍应在部署前进行全面测试。我们将利用 Beta 阶段与社区一起发现并解决最后的兼容性和工作流问题。Wails v2仍是当前的稳定版本，并将继续获得修复。

## Beta 阶段的文档

Beta 阶段期间，在 API 和工作流接受最终验证的同时，我们将英文文档作为权威来源进行维护。现阶段我们不接受翻译 PR。待文档足够稳定、译者无需反复返工后，翻译工作将在正式发布前恢复。

## v3包含哪些内容

- 明确的应用和窗口 API，包括一等的多窗口支持
- 通过静态源代码分析生成更丰富 TypeScript 绑定的 Go 服务，可保留注释和有意义的参数名称
- 可将前端资源和脚本与后端 API 打包在一起的服务——这是可安装且功能更丰富的插件的基础
- 基于 Taskfile、清晰可见且可供你检查、扩展和调试的构建系统
- 服务器构建，可在没有原生桌面窗口的情况下运行同一个应用及其服务
- 在受支持的平台上，为 Intel、Apple Silicon、amd64 和 arm64 架构提供现代化的 macOS、Windows 和 Linux 桌面支持
- 适用于 iOS 和 Android 的实验性移动端支持，可供探索，但不在桌面版 Beta 的兼容性承诺范围内

## 为什么要推出v3

Wails v2让使用现代 Web 前端构建 Go 应用变得简单直接。它一直很好地服务着这个项目以及众多应用。但其单窗口、由上下文驱动的运行时和高度托管的构建流程，使一些常见的桌面开发工作变得比应有的更困难。

v3采用了不同的模型。应用、窗口、服务、事件和平台能力都是显式对象。这使得应用规模扩大后，框架仍更容易理解，也让多窗口等功能成为应用模型的常规组成部分，而不是权宜之计。

## 新增内容

### 为真正的桌面软件而构建的应用 API

v3以显式的应用生命周期取代了v2的`wails.Run(...)`配置方式。你可以创建应用、注册服务、创建窗口，并与负责所需行为的对象直接交互。

这消除了大量隐式的上下文传递。窗口操作归属于窗口；应用级操作归属于应用。对于多窗口应用而言，这是更自然的模型，也更适合测试和维护较大的代码库。

在 Alpha 阶段使用过v3的用户给出了极其积极的反馈。开发者尤其认可这种显式模型：它让代码更容易理解、所有权更清晰，也让复杂的桌面应用可以在不与框架抗衡的情况下不断发展。

### 一等的多窗口支持

多窗口是v3的核心能力。窗口拥有各自的生命周期，可以在运行时创建、管理和关闭。因此，需要编辑器、检查器、偏好设置、工具窗口或多个独立 UI 区域的桌面软件有了更清晰的实现路径。

### 服务和生成的绑定

Go 服务取代了旧版绑定模型。它们让应用逻辑保持为普通的 Go 代码，并明确界定与前端之间的边界。生成的绑定采用能够反映应用及其服务的结构，让开发者更容易找到并使用向前端公开的 API。

v3通过静态源代码分析生成这些绑定。这意味着生成器可以保留开发者写入代码的信息，包括注释和有意义的参数名称，而不是通过反射探查已经构建好的程序。由此得到的前端 API 更丰富、更实用，生成流程也更容易理解和维护。

服务还可以将前端资源和脚本与其 Go 代码一起挂载。这让一项能力的所有组成部分都有一个统一归属：后端 API、所需的 JavaScript 或 UI，以及与宿主应用的集成点。这为能够开箱即用地提供丰富功能的 Wails 插件打开了大门——安装插件、挂载其服务，然后使用该功能——无需自行拼装一组松散的绑定和前端依赖。通用插件系统不在本次 Beta 的范围内，但v3让这一方向切实可行，而v2绑定模型无法做到这一点。

### 可供检查和调整的构建系统

v3让项目的构建结构清晰可见。项目不再把所有构建决策隐藏在单个命令中，而是采用约定式布局和基于 Taskfile 的构建配置，可与应用一起理解、扩展和调试。

### 更强大的跨平台桌面基线

该 Beta 支持 amd64 和 arm64 架构的 Windows、Intel 和 Apple Silicon 架构的 macOS，以及 amd64 和 arm64 架构的 Linux。使用 WebKitGTK 6.0的 GTK4 是默认的 Linux 技术栈；在整个v3.0系列中，GTK3 仍可作为旧版选项使用。移动端支持令人期待，但仍处于实验阶段，不在桌面版 Beta 的兼容性承诺范围内。

此版本还包含提高日常使用可靠性所需的工作：改进的平台行为、能力更强的窗口模型、更清晰的诊断，以及附带校验和与来源信息的发布产物。

## 从v2迁移

v3是一个新的主版本，迁移需要真正进行移植，而不只是更改版本号。主要的概念变化包括应用和窗口生命周期、以服务取代上下文绑定、以直接的应用和窗口 API 取代v2运行时包，以及重新生成前端绑定。

我们已发布[v2到v3的迁移指南](/migration/v2-to-v3/)，其中逐步讲解了这些变化，并包含功能映射和测试清单。该手动指南是本次 Beta 支持的迁移路径。请不要期待所有v2项目都能在未经审查的情况下完成转换：请测试转换结果，有计划地移植运行时调用，并在新应用准备就绪前保留v2。

我们也在评估一个实验性迁移助手。它不属于本次 Beta 版本；只有在针对有代表性的真实v2项目完成验证后，我们才会推荐使用。

## 坦诚回顾这段历程

首个v3 Alpha 标签发布于18年2023月。Alpha 阶段持续了很长时间，不能只用一句含糊的说明一带而过。

在此期间，项目发生了巨大的变化。首个 Wails v2 Beta 于2021年 9 月面向 Windows 发布时，代码仓库大约有4000颗星。到2022年 9 月发布v2版本时，星标数约为10300。如今已超过35000。这种增长是一种殊荣，但也改变了良好项目治理应有的方式：更多用户依赖发布决策，更多贡献者需要清晰的参与途径，而更多工作也要用于提升项目的可预测性，而不只是添加下一个功能。

我并非总能以这种增长所要求的速度和清晰度调整我们的流程。这是我的责任。解决之道不是许下宏大的承诺，也不是让每项决定都变成繁文缛节；而是更清楚地说明哪些内容受到支持、哪些仍处于实验阶段、如何作出决定，以及我们接下来要做什么。

这项工作从此次 Beta 版开始。我们现在已经明确设立了 Beta 版、候选发布版和正式发布版（GA）里程碑，作出了更清晰的兼容性承诺，更新了安全策略，并为涉及公开行为变更和新增功能的事项建立了 WEP（Wails 增强提案）流程。随着 Wails 的发展，我们将继续完善路线图并审视项目治理。我们的目标是让项目更值得信赖、更易于参与贡献，而不是让它更难推进。

我们还将重新启用[Wails subreddit](https://www.reddit.com/r/wails/)，并积极维护它，使其成为另一个开展实务讨论、提出问题和反馈意见的平台，伴随v3逐步迈向正式发布。

## 安装并试用 Beta 版

版本发布后，使用以下命令安装最新的v3 CLI：

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@latest
```

创建项目之前，请运行引导式设置向导。它会检查你的本地开发环境，并帮助配置 Wails 所需的依赖项：

```sh
wails3 setup
```

![深色模式下的 Wails v3设置向导](/assets/screenshots/wails3-setup-wizard-dark.png)

### 创建项目

一切准备就绪后，使用以下命令创建项目：

```sh
wails3 init
```

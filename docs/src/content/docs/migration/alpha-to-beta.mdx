This page is for projects already running a v3 alpha. If you are coming from
Wails v2, start with the [v2 to v3 guide](/migration/v2-to-v3) instead.

The short version: there is no code migration. The alpha to beta step is a
version bump and a regeneration, and it should take a few minutes.

## What actually changes

Very little in the code, and quite a lot in what the project promises you:

- **The API is stable.** From beta to 3.0, changes are additive or fixes.
  Anything that does have to change gets deprecated first, with the removal
  version named in the deprecation.
- **Beta releases receive security fixes. Alphas do not.** If you stay on an
  alpha, you stop receiving them. That is the main reason to move.
- The [project status page](/status) has the full picture of what is settled
  and what is still moving.

## Upgrade

### 1. Update the CLI

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@latest
wails3 version
```

`@latest` resolves to the beta, because a beta sorts above every alpha under
semantic-versioning rules.

### 2. Update the Go module

From your project directory:

```sh
go get -u github.com/wailsapp/wails/v3
go mod tidy
```

Pin the exact version rather than tracking latest. Prereleases move faster than
your release schedule does, and an unpinned dependency turns someone else's
Tuesday into your broken build:

```sh
go get github.com/wailsapp/wails/v3@v3.0.0-beta.0
```

### 3. Update the frontend runtime

```sh
cd frontend
npm install @wailsio/runtime@latest
```

**The JavaScript runtime carries its own version number, and it does not match
the CLI.** A beta CLI pairs with an `@wailsio/runtime` that still reports an
`alpha` version string. That is expected: the npm package is versioned
independently of the Go module and the CLI, and `latest` is the correct thing
to install. If your CLI says `v3.0.0-beta.0` and your `node_modules` says
`3.0.0-alpha.97`, nothing is wrong.

New projects generated by `wails3 init` pin `"@wailsio/runtime": "latest"`, so
they pick this up without any action.

### 4. Regenerate bindings

```sh
wails3 generate bindings
```

Bindings are generated from your Go services, so they need regenerating any time
the runtime under them changes. Skipping this is the most common cause of an
upgrade that builds but misbehaves at runtime.

### 5. Build and run

```sh
wails3 build
```

## If something breaks

Check these in order, because they account for most upgrade problems:

1. **A stale lockfile.** `package-lock.json` can pin an older runtime even when
   the dependency says `latest`. Remove `node_modules` and the lockfile, then
   reinstall.
2. **Bindings not regenerated.** See step 4.
3. **A cached CLI.** `wails3 version` should report the beta. If it reports an
   alpha, an older binary is earlier on your `PATH`.

If none of that explains it, please
[open an issue](https://github.com/wailsapp/wails/issues/new/choose) with your
`wails3 doctor` output, the version you upgraded from, and the exact error.
Upgrade reports from real projects are the most useful thing we receive during
a beta.
